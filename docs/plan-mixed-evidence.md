# Issue №12: разные способы проверки одного задания

24.10.2026 владелец поручил разделить automated/browser/process, сохранить
историю и итоговую приёмку по брифу, после проверок выпустить обновление
и обновить все свои установки. Полные модельные проекты не запускать.

## Контракт изменения

- Новый `mode: mixed` в test-intent, включённый политикой нового init.
  Прежние `behavior_change` / `not_applicable` сохраняют свои правила.
- Точный список критериев задачи не меняется. Для каждого критерия задаются
  один или несколько способов проверки: automated, browser, process.
  Пара критерий/способ уникальна; причина, процедура и ожидаемый результат
  обязательны. План проверки не считается выполненной проверкой.
- Новые тестовые файлы и настоящий RED покрывают только автоматическую
  группу. Без автоматической группы RED отсутствует, а не подделывается.
  Свежая адресная проверка кандидата перед сдачей остаётся обязательной.
- Браузерные/процессные свидетельства содержат задачу, попытку, candidate,
  способ, критерии и наблюдение; приложенные файлы связаны SHA.
  Старое свидетельство от другой версии или попытки не даёт PASS.
- Worker, критики и приёмщик явно оценивают все пары критерий/способ.
  Нельзя поставить критерию PASS, если один из его способов не проверен.
  Это происходит в существующих отчётах ролей, без нового интервью или роли.
- Первичная классификация записывается до первой сдачи; revisions добавляются
  к истории. Объявленную автоматическую проверку нельзя убрать/понизить ради
  обхода RED; после начала критики контракт заморожен. Попытки, участники,
  карточки, критерии, предыдущие отчёты и раунды не сбрасываются.
- Пять отказных границ сохраняются, с честной типизацией ручных проверок.
  Общепроектная независимая приёмка, trace брифа и clean clone не меняются.
- Активные закреплённые пользовательские runtime автоматически не мигрируют.
  Обновление установок применяется к новым запускам; отдельная миграция старого
  проекта не входит в это поручение.

## Этапы

1. Реализация контрактов, сохранности истории и проверок свидетельств.
2. Формы, адресный контекст, инструкции и отображение типов в деталях задачи.
3. Регрессии и отрицательные проверки; независимое техническое и evidence-ревью.
4. GitHub PR, итоговая CI на трёх ОС, stable Release, проверка ресурсов.
5. Штатное обновление каждой установленной копии с резервной копией и read-back.

Хеши и схемы доказывают привязку и сохранность, не истинность описанного
наблюдения. Её оценивает независимый проверяющий; полного модельного прогона
этот выпуск не заменяет.
