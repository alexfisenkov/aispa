# Адресный мост новой попытки владельца для закреплённого runtime 0.4.0

Этот мост относится к выбранному после двух ремонтов runtime с digest
`062f4fb7d168422870c47bb63725617947aef29bb2518811b8e2c5fae2c5a471`.
Он добавляет только путь `new-attempt ID --owner-source-file ... --source-sha256 ...
--owner-decision-id ... --quote ...` в отдельную неизменяемую копию. Старый
`--brief` и прежние попытки сохраняются. Локальный источник должен содержать
дословный вопрос с областью разрешения и ответ владельца с выбранной цитатой.
Инструмент проверяет точные байты и связь с попыткой, но не удостоверяет
личность автора текста.

Инструмент: `skills/aispa/tools/repair_owner_attempts.py`. Он запускается из
этой рабочей копии, а не из закреплённого runtime. Порядок: `inspect` без
записи; `prepare` с точным SHA журнала из inspect; независимое чтение diff,
manifest и разрешения; `apply` с точными SHA manifest и журнала, локальным
`approval-file`, SHA просмотренного разрешения, точной цитатой и явным
`--confirm`; повторное `inspect` и проверка выбранного CLI. Никакой
автоматической подготовки или выбора при запуске AISpa нет.

Пример формы команд (подставить конкретные абсолютные пути и SHA из текущего
осмотра):

```sh
python3 -B skills/aispa/tools/repair_owner_attempts.py --root PROJECT inspect
python3 -B skills/aispa/tools/repair_owner_attempts.py --root PROJECT prepare \
  --candidate-package skills/aispa --expected-journal-sha256 JOURNAL_SHA \
  --expected-approval-sha256 APPROVAL_SHA --owner-quote OWNER_QUOTE
python3 -B skills/aispa/tools/repair_owner_attempts.py --root PROJECT apply \
  --manifest-file MANIFEST_PATH --expected-manifest-sha256 MANIFEST_SHA \
  --expected-journal-sha256 JOURNAL_SHA --approval-file OWNER_DECISION_FILE \
  --expected-approval-sha256 APPROVAL_SHA --owner-quote OWNER_QUOTE --confirm
```

`prepare` копирует все 97 файлов прежнего runtime и вставляет проверенные
фрагменты только в `tools/aispa.py`, `tools/aispa_core/team.py`,
`tools/aispa_core/workflow.py`, добавляя
`tools/aispa_core/owner_task_attempt.py`. Исходные файлы сверяются с
фиксированными SHA-256. Точный diff и полный inventory нового runtime
записаны в manifest. Другие возможности текущего пакета в закреплённый runtime
не переносятся. Исторические runtime, policy, брифы, требования и события
остаются побайтно неизменными; `apply` добавляет одно событие
`runtime-repaired:owner-task-attempt-0.4.0` и меняет только активный указатель
runtime с его квитанцией. Подготовленная копия сама по себе не выбрана.

Допустим только выбранный digest выше и его точная цепочка двух прежних
квитанций. Применение сверяет manifest, исходный префикс журнала, CAS,
SHA файла разрешения, точную цитату и отсутствие ссылок. Журнал проверяется
потоком с удержанием только нужных состояний; снимок прежнего журнала
копируется блоками. Файлы свидетельств публикуются после полной записи и
`fsync`, без замены существующего пути. Если ошибка возникла после начала
append, свидетельства сохраняются: завершённое событие проверяется чтением,
а частичный журнал передаётся штатному восстановлению; автоматического второго
append нет. После выбора повторный `inspect` проверяет цепочку и новый digest.
Нельзя использовать мост как
обновление установленного AISpa или перенос политики; выпуск, GitHub CI и
установки этим действием не выполняются.

Изолированные тесты строят короткий синтетический журнал из точного Git
выпуска 0.4.0 и двух исторических repairs. Они проверяют сохранность старых
байтов, единственное событие и отказы при неверном pin, изменённом источнике,
manifest, CAS, отсутствии разрешения, ссылке и ошибке записи. Отдельный
интеграционный тест открывает заблокированную T01 настоящей командой нового
закреплённого CLI и перечитывает историю. Это подтверждает механику на
тестовой копии; выбор в рабочем прогоне и будущая предметная проверка T01/T06
подтверждаются отдельно.

Ожидаемый digest полного нового runtime:
`e7018aecae8a61f9b766b676013e01a2b2ef6f23090007b1691b2f433bf77211`.
Это расчёт на read-only точном старом pin и локальных source-файлах; в живом
прогоне он ещё не выбран.

Сначала тест был RED: `PYTHONPATH=tests python3 -B -m unittest
tests/test_runtime_owner_attempt_repair.py -v` завершился `ImportError` из-за
отсутствия `runtime_owner_attempt_repair`. Поздний раунд RED отдельно
воспроизвёл пять дефектов до исправления: удержание всего журнала, потерю
свидетельств после append, частично записанный файл и принятие случайного
README как разрешения. После исправления адресный набор прошёл 20/20,
`py_compile` трёх новых Python-файлов и `git diff --check` прошли. Тесты
используют временные проекты, точный Git release и старые
maintenance-команды; основной журнал не читают. После выбора на синтетической
T01 проверен `DisplayJournal` через полный `dashboard_snapshot.calculate`:
он показал две попытки, вернул SHA текущего журнала и не записал в него ничего.
Это совместимость текущего viewer-кода в тестовой копии, не приёмка живой панели.

Не проверены Windows, полный тестовый набор, CI, живой browser/dashboard,
канонический `prepare/apply` и новые фактические T01/T06. Их результат нельзя
выводить из этих локальных проверок.
