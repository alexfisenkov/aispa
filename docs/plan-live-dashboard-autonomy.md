# 0.3.2: автономная работа и живой дашборд

Исторический план выполненного выпуска 0.3.2.
[Доставка и границы проверки](validation-0.3.2.md), [текущий статус](status.md).

## Заказ владельца

Вопросы — только в первоначальном брифе. После него агент явно сообщает,
что можно отойти; обычные решения принимает сам и перечисляет в финале.
Панель должна обновлять проверки, этапы, задачи и требования, показывать
требования/критерии внутри задач, цветовые состояния и приблизительное время.
Порядок: общая плашка → проверки → семь этапов → два показателя времени →
горизонтальные строки задач по волнам → полный реестр требований.
Разрешены GitHub, выпуск сразу после проверок и обновление установок.
Новых полных модельных прогонов нет.

## Установленные причины

- В исходном wait отсутствовала проверка auto; сброс sealed после нового brief
  до задач повторно открывал вопросы. Контракт автономии терялся при передаче
  пакета и восстановлении краткой памяти.
- После второй завершённой задачи начинался расчёт ETA. Pending-задача уже
  имела в проекции elapsedSeconds=null; повторный elapsed вызывал round(None)
  и обрывал весь status. Ошибка воспроизведена read-only на работающем проекте.
- Требования сводились к unfinished до окончания всех связанных задач; gates
  были только boolean, сверка волны вообще не выводилась.
- Устаревший daemon мог переиспользоваться для нового run/версии, а HTML был
  загружен один раз. Старые pinned-прогоны не обновляются вместе с установкой.
- Здоровое HTTP-соединение само по себе не доказывает новые действия агента.

## Изменения и границы

1. firstBriefingClosure только в новых init; неизменный факт первого seal,
   notify-autonomous-start, контракт в пакете/карточке/памяти. Seal вне batch.
   Полномочия и требование реального согласия host не расширяются; недоступное
   фиксируется блокером, независимая работа продолжается.
2. Unknown-clock-safe расчёт; ETA не прибавляет activeSince второй раз.
   До измерений широкий ориентир по классам задач и волнам, затем observed.
3. Additive gate/requirement/task/wave details из действительных receipts;
   никакого принятия только по записанной активности или изменению файлов.
4. Новый компактный интерфейс, раскрытие деталей, подписанные цветовые состояния,
   сохраняющееся раскрытие, корректная работа без связи и при повреждённом JSON.
5. Identity managed service включает run/runtime/asset. Explicit refresh-view
   совместимо читает известный старый стабильный журнал новым viewer, сохраняет
   старый HTML; байты pinned runtime, policy, active.json и journal не меняет.
6. Code memo только внутри одного HTTP-запроса, новое чтение заново проверяет
   изменения кода/источников/evidence. Журнал проверяется прежним способом.

## Проверки

Целевые Python/Node, negative autonomy, runtime None-time, живой HTTP после
второй completed, старый daemon и refresh-view, read-only guards, одинаковые
хеши cache, live UI с раскрытием при узком/широком viewport. Два круга критики
при замечаниях. Один финальный CI с Windows; Mac допускается до её завершения
по прежнему решению владельца. Затем Release → сверка ресурсов → update-apply
→ локальный read-back. Реальный LLM-дисциплина и универсальная поддержка любого
неизвестного старого журнала не объявляются доказанными.
