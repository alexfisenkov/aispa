# Alpha.10: парный модельный тест

Отчёт от 21.10.2026. Оба запуска выполнены 20.10.2026 по UTC.

**В этом опыте AISpa прошёл полную приёмку по брифу; контрольный процесс
оказался быстрее и экономнее, но его продукт нарушил одно обязательное
условие обработки ошибок. Преимущество AISpa одновременно по качеству,
скорости и расходу токенов не подтверждено.**

Это один небольшой проект, а не универсальный рейтинг навыков.
Инструкции и движок AISpa в ходе испытания не изменялись.

## Что и как проверяли

Задание — локальная утилита `study_report.py`: строгий CSV занятий → JSON
по курсам и датам, фильтры, безопасная запись файла, понятные ошибки,
README и собственные тесты. Все семь групп требований обязательны.
Python 3.11+, только стандартная библиотека, без сети и установки пакетов.

| Условие | Одинаково для обеих ветвей |
| --- | --- |
| Модель всех оркестраторов и потомков | `gpt-6.1-sol`, reasoning `high` |
| Среда | Один Mac; разработчикам доступен Python 3.14.0; внешняя приёмка на 3.11.15 |
| Исходная версия проекта | Один начальный Git commit, отдельные каталоги и свежие контексты |
| Лимит | 60 минут от отправки задания; до двух одновременных дочерних агентов |
| Бриф и проверки | Зафиксированы SHA до запуска; скрытые тесты не выдавались исполнителям |
| Порядок | Случайно выбран до запуска: AISpa, затем контроль |
| Самостоятельность | Без вопросов владельцу и ремонта со стороны координатора эксперимента |

AISpa закреплён на `0.1.0-alpha.10`,
`bd1bc61378341860fc0465b9c8d13bdbd6ec29b7`, режим `auto/balanced`.
Контрольный пакет — `2.1.0`,
`9fc898cbe941d5b8a369f1dd657e9119676eb44f`, режим `full/normal`.
Каждый сохранял свой процесс. Два разных критика AISpa и отдельный
приёмщик действительно выполнялись; контрольному процессу дополнительные
этапы AISpa не навязывались.

Координатор передал обеим ветвям только проверенные идентификаторы нативных
потоков, которые инструмент среды не показывал в обычном ответе создания
агента. Это общий адаптер среды; советов по реализации не было.
Все дополнительные ходы собственных потомков включены в расход.

После сдачи заморожены точные commit:

- AISpa: `96b5dbcfa1cb6f4e8def0475a157a2cbe1d7bf42`.
- Контроль: `e7a955c0ee87caf4ea084a0792fc26c3f1af6c25`.

Внешняя проверка использовала чистые клоны именно этих commit.
Два свежих проверяющих получили только продукт, бриф и заранее заданную
рубрику, под обозначениями X/Y и в разном порядке. Названия процессов,
токены и время им не показывались. Для маскировки в копии README X убран
только начальный YAML-блок с названием метода; исходный клон не менялся.
Это частичное ослепление по названиям: стиль кода теоретически может
подсказать происхождение.

## Соблюдение брифа

| Проверка | AISpa | Контроль |
| --- | --- | --- |
| Заранее закреплённый скрытый CLI-набор | 61 PASS / 0 FAIL / 0 SKIP | 61 PASS / 0 FAIL / 0 SKIP |
| R1: запуск, Python 3.11, stdlib | PASS | PASS |
| R2: CSV и полная валидация | PASS | PASS |
| R3: фильтры дат | PASS | PASS |
| R4: точный JSON | PASS | PASS |
| R5: атомарная запись и сохранность | PASS | PASS |
| R6: ошибки и код завершения | PASS | **FAIL: отказ записи stdout** |
| R7: README, свои тесты, чистый клон | PASS | PASS |
| Собственные тесты из чистого клона | 25 методов, PASS | 5 методов с большим числом subtests, PASS |
| Приёмка по всем обязательным условиям | **Принят** | **Не принят** |

Число собственных методов не является сравнением покрытия. Оба набора
проверяют успешные и ошибочные сценарии. Команда из README выполнена
как `python3.11 -B -m unittest discover -s tests -v`: явно выбран минимальный
интерпретатор, `-B` отключает создание bytecode. После проверки Git чистый.

Дефект R6 найден при слепом чтении кода **после запуска**, вне исходных
61 теста. Он не добавлен задним числом в их счётчик. Рубрика заранее
требовала чтения кода и блокировала приёмку при подтверждённом нарушении
любого обязательного требования.

В дочернем процессе запрещена запись в обычный файл через
`RLIMIT_FSIZE=0`, сигнал `SIGXFSZ` игнорируется; stdout направлен в этот файл.
Это реальный отказ ОС, без подмены функций приложения. Для обеих версий
использован один сценарий на Python 3.11:

- AISpa: код **2**, одна строка `Ошибка: [Errno 27] File too large`,
  пустой stdout.
- Контроль: код **120**, та же строка и дополнительная ошибка Python
  при повторном сбросе буфера stdout.

В контрольной реализации защита при завершении охватывает только
`BrokenPipeError`; обычный `OSError` оставляет буфер для повторного flush.
AISpa закрывает stdout при `OSError`/`UnicodeError`. Находку независимо
воспроизвели второй проверяющий и координатор. Входные файлы сохранились.
Это узкий, но реальный обязательный сценарий; обычная обработка CSV
у обеих версий работает. Продукты после раскрытия проверок не исправлялись.

## Качество результата

Баллы — суждение двух проверяющих по пяти заранее заданным осям 0–4,
а не объективная сумма качества. Пары ниже означают «проверяющий A / B».

| Ось | AISpa | Контроль | Основание |
| --- | --- | --- | --- |
| Структура | 4 / 4 | 3 / 4 | У AISpa явнее разделены валидация, агрегация и запись; оба решения компактны |
| Ошибки | 4 / 3 | 2 / 2 | AISpa проходит отказ stdout; у него остаётся косметический пробел с экранированием управляющих символов в сообщениях |
| Свои тесты | 3 / 3 | 3 / 3 | Хорошее покрытие; нет полной регрессии всех отказов stdout. У контроля сильнее инъекции частичной записи и закрытия файла |
| Документация | 4 / 4 | 3 / 4 | Оба README пригодны; у AISpa есть готовый CSV-пример. Проверяющие разошлись в оценке обещания exit 2 в контрольном README |
| Простота | 4 / 4 | 4 / 4 | Один production-модуль, stdlib, без лишних зависимостей |

Первый вердикт B не заметил сбой stdout и давал контролю 4 за ошибки и
тесты. Во втором адресном круге B воспроизвёл дефект и изменил эти оценки
на 2 и 3. Исходный отчёт сохранён; эта коррекция не скрыта.
Из разницы в один субъективный балл статистическая победа не выводится.

## Время и фактические токены

Счётчики взяты из уникальных нативных ответов модели во всём дереве
каждого оркестратора, включая финальные ответы и собственные проверки.

| Показатель | AISpa | Контроль | AISpa / контроль |
| --- | ---: | ---: | ---: |
| Полное время ветви | 46 мин 12,941 с | 29 мин 14,370 с | 1,58× |
| Входные токены вне кэша | 1 356 608 | 339 738 | 3,99× |
| Кэшированные входные токены | 53 661 696 | 12 755 328 | 4,21× |
| Весь вход, включая кэш | 55 018 304 | 13 095 066 | 4,20× |
| Выходные токены | 167 828 | 81 507 | 2,06× |
| Из них reasoning | 39 423 | 26 524 | — |
| Ответы модели с usage | 432 | 141 | 3,06× |
| Потоки, включая оркестратор | 14 | 8 | — |

Кэш входит во вход, reasoning входит в выход: повторно их не складываем.
Это накопленный расход на многократную передачу контекста, а не размер
одного контекстного окна. Около 97,5% входа у обеих ветвей были кэшированными.
Денежная стоимость и списания подписки из этих счётчиков не выводятся.

Время начинается с записанного `dispatch_at` перед вызовом создания агента
и заканчивается последним завершением всего дерева. Ожидание детей и их
проверки включены. Между `dispatch_at` и первым нативным `task_started` прошло
18,231 с у AISpa и 42,198 с у контроля. Почти весь этот интервал предшествовал
самому вызову создания агента: это задержка координатора/отправки, а не
доказанная очередь провайдера. Время от первого `task_started` — 45:54,710
и 28:32,172 соответственно. Внешняя приёмка после заморозки не включена.

Независимый аудит пересчитал 573 уникальных ответа и 22 потока, сверил
модель/effort каждого хода, суммы и неизменность нативных логов. У обеих
ветвей полнота сохранённой хостом телеметрии подтверждена; поздних
неучтённых потомков не обнаружено. Это не проверка биллинга или запросов,
для которых провайдер вообще не выдал usage. Связь финального ответа с usage
подтверждена порядком событий хоста, без прямой пары item_id→response_id.

Токены подготовки эксперимента, калибровки измерителя, общего координатора
и внешних проверяющих исключены из обеих ветвей. Их полный общий расход
не измерен и не считается нулевым. В календарное время ветвей входят
описанные выше задержки до нативного запуска по заранее выбранной границе.

До этой пары была прервана попытка на `gpt-6-sol` из-за перегрузки.
По явному решению владельца обе ветви начали заново на `gpt-6.1-sol`.
Старая попытка сохранена отдельно: наблюдались 417 621 входной токен
вне кэша, 10 093 568 кэшированных и 41 603 выходных; телеметрия неполная.
Эти затраты не приписаны ни одной ветви основной пары.

## Почему получился такой результат

Наблюдаемое различие — AISpa выполнил больше подготовительных и проверочных
этапов. Его оркестратор сделал 174 ответа модели против 82 у контроля;
всего участвовали 13 потомков против 7. У AISpa отдельно работали разборщики
брифа, идеи, исследование, покрытие, планирование, два критика, приёмка задачи,
волны и всего продукта, запись знаний. Проверка и исправление формата
служебных отчётов тоже вошли в расход.

Это объясняет, где искать накладные расходы, но не доказывает, что каждый
дополнительный этап лишний или что именно два критика предотвратили дефект.
Обе ветви обнаруживали проблему закрытого stdout в собственном процессе;
AISpa обобщил обработку на другие ошибки записи, контроль исправил только
сломанный канал. Без отдельного эксперимента причинный вклад ролей неизвестен.

По заранее принятому правилу AISpa результативнее **в этом опыте**:
только он прошёл все обязательные условия. Контроль быстрее и экономнее
при почти том же обычном поведении, но сдача с дефектом R6 не равна принятому
продукту. Считать AISpa одновременно более быстрым или дешёвым нельзя.

## Ограничения и следующий шаг

- Одна пара, один заранее подробный CLI-бриф, одна модель и один Mac.
  Не проверены неоднозначная идея, большой существующий проект, UI,
  память между запусками, нативная Windows, Claude Code и Cursor.
- Случайный последовательный порядок не устраняет различия кэша,
  загрузки провайдера и случайности модели. Нет статистической значимости.
- Нет абляции YAML/памяти: их собственную экономию этот тест не измеряет.
- Сырые логи, частные архивы контрольного навыка и Git bundles кандидатов
  сохранены локально. Публичные агрегаты позволяют проверить арифметику,
  но без частных артефактов не позволяют независимо повторить весь опыт.

Следующая инженерная задача — сократить служебный обмен и повторное чтение
контекста AISpa, сохранив два критика и отдельную приёмку. Упрощать следует
сначала оформление и передачу доказательств. Применять такую оптимизацию
к уже измеренным продуктам нельзя: после изменения нужен новый заранее
закреплённый набор разных проектов с чередованием порядка.

[приёмка и воспроизведённый отказ](pilots/alpha.10/paired-test/acceptance.json).
Этот отчёт не изменяет опубликованный пакет и не является новым релизом.
