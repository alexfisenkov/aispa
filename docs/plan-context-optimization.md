# Оптимизация контекста после парного теста alpha.10

Поручение владельца: сократить служебный обмен и токены, сохранить два
независимых круга критики и приёмку, затем сравнить с закреплённым референсом
на нескольких проектах одной моделью. Логотип, название мастерской и AISpa
в панели должны открывать публичный канал `https://t.me/masterskaya_video`.

Исходный результат: [парный тест alpha.10](validation-alpha.10-paired-test.md).
Количество сохранённых байтов и ответов модели не является само по себе
экономией токенов или доказательством лишних проверок.

## План и критерии

1. Заготовки отчётов четырёх ролей: движок подставляет известные идентификаторы,
   критерии, хеши и связи. Выводы, статусы, независимость и evidence остаются
   явной работой проверяющего. Незавершённая заготовка не проходит приёмку.
2. Краткий режим служебных ответов CLI: полный ответ сохраняется с SHA и
   адресом; коды выхода, блокировки и прежний формат по умолчанию сохраняются.
3. Стабильные ссылки на одинаковые разделы context: повторное сохранение
   не создаёт новые адреса. Повреждение или ссылка не перезаписываются молча.
   Свежие критики и приёмщик читают источники независимо; собственный
   прочитанный неизменный материал можно повторно использовать только внутри
   сохранённого контекста того же участника.
4. Уточнить финальный порядок проверок, чтобы новая общая verify не
   обесценивала только что выполненное ревью волны без изменения продукта.
5. Добавить семантическую ссылку шапки, клавиатурный фокус и проверку в браузере.
6. Целевые тесты → два круга независимой критики с адресными исправлениями →
   полный локальный набор → GitHub → одна финальная CI для кандидата.
7. До модельных запусков закрепить пакеты, три брифа, стартовые деревья,
   скрытые проверки и порядок. Проекты: новый CLI, HTTP API, изменение
   существующей библиотеки. Шесть изолированных запусков на
   `gpt-6.1-sol/high`, одинаковый лимит, полный native usage всех потомков.
8. Чистые клоны, скрытая приёмка и слепое ревью после заморозки. Отдельно
   качество, время, вход вне кэша, кэш и выход; никакого ремонта после
   раскрытия проверок. Сохранить неудачные и инфраструктурные попытки.

## Границы

Не удалять роли и обязательные требования, не превращать шаблон в PASS,
не менять journal/receipts ради экономии, не подменять реальные токены
байтами. Глобальные установки не обновлять. Закреплённый референс не
исправлять. Кандидат в Git отличается от опубликованной alpha.10;
новый Release требует отдельной записи о выпуске.

## Статус

Пункты 1–6 выполнены: формы/краткий вывод/стабильный context/порядок/ссылка,
локальные проверки, два круга критики и финальная CI на трёх ОС.
[Свидетельства](validation-context-optimization.md).

Пункты 7–8 выполнены: шесть замороженных запусков, полная сохранённая native
телеметрия, чистые клоны, одинаковые внешние проверки, два слепых рецензента
на пару и независимый аудит измерений. [Отчёт](validation-context-optimization-paired-test.md).

Референс продуктивнее на этой батарее: 3/3 принятых продуктов с замечанием
к документации против 1/3; меньше времени, входа вне кэша и выхода в каждой
паре. Два круга критики AISpa и отдельные приёмщики подтверждены фактически.
Снижение затрат повтора CSV сопровождается дефектами нового продукта;
улучшение продуктивности на равном качестве не подтверждено.

Следующий долг: устранить блокировку приёмки будущей финальной передачей,
замкнуть регистрацию подготовительных фаз и сократить повторные согласования
малых задач. Проверки I/O-отказов и протокольных ошибок требуют усиления.
Измеренные продукты не исправлялись; следующий кандидат нуждается в новом
заранее закреплённом испытании. Новый Release не публиковался.
