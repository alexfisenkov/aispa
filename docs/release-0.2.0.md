# AISpa 0.2.0 — состав выпуска

Статус: **[стабильная 0.2.0 опубликована](https://github.com/alexfisenkov/aispa/releases/tag/v0.2.0)**
22.10.2026. Финальная CI, ресурсы, первая установка и обновление с откатом
подтверждены в [протоколе выпуска](validation-0.2.0.md).
Разрешение — «Приёмка решений 22.10.2026» в [решениях](decisions.md).
Это состав исторического выпуска; [текущий статус](status.md) ведётся отдельно.

## Экономный контроль

Контракт — [plan-lean-control.md](plan-lean-control.md). Причина — замеры
alpha: при одинаковой внешней приёмке AISpa тратила в 1,9–4× больше времени и
токенов, чем референс. Новые прогоны закрепляют `leanControl`:

- критик тяжёлой задачи сам закрывает её (PASS) и берёт обязанности отдельного
  приёмщика задачи; итоговая приёмка проекта по брифу остаётся;
- класс `standard` для обычного кода без критика задачи под общим обзором версии
  (работает только если план явно размечает им задачи; по умолчанию heavy);
- критик сначала читает изменения своей зоны; сценарии масштабируются глубиной;
- служебные шаги можно отправлять одной командой `batch`;
- слепая приёмка, чистый клон, журнал и реальный usage не меняются.

## Режимы проверки

Слова владельца — [brief-check-modes.md](brief-check-modes.md), контракт —
[spec-check-modes.md](spec-check-modes.md). Новый `init` требует `--check
fast|balanced|max`; навык обязан спросить человека отдельным вопросом.

- `fast` — без проверок по ходу; проблемы идут в итоговый отчёт, прогон
  завершается «с остатками», пропущенные проверки названы;
- `balanced` — класс каждой задачи выбирает система;
- `max` — все задачи heavy, сверка после каждой волны, одна дополнительная волна
  (`extra-wave`), затем остаток (`deferred`) уходит следующему прогону;
- смена режима — команда `check-mode`, слова человека хранятся дословно, смена
  видна в отчёте; автоподбора и предложений сменить режим нет;
- `routing.modelRule`: сильная модель — совет только для задач с безопасностью,
  ключами, доступом, платежами и личными данными.

Известное ограничение: при отложенной финальной задаче сдача невозможна.

## Установка и совместимость

Установщик и обновление работают как для 0.1.0: stable по умолчанию, preview до
записи, подтверждение и сохранённая копия при обновлении и откате. Пакет
0.1.0 → 0.2.0 обновляется тем же механизмом, что alpha.10 → 0.1.0.

Закреплённые прогоны 0.1.0 и alpha не мигрируют: активный прогон продолжается
своим runtime. Завершённую историю 0.1.0 (accepted, delivered_with_remaining,
cancelled) новая версия читает только для read-only handoff. Новая политика
включается новым `init`. Глобальная установка не меняется автоматически.

## Что не измерено

Модельный замер экономии не проводился: «в разы дешевле» у `fast` — подпись
выбора, а не результат измерения. Новых полных модельных прогонов и повторов
референса нет по решению владельца. Инженерные проверки и номер версии не
подтверждают пользовательские сценарии, работу каждой модели и машины учеников.
Прежние отчёты alpha и 0.1.0 не переписаны.
