# Autopilot vs obra/superpowers and mattpocock/skills

> **Status as of 2026-08-17, after the audit.** Waves 1 and 2 are fully applied (fixes 1–16),
> wave 3 partially (28–32 and part of 34). Net effect on the startup context: compression saved
> −5.2 KB, new rules added +4.7 KB, net result **−506 bytes (−0.3 %)**.
> The promised 13–18 % was not reached: it cannot be had without touching `3-spec.md`,
> `1-manifest.md` and `9-memory.md` (43 KB, not read line by line during the audit).
> Remaining from level 3: fixes 17–27.

Audit of 17 August 2026. A comparison against two reference frameworks plus a review of
our own instructions along six axes: execution accuracy, token spend, skill pack size,
dashboard reliability, quality loop, value for the developer.

Method: five parallel subagents (two on the references, three auditing by axis); every
key finding was re-checked by hand against the source. References were cloned on the
audit date: superpowers v6.3.0 (2026-08-12), mattpocock/skills — current main.

## 0. The three frameworks in numbers

| | **Autopilot** | **superpowers** | **mattpocock/skills** |
|---|---|---|---|
| Skills | 1 (18 subfiles) | 14 | 35 |
| Median SKILL.md | 18 KB (entry point) | 6.9 KB | 3.6 KB |
| Maximum | 28.7 KB (`5-subagents`) | 32.3 KB (`SDD`) | 12 KB (`ask-matt`) |
| Total text | 270 KB (+79 KB HTML) | 139 KB | 154 KB |
| Always paid | 253 tok. (`description`) | ~780 tok. (bootstrap via hook) | 0 (user-invoked) / descriptions |
| Startup context | **≈ 45,500 tok.** | ≈ 15–20K (SDD path) | ≈ 3–5K per skill |
| Orchestration | phase-based, declarative | `REQUIRED SUB-SKILL:` chain | the human |
| Observability | dashboard + `state.js` | markdown ledger | none |
| Framework self-tests | `tools/measure-run.py` | `tests/` + private evals | none |

Three different bets. mattpocock dropped process on purpose: "they take away your
control and make bugs in the process hard to resolve" — the orchestrator there is the human, the skills
are small and composable. superpowers builds discipline without observability: the agent
works for two hours, the user sees one line of narration. Autopilot is the only one
that tries to take a non-technical user from words to a working product in a single
conversation, and the price of that bet is the heaviest startup context of the three.

## 1. Instruction-following accuracy and result quality

The loop splits in two, and the halves are unevenly built.

**Traceability — 9/10.** A user requirement cannot disappear: a manifest of
verbatim quotes, four gates, blind acceptance against the brief with the spec withheld,
the Manifest axis in review, `placeholder` instead of an invented fact. Neither superpowers nor
mattpocock has anything comparable — there the requirement lives in the spec, and the spec is
a retelling, i.e. exactly the artifact whose blindness G2/G4 exist to catch.

**Evidence — 4/10.** Whether what was built actually works rests almost entirely
on the agents' self-reports.

| Gap | Where | What happens in practice |
|---|---|---|
| No red test | [`prompts/executor.md:12`](../skills/autopilot/prompts/executor.md#L12) | "Order: one test — implementation" is a writing order, not red-green. Test and code in a single edit satisfy the rule |
| No root cause | [`5-repair.md:30`](../skills/autopilot/phases/5-repair.md#L30) | "Fix it so it passes. Touch nothing else" — an open invitation to treat the symptom |
| Editing the test instead of the code is not forbidden | same place | Weakening an assertion is a literal execution of the repair request |
| No floor on test count | [`5-subagents.md:185`](../skills/autopilot/phases/5-subagents.md#L185) | `tail -30` of a suite where "0 tests, exit 0" reads as green |
| Self-review at T0 | [`6-review.md:32`](../skills/autopilot/phases/6-review.md#L32) | "all three axes yourself, inline" — the author reviews their own code, and T0 "is real and it is common" |
| Weakest review on task 01 | [`6-review.md:33`](../skills/autopilot/phases/6-review.md#L33) | Scaffold, schema and shared primitives get an inline review with no check of test assertions |
| The blocking criterion never arrives | [`craft-review.md:57`](../skills/autopilot/prompts/craft-review.md#L57) | The list of four always-blocking categories lives in [`6-review.md:131`](../skills/autopilot/phases/6-review.md#L131), which the reviewer never sees. This is exactly the defect the framework itself calls the main one: "A rule that lives only in this file does not exist" |
| Contradiction at the last gate | [`8-final.md:51`](../skills/autopilot/phases/8-final.md#L51) vs [`:74`](../skills/autopilot/phases/8-final.md#L74) | "Report it, and fix it if it is small" versus "Never fix one yourself" twenty lines later — and versus rule 5 |

For comparison, superpowers closes this with iron laws: "NO PRODUCTION CODE WITHOUT
A FAILING TEST FIRST. Write code before the test? Delete it. Start over", "Verify RED —
MANDATORY. Never skip", "NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST", "If you haven't
run the verification command in this message, you cannot claim it passes".

**Axis 1 verdict: the loop catches a lost requirement far more reliably than unfinished
work declared finished.**

## 2. Token and time spend

### Startup context — 164 KB / ≈ 45,500 tokens before the first line of code

Eleven files are always read: `SKILL.md` (4,850), `0-modes` (2,900), `0-preflight`
(2,380), `0-instruments` (2,970), `0-memory` (1,235), `1-manifest` (3,050), `2-briefing`
(5,900), `3-spec` (5,730), `4-plan` (4,050), `7-instruments` (4,730), `5-subagents` (7,730).

A full T2 run (6 tasks, `semi`, no `polish`): **≈ 71,300 tokens** in the
orchestrator's context, which is never refreshed, plus ≈ 22,300 in subagents.

**The key number is not 71k but 71k × number of turns.** The context is re-read on every
turn; at ~120 turns that is ≈ 8.5M input tokens for the skill text alone. It is cached —
but this is the floor no run goes below.

### What is already done right

- **`dashboard-template.html` (22,430 tokens) never enters the context** — it is
  copied with `cp`, with an explicit ban on reading it. This is the framework's main optimization,
  and it is done.
- **Progressive disclosure by phase** — the rule "the unit of loading is a file, not a
  section" is right and is followed.
- **Splitting `0-/7-instruments` and `0-/9-memory`** — the right idea: don't haul
  38K characters into a non-refreshing context for questions that arrive four
  phases later.
- **Subagent material kept out of the orchestrator's context** (`executor.md`,
  `craft-review.md` are passed by path) — the same decision as superpowers:
  "Hand artifacts over as files".
- **Executor context ceiling measured in tool calls** — a measured quantity
  (50 calls ≈ 120K, 1,900 tokens per call), with the arithmetic "doubling the ceiling
  doubles the bill". Neither reference has this.
- **`tools/measure-run.py`** — the run is measurable. superpowers keeps its evals
  in a private repo and they "are not part of CI today"; mattpocock has no metrics at all.

### Where we overpay

**Verbatim duplicates across files** — about 5 KB:

| Repeat | Where |
|---|---|
| "page loads `state.js`… every ten seconds" | `0-instruments:10` ≡ `7-instruments:12` |
| The "truth / human view" split | `0-instruments:7-8` ≡ `7-instruments:9-10` |
| "Never put a secret value in here" | `0-instruments:68` ≡ `7-instruments:97` |
| Return contract, 8 lines | `5-subagents:125-133` ≡ `executor.md:67-75` |
| "No more than 25 lines, no code…" | `5-subagents:135` ≡ `executor.md:77` |
| Memory markers block + brownfield | `0-memory:32,61` ≡ `9-memory:20,28,30` |
| Re-review scoped to the fix | `6-review:143-145` ≡ `5-repair:38` |
| "13 repairs across nine tickets, ~40 %" | `6-review:139` ≡ `5-repair:11` |
| "don't open `.autopilot/`" + rationale | `5-subagents:65`, `8-final:19`, `3-spec:202` |

The `0-/7-` and `0-/9-` pairs are a direct consequence of the split: both halves are read in the same
run, so part of the gain is eaten back.

**Sections that don't pay for their size:**

| Section | Bytes | Why |
|---|---:|---|
| `7-instruments` "What the dashboard shows" + progress bar + estimate | ~4,100 | The template computes all of it; the agent only writes `state.js` and may not touch the HTML |
| `SKILL.md` "Reading this skill" | ~1,900 | The rule is enforced by the phase table below it |
| `0-modes` "Why four and not three" + "Why this is a third dial" | ~1,400 | A design defense for a human reader, not an instruction to the agent |
| `SKILL.md` "The words the user sees" — rationale | ~1,100 | The table is enough |
| `rationalizations.md` | 16,941 | ~15 lines repeat verbatim the five rules of `SKILL.md:167-171` and the red flags inside the file itself; read up to three times per run |

Plus twelve spot compressions (the `data:`-URI forensics, the ceiling arithmetic
392 M/161 M, "The reason is arithmetic, not taste", two paragraphs in `2-briefing` about the
same thing) — another ≈ 3,300 tokens.

**Realistic compression ceiling: 13–18 % of startup (6–8K tokens) without losing a single
rule.** This is not "tighten the prose" — it is striking rationales addressed to a human
reading the README from files the agent reads in action.

### Compaction risk

| | ~Tokens |
|---|---:|
| System + tools | 12,000 |
| Framework text (11 files) | 45,500 |
| Brief + manifest | 3,500 |
| `spec.md` — written by the orchestrator, so it sits whole in its context | 15,000–25,000 |
| Tasks + `interfaces.md` | 3,500 |
| **Before the first task** | **≈ 80–90K** |
| By phase 8 | ≈ 120K |

T2 fits a 200K window with ~40 % to spare. **T3 and any run with `polish` compact
at least once**, usually between phases 5 and 8 — the framework admits this itself
(`SKILL.md:31`). `deep` moves the compaction point to the middle of the build.

**Four load-bearing mechanisms live only in context and die on compaction:**

| What is lost | Cost |
|---|---|
| The path to the skill directory (`<skill-dir>` is a placeholder, defined nowhere) | `executor.md` and `craft-review.md` stop reaching subagents — silent degradation of code quality |
| Handles of live reviewers | A new reviewer for every task; cross-task findings vanish |
| The text of the blocking finding at repair-request time | The repair is wasted, the `repairs` counter is already spent |
| Deferred findings at tier T0 | `concerns` exists only inside the task object ([`7-instruments.md:64`](../skills/autopilot/phases/7-instruments.md#L64)); with `tickets: []` there is nowhere to put them, and phase 8 triage becomes theater |

The `state.js` skeleton is done right — but these four holes land exactly on the mechanisms
the framework treats as load-bearing. **Four fields costing ~65 tokens in total close
all four.**

## 3. Skill pack size

270 KB of text plus 79 KB of HTML that never enters the context. Of the 270 KB:

- **Mandatory core** — ~164 KB (the 11 startup files). Compressible by 13–18 %.
- **Conditional** — `6-review`, `9-memory` (×2), `5-repair`, `8-final`, `rationalizations`,
  `polish`. Another ~26K tokens per run.
- **Subagent material** — `executor.md`, `craft-review.md`. Compact and well
  written; leave them alone, except for the additions from section 6.

**Little is superfluous, but much is over-explained.** The framework is written in the genre of
"every rule carries its own argument" — that makes it persuasive to a human and
expensive for an agent. mattpocock states exactly this test: *"Hunt no-ops sentence by
sentence: an instruction the model already obeys by default pays load to say nothing.
The test — does it change behaviour versus the default? … When a sentence fails, delete
the whole sentence rather than trim words from it."* Not all of our paragraphs pass this test:
"Read what is already here; assume nothing", "When in doubt, serialise"
(duplicates "Same files → serialise" one line above), "Order matters — the user reads the
top", "Refactoring belongs here, not inside the red-green loop".

**What is missing at negligible cost:**

1. `skillDir` in `state.js` — **~15 tokens, the most valuable fix of the audit.**
2. Top-level `concerns: []` — ~10 tokens.
3. `repairFindings: []` — the finding text on disk, ~20 tokens.
4. `reviewers: {manifestSpec, craft}` — handles of live reviewers, ~20 tokens.
5. An "after compaction" block in `SKILL.md`, ~120 tokens: "Lost the thread — re-read
   `state.js`, `manifest.md`, `interfaces.md`, the current phase file. Nothing else".
   Otherwise the agent re-reads `5-subagents.md` (7,730 tokens) instead of three state files.

## 4. Dashboard — 6/10

Architecture at 8–9, launch procedure at 4–5.

**What is done well and will survive any change.** One truth (`state.js`), one view,
zero build step. The template is self-contained — logos as `data:base64`, icons as inline SVG,
the only subresource is `<script src="state.js">`. Auto-refresh is done not via reload
and not via meta-refresh but by re-loading `state.js?t=…` every 10 s — a deliberate workaround
for panes that block navigation, and it was **measured, not assumed**. A broken write is
safe: `onerror`/`onload` lead to a single `next()`, the old state stays on screen.
Re-render only when the stamp changes. `spanMs` returns `null` instead of `NaN`. An explainer
screen instead of a blank one. For a skill this is rare maturity.

**Four high-probability failures, all silent:**

| # | Problem | Root |
|---|---|---|
| **H1** | `cp <skill-dir>/phases/dashboard-template.html` — the placeholder appears in the skill **exactly once** and is defined nowhere. The install path varies (`~/.claude/skills/`, plugin, project `.claude/skills/`). `cp` fails → no dashboard for the whole run | [`0-instruments.md:17`](../skills/autopilot/phases/0-instruments.md#L17) |
| **H2** | No verification at all — not of `cp`, not of server liveness, not of rendering. And the rule "A failure is not an error… Do not retry" effectively forbids it | [`0-instruments.md:107`](../skills/autopilot/phases/0-instruments.md#L107) |
| **H3** | The server dies silently: the free port is taken via bind→close (TOCTOU), stderr goes to `/dev/null`, `serve.pid` is written unconditionally → dead PID, the pane points at nothing | [`0-instruments.md:85-87`](../skills/autopilot/phases/0-instruments.md#L85) |
| **H4** | Targeted Edit on non-unique anchors: `"status": "pending"` occurs 7 times in `stages`, and `updatedAt`/`startedAt`/`stages[0].startedAt` are the same string at creation time. No instruction anywhere on "what to do if the Edit didn't match" | [`0-instruments.md:130`](../skills/autopilot/phases/0-instruments.md#L130) |

Plus two internal contradictions: [`0-preflight.md:108`](../skills/autopilot/phases/0-preflight.md#L108)
("on resume, assume the tab is open") versus `0-instruments.md:106`; and the write
savings in [`5-subagents.md:194`](../skills/autopilot/phases/5-subagents.md#L194) ("The user
cannot see the difference — the screen follows either way") versus the `startedAt` rule
in `0-instruments.md:133` — a batched `startedAt` gives a frozen timer, exactly what
is forbidden.

And one template defect that turns a one-off failure into a permanent one: **an exception in
`render()` kills polling forever** (`applyState()` calls `render()` without try/catch,
`pollState()` after it never runs, and `lastStamp` has already moved — a corrected
`state.js` will not re-render even manually). In the pane navigation is blocked, so the user cannot
reload the page.

**Six fixes — about 15 lines of text and 2 lines of JS — raise the mechanism to 8–9
without changing the architecture.**

## 5. Quality loop — 6.5/10

**What is done strongly and the references lack:**

- **Three review axes with a no-merge rule** (Manifest / Spec / Craft). mattpocock has two
  (Standards/Spec) with the same rule "Do not merge or rerank findings"; superpowers has
  a single Critical/Important/Minor rubric. The Manifest axis is ours, and it "does not exist in
  ordinary code review".
- **The reviewer outlives the task.** Cross-task findings ("ticket 05 quietly contradicts
  ticket 02") are invisible to any per-ticket reviewer. Neither reference has this.
- **The question "could the executor have known?"** as a way to assign a finding to an axis — a precise
  and cheap classifier.
- **`interfaces.md`** as the shared contract of eight independent contexts. In superpowers the
  equivalent lives in the dispatch prompt — a file is better.
- **Three "subagent" smells** (*Reinvention*, *Silent narrowing*, *Invented fact*) —
  absent from Fowler and from the references, and they describe exactly what breaks
  in parallel work.
- **Hard ceilings**: `repairs`, `retries`, `handoffs` — two each, an honest stop
  when exhausted. No infinite loop by construction.
- **Separating unfinished work from failure** (same context versus a fresh one) with a precise
  rationale: "a cold reader repairs the symptom and breaks the reason".
- **Blind acceptance G4** with an explicit ban on opening `.autopilot/` — and the understanding that
  "not sending the file" no longer equals "hiding it" once the directory lives in the repository.

**What is missing:**

- **Adversarial checking of findings.** No attempt to refute, no second opinion on a
  `clean` verdict, no protocol when reviewers disagree.
- **The reviewer's right to run code.** [`craft-review.md:7`](../skills/autopilot/prompts/craft-review.md#L7)
  forbids even opening a neighboring file — there is physically no way to check the central thesis
  "a green run is evidence only if the tests could have been red"; only reading remains.
  superpowers has Mutation Check for this.
- **A security axis.** No injection, no authorization, no input validation — even though
  the framework builds bots and forms with secrets.
- **Build checks.** The only one is incidental, in the memory agent: "A command that fails
  does not go in" ([`9-memory.md:106`](../skills/autopilot/phases/9-memory.md#L106)).
  A failed `npm run build` quietly stays out of the docs instead of
  stopping the run.
- **Running the product before phase 8.** Fifteen tasks can close on a green
  suite, and the first launch happens at the very end.
- **A route for `DONE_WITH_CONCERNS`.** The status is in the contract; there is no handler in the
  "After each ticket" list.

**Pressure on the reviewer points downward with no counterweight.** "Nothing to block — write
`нет` (none), it is a normal and frequent answer" + "A reviewer that does not know this hedges
upward" — while the cost of a missed finding is never stated to it anywhere.

## 6. Value for the developer

Yes, substantial — and it sits somewhere other than in either reference.

**What Autopilot gives that neither of them does:**

1. **A non-technical user reaches a result.** mattpocock needs a human
   orchestrator who drives the `grill → spec → tickets → implement → review` chain
   by hand and clears context between tickets. superpowers needs an understanding of which skill
   to call when. Autopilot is the only one that works from a dictated brief.
2. **Observability.** In superpowers this is an openly acknowledged gap: during a two-hour
   autonomous run the user sees almost nothing, the controller's decisions arrive as one dump
   at the end. A dashboard with live timers is a real advantage, not decoration.
3. **A requirement cannot disappear.** Manifest + four gates + blind acceptance —
   the only protection among the three frameworks against "a requirement that stopped
   existing somewhere around the third rewrite".
4. **Secrets as a cross-cutting rule**, with redaction on input, before anything is written to a file. Neither
   reference has anything like it.
5. **One Russian term per stage.** «Сборка» (build) — the whole run, «таск» (task) — the unit of work.
   A UX decision nobody else has, and it is the right one.
6. **Three independent dials** (mode / depth / polish) with an honest account of why there are
   three and not one.
7. **Measurability.** `tools/measure-run.py` computes the real cost of a run from the logs.

**What it costs:** the most expensive startup of the three (45.5K tokens versus ~15–20K
for superpowers), guaranteed compaction at T3, and an evidence loop weaker than
superpowers', even though the traceability loop is stronger than both.

**Final scores by axis:**

| Axis | Autopilot | superpowers | mattpocock |
|---|---|---|---|
| Requirement traceability | **9** | 5 | 6 |
| Evidence of results | 4 | **9** | 7 |
| Context economy | 6 | 7 | **9** |

## 7. Do not touch

What must stay as is through any changes.

1. **The manifest of verbatim quotes and the four gates.** The core of the value. G2 and G4 as "the same
   question at both ends of the flight" — a precise construction.
2. **Rule 5** — the orchestrator does not write code. Matches superpowers ("Never fix
   findings yourself in the controller session — your context stays clean for
   coordination, and controller fixes skip review"), and our rationale is better.
3. **Progressive disclosure by phase** and the rule "the unit of loading is a file".
4. **The ban on reading `dashboard-template.html` into context.**
5. **The executor context ceiling in tool calls + a five-line handoff**,
   of which three (`РЕШЕНИЯ` (decisions), `ТУПИКИ` (dead ends), `ДАЛЬШЕ` (next)) are the only thing not in the code.
6. **The living reviewer** and three axes with the no-merge rule.
7. **Passing material to subagents by path, not by pasting.**
8. **The three "subagent" smells** in `craft-review.md`.
9. **Secrets, `interfaces.md`, the user glossary, modes/depth/polish.**
10. **The dashboard architecture**: one state, one view, re-loading a subresource,
    zero external dependencies.

## 9. One observation about genre

superpowers measures its wording: the ban "don't restate the brief" produced 4.4 restatements
of the spec — **worse than no instruction at all** (3.6); a positive recipe produced 3.0 with zero
variance. Hence the rule "Match the Form to the Failure": prohibitions work against
discipline failures and backfire on output-form failures. And the metric: "Variance is a metric.
Five different interpretations across five reps means the wording isn't binding".

Our wording is not measured — it is argued. An argument persuades the human
reading the file; it does not always change the agent's behavior, and there is currently no way to tell which
paragraph actually works. `tools/measure-run.py` counts money and contexts — but not
rule compliance. The strongest investment on the horizon after fixes 1–8: **five runs
of one brief, recording where an instruction failed, and rewriting exactly those
phrasings.** Then section 8 of the next audit will rest on measurement rather than
on reading.
