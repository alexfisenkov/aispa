## 22.10.2026 — режимы проверки (ветка `work/lean-control`, не выпущено)

Слова владельца — [бриф](brief-check-modes.md), контракт —
[спецификация](spec-check-modes.md). Новый init принимает `--check
fast|balanced|max` (обязателен, как `--mode`); навык обязан спросить человека
отдельным вопросом и передать ответ явно. Сделано:

- `check_modes.py`: режим, история смен, класс задач по режиму (`fast` / план /
  `heavy` с `plannedTier`), глубина сценариев (fast — main+error, max — все восемь).
- Команда `check-mode <режим> --file`: слова человека хранятся дословно отдельной
  записью, бриф и фиксация не затрагиваются; `pending`, запущенные без сдачи и
  `blocked` без начатой проверки задачи получают новую попытку.
- Класс `fast`: без test-intent/RED, критиков, сверки волн и отдельного
  `integration-review`; остаются handoff, чистый клон, blind.
- `max`: все задачи heavy, сверка после каждой волны; `extra-wave <id>` (одна на
  задачу), затем `deferred` в остатки; зависимые задачи строятся без отложенной
  (`deferredDependencies`); пометка на панели.
- `routing.modelRule`: дешёвая модель по умолчанию, сильная — только для задач
  с путями безопасности, ключей, секретов, сертификатов, доступа, платежей и
  личных данных; высокий риск и ремонт её не включают; совет, не выбор.
- Инструкции навыка (SKILL, phases 01/03/04/05, references, prompts) описывают режимы.
  Известное ограничение: при отложенной финальной задаче сдача невозможна.

Проверки на macOS (Python 3.14), выполнены оркестратором: полный набор 784
теста, OK, 20 пропусков для других ОС; Node 43/43; `git diff --check` PASS.

## 22.10.2026 — экономный контроль (ветка `work/lean-control`, не выпущено)

Причина — замеры: при одинаковой внешней приёмке AISpa тратила в 1,9–4×
больше времени и токенов, чем референс; код писался на 6,6% входа повтора
Pulsefold, критик одной задачи и отдельный приёмщик занимали 31%, координатор
37%. Новый init закрепляет `policy.leanControl`:

- `reviewPolicy: lean` — PASS критика закрывает heavy-задачу
  (`critic_acceptance`); критик проверяет критерии замыкания, ограничения,
  `trace` и `inheritedProofs`. Отдельного приёмщика задачи нет. Ремонт и
  второй критик — как в adaptive; `drift` несовместим с PASS.
- Класс `standard` — обычный код без критика задачи под обязательным общим
  обзором версии. Нельзя: высокий риск, зависимость других задач (кроме финальной),
  чувствительные зоны.
  `submit` отклоняет изменения вне зон и в чувствительных путях; повышение до
  heavy — через `promote-task`.
- Пакет критика lean: `zoneChanges` и порядок чтения «сначала изменения»,
  полные брифы и spec — по необходимости.
- Сценарии в lean по глубине: strict 2, balanced 4, deep 8 измерений.
- `batch --file` — до 25 служебных команд одним вызовом, остановка на ошибке.

Закреплённые adaptive/legacy прогоны не меняются. Сквозной CLI-сценарий
обновлён под lean (два участника задачи вместо трёх). Модельный замер
экономии не проводился. [План](plan-lean-control.md), отличия от
предложенного владельцу — там же.

Проверки на macOS (Python 3.14): полный набор 708 тестов, OK, 20 пропусков
для других ОС; Node 40/40; `git diff --check` PASS. Критика: critic-logic
(1 BLOCK — финальный критик не читал код standard; исправлено: у финала
`zoneChanges` = весь diff), critic-code (1 BLOCK — порядок `inheritedProofs`
ломал доказательство; 7 WARN/NOTE; второй круг — закрыты, найденная
Windows-регрессия регистра путей исправлена), critic-skeptic (полнота и
честность описания; исправлены `decisions.md` и раздел отличий). CI трёх ОС
не запускалась: одна финальная CI — перед слиянием.

## 21.10.2026 — кандидат стабильной 0.1.0, два класса задач

По прямому решению владельца новый init включает light/heavy. Неуказанный
класс остаётся heavy; light допускает только обоснованные низкорисковые
правки точных безопасных файлов. Проверка и worker-report завершают light
как `verified_completion`, без отдельной критики и приёмки этой задачи.
Heavy сохраняет адаптивные один-два круга и отдельного приёмщика. Повышение
класса сохраняет историю; reset/replan/переименование не снимают ограничения.

У финальной light добавлен отдельный независимый обзор всей версии до
handoff/clean clone. Для финальной heavy общий обзор остаётся частью её
критики. Пять направлений, полный diff и отдельная итоговая приёмка по брифу
сохраняются. Панель различает класс и подтверждённое выполнение задачи;
ни отсутствие критика light, ни completed не означают принятия проекта.

Версия кандидата — 0.1.0. Первый установщик по умолчанию выбирает stable
SemVer вместе с GitHub `prerelease=false`; явный опубликованный prerelease
по `--tag` поддерживается. Alpha.10 добавлена в read-only handoff завершённой
истории; активные журналы и закреплённые runtime не мигрируют.

Адресно проверены 17 тестов хранилища, 12 первой установки и 26 обновления/
упаковки. Изолированные проверки охватывают alpha.10 → 0.1.0 → rollback,
байты и режимы файлов, неизменность runtime, stable preview/apply и
воспроизводимую упаковку. GitHub-транспорт в этих тестах синтетический.
Полный набор, независимая проверка кандидата, финальная матрица CI и live
Release ещё ожидают фиксации в [validation-0.1.0.md](validation-0.1.0.md).

## 21.10.2026 — условный второй критик и исправления приёмки

Новый `init` закрепляет адаптивную политику: первый PASS ведёт к отдельному
приёмщику; WARN/BLOCK/FAIL требуют ремонта и второго свежего критика.
Назначение второго критика до действительного ремонта запрещено. Старые
закреплённые прогоны сохраняют два обязательных круга.

Авторство фаз связывается с реальным участником и неизменным отчётом.
Координатор может вести подготовительные фазы; независимые проверяющие
сохраняются. Для одной задачи и одной волны полная финальная независимая
приёмка может подтвердить последнюю волну без дублирующего согласования.

Заранее зарегистрированные сроки исполнения отделены от свойств продукта.
Будущая передача результата не получает ложный PASS и остаётся видимым
обязательством. Тип события и срок сверяются с двумя исходными независимыми
разборами; история не меняется при переносе в новый прогон. Отказы ввода,
вывода, хранения, протокола и зависимостей включены в тестовый контракт
с адресными источниками. Заполненная матрица не заменяет выполнение тестов.

Дашборд показывает пропущенный второй круг и оставшиеся сроки. Обновлены
фазовые инструкции, контракты, подсказки ролей и регрессионные проверки.
Финально локально: 629 Python-тестов (609 PASS / 20 OS-specific SKIP),
Node 37/37, пример 15/15. Второй круг критики кода — PASS. Результаты новой
модельной батареи приведены ниже. [CI всех шести jobs](https://github.com/alexfisenkov/aispa/actions/runs/39548762214)
для `7b39b9e` прошла; Release не создаётся.
