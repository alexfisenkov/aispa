# Оркестрация AISpa · 0.1.0-alpha.8

Координатор работает в нативной среде Codex, Claude Code или Cursor. Он
запускает агентов и передаёт им контекст. Python-движок проверяет переходы,
сохраняет роли, связи и доказательства; вызовов модельных провайдеров в нём нет.

## Постоянный проектный контекст

Init сначала инвентаризирует фактические имена документов, манифестов, точек
входа и каталогов. Чужая структура не заменяется шаблоном. Минимальный
AGENTS.md создаётся только при отсутствии; существующий текст сохраняется.
Codex получает ссылку и в существующем AGENTS.override.md, Claude Code —
в CLAUDE.md, Cursor — в принадлежащем AISpa `.cursor/rules/aispa.mdc`.
Конфликт чужого файла или изменённого управляемого блока обнаруживается явно.
Перед правкой существующих правил сохраняется backup.

Стабильный блок правил указывает в `.aispa/context/`:

| Файл | Назначение |
|---|---|
| INDEX.md | карта контекста и фактического проекта |
| brief.md | полные исходные слова с ссылками на неизменные источники |
| spec.md | текущая спецификация и ссылка на источник |
| plan.md | полный текущий план и статусы задач |
| decisions.md | решения агента и решения владельца по объёму |
| progress.md | этап, блокеры, следующие действия, участники и история попыток |
| memory.md | ограниченная краткая память с указателями на полные сведения |
| requirements.json | текущий реестр требований |
| project-study.md | записанное исследование и ссылки на собранные источники |
| idea.md | краткий разбор идеи и ссылка на полный исходный отчёт |
| knowledge.md | указатель на знания по готовому коду и адресные команды чтения |
| carryover.md | история предыдущих прогонов, решения и незакрытые обязательства |
| source-map.json | run, digest состояния и события, источники и хеши представлений |

Эти файлы производны. Канон — `.aispa/runs/<run>/events.jsonl` и неизменные
исходники. Refresh пишет только скрытые представления и не меняет хеш кода
из-за времени или статуса. Перезапись views не разрешает потерю канонических
данных. Чтение `.env` и навязывание прикладных каталогов в bootstrap не входят.

Перед spec и plan нового прогона агент выполняет discover, читает собранные
фрагменты и записывает discover --file. Отчёт охватывает архитектуру, данные,
точки входа, зависимости, команды, соглашения и риски. Каждое наблюдение имеет
ссылки с SHA-256; отсутствие сведений отмечается явно. Для файлов с другими
именами доступен повторяемый --include. Изменение выбранного источника или
появление нового подходящего источника требует обновить исследование перед
новым планом. Подробности и ограничения — [project-memory.md](project-memory.md).

## До разработки: идея и границы задач

Аналитик идеи работает до seal. Он рассматривает проблему, пользователя,
наблюдаемый результат, варианты решения и малый эксперимент; дополнительно
проверяет противоречия, первое действие, пустые состояния, сбои, данные,
доступы, рост и возвращение пользователя. В compact короче изложение, в deep
подробнее анализ; первые пять областей обязательны для обоих режимов.

Исходные слова сохраняются без переписывания. Отчёт idea связан с их SHA и
точными цитатами и отражает каждое действующее требование. Предположения
отделены от наблюдений и проверяются явно. Предложения функций не меняют scope:
выбранные дополнения сначала получают отдельное требование kind addition.
Содержимое решения переносится в спецификацию; ядро владельца не сокращается.

В auto аналитик выбирает решения сам; important/interview задают вопросы
только на этапе брифа. Новый разбор после изменения исходных слов не является
разрешением открыть дополнительное интервью посреди разработки. Свежая
структурная проверка не доказывает, что идея будет успешна у пользователей.

После покрытия спецификации координатор выполняет plan-check для черновика.
Связанные мелкие части одного результата можно объединить, самостоятельные
риски и понятные границы — сохранить с объяснением. Отчёт planReview содержит
исходный черновик, группы и причины сохранённого разделения. Проверяются
точные наборы требований, критериев, зон и внешние зависимости; риск не
понижается, исходные непустые riskReason сохраняются. Совпавшие тексты
критериев объединённых задач получают разные префиксы исходных ID и остаются
отдельными проверками; остальные тексты не меняются. Роли создаются для итоговых задач. Количество `4 × задачи` —
показатель устройства плана, не измеренные токены или общее число агентов.

Порядок и схемы — [product-development.md](../skills/aispa/references/product-development.md).

## Цикл задачи

1. Plan с актуальным разбором размера создаёт карточки четырёх ролей по каждой задаче; team может дополнить
   специализацию и проверки до первой критики.
2. Координатор получает пакет worker, делает start, создаёт нативного исполнителя
   и сразу записывает assign по реальным runtime/native-id/session.
3. Worker реализует задачу в своей зоне. Адресный verify фиксирует поведение и
   снимок входов задачи. Submit записывает полный отчёт исполнителя.
4. Новый critic1 независимо проверяет кандидат. При FAIL исполнитель исправляет
   замечания, снова проверяет код и сохраняет repair с SHA первого отчёта.
5. Новый critic2 работает всегда, в том числе после первого PASS. Он проверяет
   кандидата и разрешения всех блокирующих замечаний. Всего два раунда.
6. После второго PASS новый acceptor читает исходный бриф и проверяет результат
   по задаче, критериям предков и ограничениям. Только его complete завершает
   задачу. Trace привязывает результат к точным словам владельца.

Карточки — устойчивые определения ролей; нативный агент — отдельный экземпляр
на конкретную задачу/попытку. Его ID берётся из ответа инструмента среды.
Разные строки ID и поле independent не доказывают независимость сами по себе:
координатор отвечает за реальные отдельные контексты и честные наблюдения.

`context --kind task --task T01 --role <role> --write` сохраняет адресный пакет.
Он содержит роли, участников, попытку, expectedChecks, traceRequirements,
inheritedProofs, проверки и нужные исходники. Организатор передаёт пути,
а не постоянно перепечатывает весь журнал. Файл пакета ограничен 16 000 байт:
крупные разделы сохраняются полностью в отдельных артефактах со ссылками и
хешами. Критерии, ограничения и исходные слова не усекаются. Native ID не заменяет внутренний
receipt.actor, которым подписывается отчёт.

Каталог нужен для поиска, когда пути ещё неизвестны. Если zones/readZones
задачи и её зависимостей перечисляют точные существующие допустимые файлы,
пакет автоматически обходится без каталога. При широких зонах координатор
может передать уже выбранные файлы повторяемым `--source`: они проверяются
по тем же границам. Это не меняет basis, набор входов проверки и expectedChecks.
`documentRouting` объясняет выбранный режим; `documentWarnings` сохраняет
проблемы всех выбранных источников и зарегистрированных общих входов, даже
сверх 48 строк. Если пути ещё неизвестны, передаётся компактный каталог:
путь, статус, актуальное описание до 160 символов. Хеши и состояние заголовка
запрашиваются адресно через `documents --path … --detailed`.

Не читай полный каталог для уже известных путей. Большие обязательные
разделы передавай частями и проверяй отсутствие обрезки ответа инструмента;
файл на диске и текст, полученный моделью, — разные свидетельства доставки.

Карточки, назначения, смены исполнителей, сдачи, два отчёта критиков,
исправления и приёмка сохраняются в taskHistory и неизменных артефактах.
Пересборка карточек до критики требует новых назначений; после первого раунда
контракт заморожен. Изменение после второго PASS нельзя провести под старым basis.

Маршрутизация модели — рекомендация координатору. Только исполнитель явно
низкорисковой задачи с riskReason, без зависимых задач и без повторной попытки
может получить standard. Для остальных исполнителей, двух критиков и приёмщика
рекомендуется strong. Фактическую доступную модель выбирает среда с учётом
правил проекта; названия моделей движок не выдумывает. Отсутствие нужного
варианта не отменяет роли и не разрешает молчаливое понижение.

## Зависимости и свежесть

Zones определяет запись, readZones — дополнительные входы. В набор чтения
входят зависимости и общие файлы проекта. Если запись одной задачи пересекает
чтение/запись другой, нужна явная dependsOn. Разнесение по волнам без связи
не защищает происхождение доказательств и отклоняется.

Принятый потомок может законно изменить результат предка. Тогда его приёмщик
перепроверяет все критерии предка, сохраняет ссылки inheritedProofs и исходные
ограничения. Только свежая принятая цепочка позволяет опереться на исторический
результат. Независимый сосед или одно поле completed такого права не дают.

После волны требуются общая verify и независимая сверка полного брифа.
Последняя сверка должна оставаться актуальной перед входом в следующую волну.
Финальная приёмка всего проекта — отдельный этап; две критики задачи не
заменяют ни её, ни проверку реального пользовательского сценария.

## Чистая проверка перед сдачей

Новые init включают обязательную проверку чистого клона. После сохранения
изменений в Git clean-prepare создаёт отдельную копию точного HEAD; clean-verify
запускает выбранную реальную команду продукта в ней. Отчёт связан с commit,
деревом, снимком файлов и результатом процесса. Новый commit или изменение
контролируемых файлов делает свидетельство устаревшим.

Пакет context --kind blind содержит исходные брифы и адрес клона. Проверяющий
сначала записывает самостоятельные наблюдения о продукте. Только после этой
записи становится доступен пакет acceptance для сверки всех требований. Python не может удостоверить, что
модель действительно не читала предыдущие обсуждения: свежий контекст обязан
обеспечить координатор. Проверка в клоне не изолирует ОС или сеть.

## После приёмки: отдельный автор знаний

Между успешной acceptance и finish координатор создаёт нового свежего участника,
отличного от исполнителей, критиков и итогового приёмщика. Knowledge-assign
записывает реальную identity. Пакет context --kind knowledge передаёт снимок
кода, безопасные пути и фактические проверки с digest. Автор читает готовые
источники и сохраняет команды, ловушки, причины решений и термины; если
категория не дала полезного знания, указывает причину в uncertainties.

Knowledge-record сохраняет неизменную запись. Новый finish требует её
актуальности, но все прежние условия приёмки остаются обязательными.
Сохранение знаний не запускает ещё одного критика задачи и не расходует
дополнительный третий раунд: это самостоятельный этап после приёмки.

В следующем запуске знания читаются по path/kind и проверяются по SHA источников.
Полный архив не подгружается автоматически; пакет задачи содержит лишь короткие
релевантные подсказки. Исторический успех команды не считается нынешним PASS.
Blind-приёмщик знаний и чужих оценок не получает.

При новом init знания автоматически получают контрольный снимок рабочего
набора и ссылку на неизменный архив. В активном прогоне knowledge-compact
позволяет продолжить после 64 локальных отчётов, сохраняя исходную историю.
Рабочая часть снимка ограничена 128 записями и 512 KiB; один артефакт — 1 MiB.
Обычная выдача не обходит архив. Адресный запрос с --archive и --archive-depth
читает ограниченную глубину 1–64 (по умолчанию 4), а archive.unread явно
показывает оставшийся непрочитанный архив. Счётчик archivedRecordCount
отражает число отчётов автора, не уникальные знания. Старые редакции не
возвращаются взамен устаревших новых, прежний PASS текущим не становится.

## Блокировка и продолжение

FAIL второго критика или приёмщика закрывает попытку и блокирует задачу.
Координатор продолжает независимые задачи и сообщает остаток. Reset, replan,
новое имя задачи или незаписанный третий критик не являются обходом лимита.

После финального ответа владелец может прислать новые поправки. Они сохраняются
новым brief; new-attempt связывает новую попытку с точной цитатой нового
разрешения и предыдущей попыткой. Затем пересверяются бриф, спецификация,
coverage и план, создаются новые участники. Старое доказательство остаётся
в истории. Агент не открывает дополнительные вопросы в ходе разработки,
чтобы автоматически получить себе третий раунд.

Новый допустимый init прикрепляет неизменную историю предыдущего прогона.
Остатки видны сразу, но текущие требования, задачи и PASS автоматически не
наследуются. carry map связывает обязательство с новым требованием по новым
словам владельца; carry resolve требует свежих доказательств текущего прогона.
Необработанные остатки сохраняются в финальном результате. Точный порядок —
[project-memory.md](project-memory.md).

Команды и форматы: [process.md](../skills/aispa/references/process.md),
[contracts.md](../skills/aispa/references/contracts.md). Нативные прогоны всех
трёх сред остаются отдельным пунктом [испытаний](testing.md).
