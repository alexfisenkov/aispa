# Оркестрация AISpa · 0.1.0

Координатор работает в нативной среде Codex, Claude Code или Cursor. Он
запускает агентов и передаёт им контекст. Python-движок проверяет переходы,
сохраняет роли, связи и доказательства; вызовов модельных провайдеров в нём нет.
Новый init 0.1.0 закрепляет `taskTiers` вместе с `adaptiveCritique`
и прежними проверками источников, дизайна, usage, интеграции и намерения тестов.
Статус выпуска — [validation-0.1.0.md](validation-0.1.0.md).
Старый активный прогон остаётся на своём
закреплённом runtime и не получает новый контракт задним числом.

## Постоянный проектный контекст

Init сначала инвентаризирует фактические имена документов, манифестов, точек
входа и каталогов. Чужая структура не заменяется шаблоном. Минимальный
AGENTS.md создаётся только при отсутствии; существующий текст сохраняется.
Codex получает ссылку и в существующем AGENTS.override.md, Claude Code —
в CLAUDE.md, Cursor — в принадлежащем AISpa `.cursor/rules/aispa.mdc`.
Конфликт чужого файла или изменённого управляемого блока обнаруживается явно.
Перед правкой существующих правил сохраняется backup.

Стабильный блок правил указывает в `.aispa/context/`:

| Файл | Назначение |
|---|---|
| INDEX.md | карта контекста и фактического проекта |
| brief.md | полные исходные слова с ссылками на неизменные источники |
| spec.md | текущая спецификация и ссылка на источник |
| plan.md | полный текущий план и статусы задач |
| decisions.md | решения агента и решения владельца по объёму |
| progress.md | этап, блокеры, следующие действия, участники и история попыток |
| memory.md | ограниченная краткая память с указателями на полные сведения |
| requirements.json | текущий реестр требований |
| project-study.md | записанное исследование и ссылки на собранные источники |
| idea.md | краткий разбор идеи и ссылка на полный исходный отчёт |
| knowledge.md | указатель на знания по готовому коду и адресные команды чтения |
| carryover.md | история предыдущих прогонов, решения и незакрытые обязательства |
| source-map.json | run, digest состояния и события, источники и хеши представлений |

Эти файлы производны. Канон — `.aispa/runs/<run>/events.jsonl` и неизменные
исходники. Refresh пишет только скрытые представления и не меняет хеш кода
из-за времени или статуса. Перезапись views не разрешает потерю канонических
данных. Чтение `.env` и навязывание прикладных каталогов в bootstrap не входят.

Перед spec и plan нового прогона агент выполняет discover, читает собранные
фрагменты и записывает discover --file. Отчёт охватывает архитектуру, данные,
точки входа, зависимости, команды, соглашения и риски. Каждое наблюдение имеет
ссылки с SHA-256; отсутствие сведений отмечается явно. Для файлов с другими
именами доступен повторяемый --include. Изменение выбранного источника или
появление нового подходящего источника требует обновить исследование перед
новым планом. Подробности и ограничения — [project-memory.md](project-memory.md).

## До разработки: идея и границы задач

Аналитик идеи работает до seal. Он рассматривает проблему, пользователя,
наблюдаемый результат, варианты решения и малый эксперимент; дополнительно
проверяет противоречия, первое действие, пустые состояния, сбои, данные,
доступы, рост и возвращение пользователя. В compact короче изложение, в deep
подробнее анализ; первые пять областей обязательны для обоих режимов.

Исходные слова сохраняются без переписывания. Отчёт idea связан с их SHA и
точными цитатами и отражает каждое действующее требование. Предположения
отделены от наблюдений и проверяются явно. Предложения функций не меняют scope:
выбранные дополнения сначала получают отдельное требование kind addition.
Содержимое решения переносится в спецификацию; ядро владельца не сокращается.

В auto аналитик выбирает решения сам; important/interview задают вопросы
только на этапе брифа. Новый разбор после изменения исходных слов не является
разрешением открыть дополнительное интервью посреди разработки. Свежая
структурная проверка не доказывает, что идея будет успешна у пользователей.

Alpha.9 добавляет пять challenge: adoption без имеющихся пользователей,
value_cost с измеримой пользой и затратами, operations с оператором и
поставкой данных, lifecycle с повторным визитом и второй неделей, actors
с правами других участников. Наблюдение отделяют от гипотезы, выбранного
решения и проверки. При coverage проверяющий ищет в спецификации решение
вместе со способом его проверки. Полнота пяти строк не доказывает спрос.

После покрытия спецификации координатор выполняет plan-check для черновика.
Связанные мелкие части одного результата можно объединить, самостоятельные
риски и понятные границы — сохранить с объяснением. Отчёт planReview содержит
исходный черновик, группы и причины сохранённого разделения. Проверяются
точные наборы требований, критериев, зон и внешние зависимости; риск не
понижается, исходные непустые riskReason сохраняются. Совпавшие тексты
критериев объединённых задач получают разные префиксы исходных ID и остаются
отдельными проверками; остальные тексты не меняются. Роли создаются для итоговых
задач. `taskRoleSlots` оценивает одну базовую роль light и 3–4 роли heavy
с adaptive; legacy `two_rounds` сохраняет расчёт четырёх. Общий обзор проекта
и финальная приёмка учитываются отдельно. Это устройство одной попытки,
не предел нативных запусков: подготовка, замены исполнителей и новые разрешённые
попытки не включены. Фактическое число вызовов и токены подтверждает native usage.

Порядок и схемы — [product-development.md](../skills/aispa/references/product-development.md).

Новый planReview включает delivery: законченные пользовательские срезы с
демонстрацией по критерию задачи. Для изменения контрактов или данных он
фиксирует expand → migrate всех известных потребителей → contract, зависимости,
проверки совместимости и rollback. Код проверяет заданные связи, а полноту
списка потребителей координатор устанавливает исследованием проекта.

## Класс задачи и лёгкий маршрут

При новом `init` класс хранится в плане, карточке и истории попытки:
`tier: light|heavy`, `tierReason`, `changeKind`. Без явного выбора — heavy.
Само `risk=low` не отключает критиков. Для light нужны непустые riskReason и
tierReason, один из видов `documentation`, `formatting`, `presentation` и
от 1 до 12 точных безопасных файлов. Общая папка, glob, исполняемый файл,
ссылка или файл кода, правил, конфигурации, доступа и публичного контракта
не проходят этот маршрут. Допустимые пути и расширения задаёт `task_tiers.py`;
они не доказывают смысловую безопасность изменения, за неё отвечает координатор.

Light создаёт только карточку worker. Реальный исполнитель получает пакет,
проходит start/assign, сохраняет намерение проверки и выполняет адресный verify.
Успешный `submit` проверяет полный worker-report, свежесть источников,
доказательства критериев, границы изменения и входные зависимости. После
этого задача получает `completed` и `completionKind=verified_completion`.
Отдельные critic1/critic2/acceptor не назначаются, `complete` от выдуманного
приёмщика не требуется. В журнале нет фиктивного критического PASS.

Это подтверждённое выполнение задачи, а не приёмка проекта. Независимая сверка
волны, обзор всей версии, чистый клон и итоговый приёмщик по брифу сохраняются.
Light не может самостоятельно подтвердить устаревшее доказательство предка,
код которого она изменила; такой риск требует тяжёлого маршрута.

Новый риск фиксируется командой `promote-task T01 --reason "<причина>"`.
Она сохраняет прошлую light-попытку, создаёт heavy, снимает прежний proof и
возвращает задачу в pending для новых назначений и проверки. Понижение после
начала работы, укрупнение heavy в light, reset и новое имя не обходят историю.

## Цикл тяжёлой задачи

**Lean (новые прогоны с `leanControl`).** Карточки — worker, critic1 и
условный critic2. Критик проверяет и бывшие обязанности приёмщика: критерии
задач замыкания, ограничения, `trace` к точным цитатам владельца и
`inheritedProofs`. Его PASS запечатывает раунд как приёмку задачи
(`completionKind: critic_acceptance`, тот же отчёт и actor); шаги 6 и
`complete` ниже не выполняются. `drift` исключает PASS. Пакет критика
содержит `zoneChanges` и правило чтения «сначала изменения». Обычный код без
риска для других задач может идти классом standard без критика задачи — его
покрывает общий обзор версии. Описанная ниже последовательность действует для
закреплённых adaptive и legacy попыток.

**Режимы проверки (новые прогоны с `leanControl`).** Сколько проверять, выбирает
только человек: `init --check fast|balanced|max`, смена — его словами через
`check-mode --file`. `fast` — задачи класса `fast` без критиков, RED и сверок волн,
проблемы в итоговом отчёте; `balanced` — классы плана; `max` — все задачи heavy,
сверка после каждой волны, одна `extra-wave` после неудачи второго критика, затем
`deferred` в остатки, зависимые задачи строятся без отложенной
(`deferredDependencies`). Журнал, usage, handoff, чистый клон и blind остаются.
Решения — [бриф](brief-check-modes.md), контракт — [спецификация](spec-check-modes.md).

Новый `init` включает `adaptiveCritique`. Выбранный `reviewPolicy: adaptive`
закреплён в попытке и карточках. Существующая попытка не меняет политику при
переключении флага прогона. Старые попытки без поля `reviewPolicy` сохраняют
legacy `two_rounds`: второй критик обязателен после любого первого результата.

1. Для heavy plan с актуальным разбором размера создаёт карточки четырёх возможных ролей;
   team может дополнить специализацию и проверки до первой критики. Карточка
   critic2 не означает запуск агента.
2. Координатор получает пакет worker, делает start, создаёт нативного исполнителя
   и сразу записывает assign по реальным runtime/native-id/session.
3. Worker реализует задачу в своей зоне. Адресный verify фиксирует поведение и
   снимок входов задачи. Submit записывает полный отчёт исполнителя.
4. Новый critic1 независимо проверяет кандидат. В adaptive строгий PASS ведёт
   сразу к отдельному acceptor; critic2, ремонт и фиктивный второй PASS не создаются.
   При WARN/BLOCK/FAIL координатор читает `repair-plan T01` для basis и
   requiredFindingIds (blocking и warning), записывает диагноз и маршрут.
   Локальный дефект исправляет тот же worker; потерянный контекст или неверный
   подход — новый свежий сильный worker. Затем проверка и repair с SHA первого
   отчёта. Внешний блокер не маскируют ремонтом.
5. После ремонта новый critic2 проверяет кандидата и разрешения всех обязательных
   замечаний; unresolved исключает PASS. Максимум два раунда.
6. После PASS последнего обязательного критика новый acceptor читает исходный бриф и проверяет результат
   по задаче, критериям предков и ограничениям. Только его complete завершает
   задачу. Trace привязывает результат к точным словам владельца.

В adaptive каждый критик и приёмщик явно указывает `verdict: PASS|WARN|BLOCK|FAIL`.
PASS требует пройденных проверок, пустого unmapped, отсутствия обязательных и
нерешённых замечаний; у приёмщика trace должен быть aligned. Информационный
`note` может сопровождать PASS; требующее действия замечание получает severity
`warning` или `blocking`. В отчёте критика каждая непрошедшая проверка требует обязательного ID,
который проходит через repair-plan, addresses ремонта и resolutions critic2.
Неизвестный verdict и противоречивый PASS отклоняются без расходования раунда.

Карточки — устойчивые определения ролей; нативный агент — отдельный экземпляр
на конкретную задачу/попытку. Его ID берётся из ответа инструмента среды.
Разные строки ID и поле independent не доказывают независимость сами по себе:
координатор отвечает за реальные отдельные контексты и честные наблюдения.

`context --kind task --task T01 --role <role> --write` сохраняет адресный пакет.
Он содержит роли, участников, попытку, expectedChecks, traceRequirements,
inheritedProofs, проверки и нужные исходники. Организатор передаёт пути,
а не постоянно перепечатывает весь журнал. Файл пакета ограничен 16 000 байт:
крупные разделы сохраняются полностью в отдельных артефактах со ссылками и
хешами. Критерии, ограничения и исходные слова не усекаются. Native ID не заменяет внутренний
receipt.actor, которым подписывается отчёт.

`template worker|critic1|critic2|acceptor --task T01 --write` подготавливает
редактируемую форму после назначения роли. Из состояния берутся basis,
actor, полное множество checks, связи критиков/исправления, trace и метаданные
branchReview. Смысловые поля остаются незавершёнными, verdict равен null;
независимость проверяющий
подтверждает сам. Генерация формы не выполняет submit/review/complete и не
расходует круг критики. Настоящая запись повторяет все прежние guards.
Глобальный `--compact` перед командой сокращает обычный ответ записи/status:
полный JSON хранится в прогоне с адресом и SHA. Это не сокращает доказательства
и не меняет коды выхода. Команды чтения и ошибки guards остаются прежними.
Для light доступна только форма worker; обязательные проверки и доказательства
в ней сохраняются.

Каталог нужен для поиска, когда пути ещё неизвестны. Если zones/readZones
задачи и её зависимостей перечисляют точные существующие допустимые файлы,
пакет автоматически обходится без каталога. При широких зонах координатор
может передать уже выбранные файлы повторяемым `--source`: они проверяются
по тем же границам. Это не меняет basis, набор входов проверки и expectedChecks.
`documentRouting` объясняет выбранный режим; `documentWarnings` сохраняет
проблемы всех выбранных источников и зарегистрированных общих входов, даже
сверх 48 строк. Если пути ещё неизвестны, передаётся компактный каталог:
путь, статус, актуальное описание до 160 символов. Хеши и состояние заголовка
запрашиваются адресно через `documents --path … --detailed`.

Не читай полный каталог для уже известных путей. Большие обязательные
разделы передавай частями и проверяй отсутствие обрезки ответа инструмента;
файл на диске и текст, полученный моделью, — разные свидетельства доставки.

Карточки, назначения, смены исполнителей, сдачи, реально выполненные отчёты критиков,
исправления и приёмка сохраняются в taskHistory и неизменных артефактах.
Пересборка карточек до критики требует новых назначений; после первого раунда
контракт заморожен. Кандидат после PASS последнего обязательного критика не
меняется до приёмки. Новый basis или новая форма не дают дополнительный раунд.

Маршрутизация модели — рекомендация координатору. Только исполнитель явно
низкорисковой задачи с riskReason, без зависимых задач и без повторной попытки
может получить standard. Для остальных исполнителей, каждого критика и приёмщика
рекомендуется strong. Фактическую доступную модель выбирает среда с учётом
правил проекта; названия моделей движок не выдумывает. Отсутствие нужного
варианта не отменяет роли и не разрешает молчаливое понижение.

## Зависимости и свежесть

Zones определяет запись, readZones — дополнительные входы. В набор чтения
входят зависимости и общие файлы проекта. Если запись одной задачи пересекает
чтение/запись другой, нужна явная dependsOn. Разнесение по волнам без связи
не защищает происхождение доказательств и отклоняется.

Принятый heavy-потомок может законно изменить результат предка. Тогда его приёмщик
перепроверяет все критерии предка, сохраняет ссылки inheritedProofs и исходные
ограничения. Только свежая принятая цепочка позволяет опереться на исторический
результат. Light-потомок опирается только на актуальные прямые доказательства
зависимостей; самостоятельной переприёмки изменённого предка у него нет.
Независимый сосед или одно поле completed такого права не дают.

После волны требуются общая verify и независимая сверка полного брифа.
Последняя сверка должна оставаться актуальной перед входом в следующую волну.
Финальная приёмка всего проекта — отдельный этап; выполнение или критика задачи не
заменяют ни её, ни проверку реального пользовательского сценария.

После каждого фактически выполненного verify/clean-verify движок добавляет
запись `commands` с purpose, scope задачи/попытки, code/candidate, временем,
exit code и SHA вывода. Чтение по фильтру ограничено и не выдаёт сырые логи;
точная запись доступна по SHA. Неуспешная команда остаётся историей, но не
становится проверенной рекомендацией. Старый успех не даёт текущий PASS.

## Чистая проверка перед сдачей

Обычные README/архитектура/решения/словарь создаются вместе с задачами и входят
в проверки кандидата. Для последней волны порядок такой: проверяемое завершение
light и приёмка heavy → общий обзор всей версии → Git commit кода/документов →
свежий project verify с purpose check → `handoff --file …` → сверка последней
волны по всему брифу → чистый клон. Для heavy общий обзор уже входит в её
критический отчёт; отдельное повторное ревью ради этой строки не создаётся.
Лишняя общая verify после wave меняет basis даже без изменения кода и требует
повторного ревью волны; не запускай её без нового основания. Изменившиеся код
или свидетельства по-прежнему требуют повторения затронутых проверок.
Handoff проверяет
происхождение, SHA и структуру, но не удостоверяет качество или приватность
смысла текста. Исходный бриф не экспортируют в публичные документы.

Новые init включают обязательную проверку чистого клона. После handoff и
сохранения изменений в Git clean-prepare создаёт отдельную копию точного HEAD; clean-verify
запускает выбранную реальную команду продукта в ней. Отчёт связан с commit,
деревом, снимком файлов и результатом процесса. Новый commit или изменение
контролируемых файлов делает свидетельство устаревшим.

Пакет context --kind blind содержит исходные брифы и адрес клона. Проверяющий
сначала записывает самостоятельные наблюдения о продукте. Только после этой
записи становится доступен пакет acceptance для сверки всех требований. Python не может удостоверить, что
модель действительно не читала предыдущие обсуждения: свежий контекст обязан
обеспечить координатор. Проверка в клоне не изолирует ОС или сеть.

## После приёмки: отдельный автор знаний

Между успешной acceptance и finish координатор создаёт нового свежего участника,
отличного от исполнителей, критиков и итогового приёмщика. Knowledge-assign
записывает реальную identity. Пакет context --kind knowledge передаёт снимок
кода, безопасные пути и фактические проверки с digest. Автор читает готовые
источники и сохраняет команды, ловушки, причины решений и термины; если
категория не дала полезного знания, указывает причину в uncertainties.

Knowledge-record сохраняет неизменную запись. Новый finish требует её
актуальности, но все прежние условия приёмки остаются обязательными.
Сохранение знаний не запускает ещё одного критика задачи и не расходует
дополнительный третий раунд: это самостоятельный этап после приёмки.
После acceptance публичные документы не дописываются как часть приватной
записи знаний. Любой исторический успешный execution текущего прогона можно
цитировать как источник команды, включая прежний candidate; флаг
`currentAtCuration` не заменяет свежую общую проверку и acceptance.

В следующем запуске знания читаются по path/kind и проверяются по SHA источников.
Полный архив не подгружается автоматически; пакет задачи содержит лишь короткие
релевантные подсказки. Исторический успех команды не считается нынешним PASS.
Blind-приёмщик знаний и чужих оценок не получает.

При новом init знания автоматически получают контрольный снимок рабочего
набора и ссылку на неизменный архив. В активном прогоне knowledge-compact
позволяет продолжить после 64 локальных отчётов, сохраняя исходную историю.
Рабочая часть снимка ограничена 128 записями и 512 KiB; один артефакт — 1 MiB.
Обычная выдача не обходит архив. Адресный запрос с --archive и --archive-depth
читает ограниченную глубину 1–64 (по умолчанию 4), а archive.unread явно
показывает оставшийся непрочитанный архив. Счётчик archivedRecordCount
отражает число отчётов автора, не уникальные знания. Старые редакции не
возвращаются взамен устаревших новых, прежний PASS текущим не становится.

## Блокировка и продолжение

WARN/BLOCK/FAIL второго критика или приёмщика закрывает попытку и блокирует задачу.
Координатор продолжает независимые задачи и сообщает остаток. Reset, replan,
новое имя задачи или незаписанный третий критик не являются обходом лимита.

После финального ответа владелец может прислать новые поправки. Они сохраняются
новым brief; new-attempt связывает новую попытку с точной цитатой нового
разрешения и предыдущей попыткой. Затем пересверяются бриф, спецификация,
coverage и план, создаются новые участники. Старое доказательство остаётся
в истории. Агент не открывает дополнительные вопросы в ходе разработки,
чтобы автоматически получить себе третий раунд.

Новый допустимый init прикрепляет неизменную историю предыдущего прогона.
Остатки видны сразу, но текущие требования, задачи и PASS автоматически не
наследуются. carry map связывает обязательство с новым требованием по новым
словам владельца; carry resolve требует свежих доказательств текущего прогона.
Необработанные остатки сохраняются в финальном результате. Точный порядок —
[project-memory.md](project-memory.md).

## Сохранённые контрольные точки и общий обзор

До `seal` полный исходный бриф отдельно читают `brief-analyst` и свежий
`brief-reviewer`. Первый анализ не выдаётся второму до его собственной записи.
`brief-map` связывает каждый исходный фрагмент с требованием, контекстом или
явным расхождением; только согласованный полный отчёт пропускает `seal`.
После spec сценарии восьми измерений и контракт интерфейсов предшествуют
плану. Их цитаты и SHA устанавливают происхождение, не истинность продуктовой
гипотезы. У владельца остаётся право на конкретное новое решение по scope.

План содержит единственную финальную задачу, которая зависит от остальных и
читает всё дерево кода; readZones позволяет сохранить ограниченную write-зону.
Если она heavy, в каждом выполненном круге её критики проверяют полный diff
по поведению, интеграции, сопровождаемости, данным/безопасности и тестам.
Это обязательно и при единственном круге после первого PASS; отдельного
третьего круга нет.

Если финальная задача light, после актуального завершения всех задач нужен
отдельный свежий участник с ролью `integration-reviewer`. Координатор
регистрирует его реальные native ID/session через `participant`; участник
отличается от исполнителей и итогового приёмщика. `integration-review --actor
<actor>` возвращает весь diff, basis, code и незаполненную форму пяти направлений.
После независимой проверки `integration-review --actor <actor> --file <report>`
сохраняет неизменный PASS/FAIL. Нужны полный список изменений и существующие
доказательства по всем направлениям. Изменение кандидата или повреждение
свидетельств снимает актуальность PASS. FAIL не заменяется новым вердиктом
того же кандидата; для изменённого кандидата нужен новый свежий проверяющий.
Без текущего PASS не проходят handoff и clean clone. Это один общий обзор
проекта, а не критик и приёмщик каждой light-задачи.

Для изменённого поведения `testIntent` связывает
реальные новые тесты и их RED до первой сдачи с текущим GREEN.
Для docs/config/integration и ранее существующего поведения нужен предметный
отказ по каждому критерию, а не молчаливая отмена теста.

При `errorBoundaryChecks` намерение содержит `failureChecks` — привязанную
к исходникам матрицу применимых отказов и причин неприменимости. Критики и
приёмщик проверяют матрицу, сохранность данных и реальные отрицательные
сценарии. Пути и SHA устанавливают источник намерения, но не подтверждают
выполнение. Порядок — [отказные проверки](../skills/aispa/references/failure-checks.md).

Роли общих фаз получают отдельные записи `participant` из нативных ответов
среды. Task роли остаются в `assign`, автор знаний — в `knowledge-assign`.
Повтор одного native ID под новой session не создаёт независимости.
`usage-import` учитывает исходные native вызовы, `usage` отдельно показывает
измеренные токены и пробелы по ролям/участникам; полноту стоимости нельзя
достроить из размера пакетов или поздней догадки.

Дашборд имеет отдельное ожидание владельца, свернутую историю и исторический
экспорт. Архив не опрашивает сервер и не показывает прежнюю приёмку как
текущую. Оборванную последнюю запись журнала чинят только через просмотр
кандидата, побайтную резервную копию и CAS; прогон остаётся paused до свежей
проверки и независимого `recovery-reviewer`. Неизвестные внешние эффекты
оставляют его заблокированным для продолжения.

Команды и форматы: [process.md](../skills/aispa/references/process.md),
[contracts.md](../skills/aispa/references/contracts.md). Нативные прогоны всех
трёх сред остаются отдельным пунктом [испытаний](testing.md).
