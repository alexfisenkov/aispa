# Адресный мост старта повторной финальной T06 для закреплённого 0.4.0

Этот мост продолжает выбранный owner-attempt runtime с digest
`e7018aecae8a61f9b766b676013e01a2b2ef6f23090007b1691b2f433bf77211`.
Он переносит только проверенный путь старта ранее начатой финальной heavy T06,
для которой владелец открыл новую попытку. Исторически принятые зависимости
проверяются по их полным сохранённым цепочкам; старое доказательство не
объявляется актуальным. Свежие реализация, критика и итоговая приёмка T06
остаются обязательными. Бриф, policy, прежние попытки и runtime не переписываются.

Инструмент — `skills/aispa/tools/repair_final_retry.py` из этой рабочей копии.
Порядок: read-only `inspect`; `prepare` с точными SHA текущего журнала и
просмотренного разрешения; независимое чтение diff и manifest; `apply` с
точными SHA manifest/журнала/разрешения, цитатой и `--confirm`; повторный
`inspect` и проверка выбранного CLI. Подготовленная копия сама по себе не
выбрана. Команды используют конкретные абсолютные пути и SHA из текущего
осмотра:

```sh
python3 -B skills/aispa/tools/repair_final_retry.py --root PROJECT inspect
python3 -B skills/aispa/tools/repair_final_retry.py --root PROJECT prepare \
  --candidate-package skills/aispa --expected-journal-sha256 JOURNAL_SHA \
  --expected-approval-sha256 APPROVAL_SHA --owner-quote OWNER_QUOTE
python3 -B skills/aispa/tools/repair_final_retry.py --root PROJECT apply \
  --manifest-file MANIFEST_PATH --expected-manifest-sha256 MANIFEST_SHA \
  --expected-journal-sha256 JOURNAL_SHA --approval-file OWNER_DECISION_FILE \
  --expected-approval-sha256 APPROVAL_SHA --owner-quote OWNER_QUOTE --confirm
```

Разрешение владельца в рабочем проекте:
`.aispa/inbox/owner-new-attempts-20261026-source.md`, SHA-256
`4390459892eb5d64118acc845dfa9b0675d6e0efa36b852f613821e4d36ad47c`,
точная цитата «Да давай». Оно разрешает свежие попытки T01/T06 с сохранением
истории, но не удостоверяет личность автора локального файла и не заменяет
приёмку. T01 уже принята; у T06 открыта попытка, заблокирован её старт после
изменения исходника теста T05.

При подготовке копируются все 98 файлов выбранного runtime; меняется только
`tools/aispa_core/workflow.py`. Из текущего source-файла с SHA-256
`1626a3976025d1051fc3cf08830eaa881f857acb960e80fb8f0c98df68501a0f`
(`runtime_final_retry_repair.SOURCE_HASHES`, перезакреплён в сборке 0.5.0)
извлекаются два адресных guard-вызова и методы проверки финального повтора.
Остальные отличия рабочей ветки в закреплённую копию не попадают.
Исторический source `0d7606ce9273b1f79933489aad98818d11badd705461320051c6a0ae833dfe03`
остаётся в `HISTORICAL_SOURCE_HASHES`: manifest, уже подготовленный по нему,
проверку сохраняет. Исторический owner-attempt manifest сохраняет свой source
SHA. Его maintenance-проверка допускает известные source SHA `workflow.py`:
первоначальный `7c53f2f7ca48ccc80962d8123144dd9dd47344ac65142f4950c998982c3b678d`,
исторический `0d7606ce…` и текущий `1626a3976025…` (таблица —
[runtime-owner-attempt-repair.md](runtime-owner-attempt-repair.md)). Более
поздний source допустим для повторения прежнего моста только потому, что его
точный выходной workflow SHA остаётся прежним
`0ac372f9676893419a954a98bd61be3cdf7fd570cf14be7154416ce2111e3392`.
SHA-256 изменённого файла: старый
`0ac372f9676893419a954a98bd61be3cdf7fd570cf14be7154416ce2111e3392`,
новый `a271ee1701bfa2440f13e417dad9e22895300e564089f168d7219c3dca5b6d1c`.
Расчётный digest новой полной копии:
`8cfaf0b935f1fa095b692537549768f4c6052389e03d5b502b75d5f1158df9fa`.
Он получен read-only splice точного прежнего pin и локального source;
живой выбор этим расчётом не подтверждён.

Мост принимает только точную цепочку двух zone repairs и owner-attempt repair,
сверяет их manifest, receipt, сохранённые префиксы и прежние digest. Manifest
нового ремонта перечисляет весь inventory, один разрешённый diff и parent
owner-manifest. `apply` использует CAS журнала и не заменяет занятые пути.
Свидетельства публикуются после `fsync`. После начала append они сохраняются
при ошибке: полный append перечитывается, частичный передаётся штатному
восстановлению, неопределённый не повторяется автоматически. Только отдельное
событие `runtime-repaired:final-owner-retry-0.4.0` меняет указатель runtime и
добавляет новую квитанцию.

Первый кодовый обзор нашёл две границы. **FRB1:** потоковый осмотр теперь на
каждой строке между ремонтами проверяет выбранную zone-квитанцию и ожидаемый
digest, включая период перед owner repair; временное изменение с последующим
возвратом обнаруживается. **FRB2:** файл разрешения до чтения проходит
`lstat`, затем открывается без перехода по ссылке и без блокировки на FIFO,
повторно проверяется через `fstat` и читается физически не более чем
131 073 байт. Максимальный допустимый файл — 131 072 байта. Такой же
ограниченный осмотр повторяется под замком до записи свидетельств. SHA и
точная цитата по-прежнему обязательны.

Повторный кодовый обзор остался **WARN**: до первого zone repair сканер ещё
допускал временную смену исходного `runtimeDigest` с возвратом. Отдельный
синтетический тест воспроизвёл этот дефект до правки и прошёл после проверки
`zone.OFFICIAL_DIGEST` на каждой строке до первого ремонта. Тестовый
CLI-сценарий теперь закрепляет официальный digest уже в начальном событии.
Третьего независимого обзора моста не было; локальный тест не переименовывает
второй WARN в PASS. Весь изменённый код подлежит свежей проверке в T06.

Изолированные тесты строят короткий журнал из официального 0.4.0 и трёх
исторических repairs в временном проекте. Они проверяют один изменённый файл,
сохранение префикса/старых bytes, CAS, SHA, разрешение, ссылки и коллизии,
ограниченное удержание строк при двух размерах журнала, ошибки до append и
полный/частичный append. Отдельный тест запускает `start T06` через настоящий
CLI выбранной тестовой копии: прежний CLI отказывает из-за устаревшей
зависимости, новый открывает свежую попытку. Для достижения этой границы
тестовый проект создаёт синтетические валидные coverage/plan gates; это не
доказательство таких gates в рабочем прогоне.

Локальные проверки и их результат фиксируются отдельно от выбора в рабочем
прогоне. Четыре адресных теста FRB1/FRB2 сначала воспроизвели оба дефекта
(4/4 ожидаемых отказа до исправления). После исправления и двух дополнительных
проверок повторного чтения под замком и замены файла на FIFO адресный набор
старого и нового bridge до последнего уточнения прошёл 38/38; `py_compile`
изменённых Python-файлов и `git diff --check` прошли. Исходный RED
зафиксировал отсутствие нового bridge-модуля до реализации; отдельный сбой
синтетической подготовки обнаружил устаревшую привязку source SHA прежнего
owner bridge и был исправлен точным whitelist выше. Ни тот, ни другой RED
не доказывает предметное поведение T06. После последнего guard отдельно
проверены воспроизводящий тест и запуск CLI на временном проекте. Основной
агент затем выполнил общий адресный набор: 46/46 PASS за 59,182 с, исходники
во время проверки не менялись. SHA вывода:
`ec9589926067515ca04c54efce9838832e2eea135ebb3cf256629d4922de62cd`.
Это локальная проверка кода, не формальная приёмка T06.

Read-only `inspect` рабочего прогона до усиления FRB1/FRB2
`20261025T164520-scale-reliability-515f5192` прошёл при SHA журнала
`10705b2ac2c024392f28c88e88cde26f75c0441e926068d0c0610f76b2b9a223`;
SHA до и после совпал. Выбран прежний digest `e7018aec…`, новый мост не
выбран; сканер проверил цепочку трёх старых ремонтов и 851 локальный артефакт.
Шесть внешних ссылок не перепроверялись. Усиленный scanner на рабочем
прогоне ещё не запускался. Это совместимость прежнего осмотра с рабочей
историей, а не разрешение выполнить `apply`.

Windows, полный набор тестов, CI, канонические `prepare/apply`, фактическая
T06 и пользовательская приёмка этим документом не подтверждаются.
