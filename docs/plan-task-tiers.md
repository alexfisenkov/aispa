# Следующий этап: лёгкие и тяжёлые задачи

Идея владельца, добавленная во время оптимизации служебного обмена: различать
лёгкие и тяжёлые задачи; лёгкие могут завершаться без отдельных критиков.
Статус: QUEUED_AFTER_LEAN_REPEAT. Реализация начинается после текущего
единственного повторного замера, чтобы не менять его условия.

## Предварительные границы

Лёгкая задача — ограниченная, обратимая правка с однозначным результатом,
который можно проверить короткой детерминированной проверкой или перечитыванием.
Примеры для рассмотрения: опечатка, форматирование, небольшая локальная
правка оформления. Число строк само по себе не определяет риск.

Изменения бизнес-логики, данных, доступов, интеграций, публичных контрактов,
зависимостей или поведения системы требуют стандартного маршрута. При
неопределённости выбирать тяжёлую задачу. Окончательные критерии закрепить
по анализу действующих контрактов, не вводить неявный обход проверок.

Для лёгких задач исследовать маршрут без отдельных critic1/critic2 и без
лишних передач между агентами; оставить проверку факта изменения и общую
финальную сверку продукта с брифом. У тяжёлых сохраняется действующий
маршрут: первый PASS → отдельный приёмщик; non-PASS → ремонт → новый
второй критик → приёмщик. Нельзя переименованием в «лёгкую» обойти уже
полученный non-PASS или списать исходное обязательное требование.

Класс и основание фиксируются до исполнения; новые риски повышают класс.
Нужны совместимость старых закреплённых прогонов, понятное отображение
фактического маршрута в панели и тесты ошибочной классификации/обходов.

## Порядок

1. Завершить текущую оптимизацию, узкую проверку WARN-ветки и один повтор
   AISpa без нового запуска референса.
2. Уточнить границы по действующим контрактам AISpa. В закреплённых инструкциях
   референса 2.1.0 уже подтверждён выбор точечного ревью: оно нужно для фундамента,
   рисков и незавершённых требований, остальные задачи проходят общую проверку
   ветки в конце. Это факт об инструкции, не доказательство исполнения каждого
   её запуска; исходники и формулировки в AISpa не копируются.
3. Определить узкие критерии лёгкой задачи, формат решения и границы допуска.
4. Реализовать отдельно от текущего измеряемого кандидата, проверить
   детерминированно и провести адресную критику по фактическим замечаниям.
5. Записать код и свидетельства в GitHub. Дополнительную полную батарею
   модельных прогонов автоматически не запускать.
