# Испытания и ограничения AISpa

Текущий выпуск, подтверждённые результаты и остатки — [status.md](status.md).
Последняя доставка и адресная CI — [validation-0.3.5.md](validation-0.3.5.md).
Исторические числа ниже сохраняют свои версии и не заменяют проверки новой версии.
По решению владельца новые полные модельные прогоны для 0.1.0 не проводятся;
экономия токенов light/heavy не измеряется и не объявляется.

## Автоматические проверки

Из корня: `python3 -B -m unittest discover -s tests -v`.
Нужны Python 3.11+ и Git; внешних Python-зависимостей нет.
В PowerShell: `python -X utf8 -B -m unittest discover -s tests -v`
или `py -3 -X utf8 -B -m unittest discover -s tests -v`.
Для Windows нужен Git for Windows; подробности — [windows.md](windows.md).
Поведение JS: `node --test tests/dashboard.test.cjs`, Node 18+, без npm-пакетов.
Тесты выполняют доставляемый inline-скрипт в небольшой модели DOM; реальный
браузер дополнительно проверяется при изменении вёрстки.

| Уровень | Что проверяется |
|---|---|
| Хранилище | история, блокировка записи, изменение исходника, повреждённая запись, пути, снимок кода |
| Контракт | цитаты, обязательное ядро, полнота плана, зависимости, зоны, доказательства, устаревание |
| Сдача | отказ без проверок; отказ при непроверенном ядре; отдельный итог с второстепенным остатком |
| CLI | настоящий subprocess, коды ошибок, весь синтетический путь до finish, сохранённая версия движка |
| HTTP | локальная выдача HTML и JSON из текущего прогона |
| Время | старт/завершение, пауза, повторный запуск, диапазон оценки по волнам, отсутствие выдуманного ETA |
| Интерфейс | фильтры, безопасный текст, деморежим, ошибки связи, живые часы и правильные поля остатков |
| Класс задачи | heavy по умолчанию, явные безопасные границы light, адресная проверка и worker-report → verified completion без task critics/acceptor; повышение класса и запрет обхода истории |
| Команда heavy | закреплённая политика, первый PASS → отдельный acceptor, WARN/BLOCK/FAIL → repair → свежий critic2, максимум два раунда; legacy сохраняет два обязательных раунда |
| Общий обзор | финальная heavy включает полный diff в критику; финальная light требует отдельный integration-review с пятью направлениями и независимым участником до handoff/clone |
| Verdict и замечания | явный verdict, отказ без расходования раунда при неизвестном verdict/противоречивом PASS, warning и blocking ID в диагнозе, ремонте и resolutions |
| Зависимости | явный write/read порядок, транзитивные входы, наследование исторических доказательств через принятого потомка |
| Проектный контекст | сохранение правил, backup, три адаптера, override, конфликт Cursor, symlink/traversal, точные источники, ограниченная память и свежесть |
| Изучение проекта | содержимое и SHA-256 источников, семь областей, неподтверждённые команды, явные include, секреты, Git ignore, ссылки, лимиты, пропуски, свежесть и повторное использование |
| Память между прогонами | проверяемая передача, неизменные исходники, остатки, новые слова владельца, map/resolve, запрет наследования текущего PASS |
| Пакеты и usage | основной файл до 16 000 байт, полные разделы по ссылкам, обязательные критерии, advisory routing и реальные отдельные метрики |
| Чистый клон | точный commit, отдельные файлы, очищенное окружение, Unicode-пути/вывод, реальная offline-установка wheel в локальную venv, timeout, остановка дочерних процессов, целостность и устаревание свидетельства |
| ОС | POSIX process group и нативный Windows Job Object; Windows SystemRoot, Scripts/python.exe, режимы Git, пути с пробелами и кириллицей |
| Обновление | SemVer и Release-only выбор, offline, проверка manifest/ZIP, кандидат, согласие, CAS, backup/rollback, защита Git/runtime |
| Первая установка | default stable SemVer вместе с GitHub prerelease=false; explicit published tag, честный флаг в preview, отказ без stable, подтверждённый apply в свободную папку |
| Ресурсы Release | воспроизводимый пакет из точного commit, состав, версия, LICENSE и manifest без публикации |

В тестах независимый проверяющий **моделируется синтетическим отчётом**.
Это подтверждает обработку отчёта, а не независимость или качество модели.

`test_adaptive_review.py` проверяет обе ветки нового маршрута, старые попытки
без поля политики, отдельного приёмщика, зависимости, полное интеграционное
ревью каждого выполненного круга, устаревший basis и запрет третьего раунда/
reset. Отображение пропущенного critic2 не создаёт фиктивного actor или PASS.
Оценка 3–4 базовых ролей не ограничивает число реальных запусков с подготовкой,
заменами и новыми разрешёнными попытками. Снижение стоимости проверяется
отдельным нативным прогоном, а не числом ролей.

`test_task_tiers.py` проверяет настоящий verify/submit лёгкой задачи, отсутствие
task critics/acceptor, свежесть proof, запрет опасных путей и исполняемых файлов,
сохранение истории при promote и запрет понижения/обхода через новый ID.
`test_light_integration_review.py` проверяет независимый общий обзор, полноту
diff/пяти направлений, сохранённый FAIL, свежего участника для нового кандидата,
изменение кода и доказательств. Отдельная итоговая приёмка по брифу сохраняется.
Эти тесты используют синтетические отчёты участников, а не новые модельные прогоны.

`test_store.py`, `test_install.py` и `test_updates.py` дополнительно покрывают
alpha.10 → 0.1.0 → rollback, read-only handoff только завершённой истории,
сохранение байтов/режимов и pinned runtime, стабильную первую установку и
воспроизводимую упаковку. Подменённый транспорт не доказывает публикацию.

При `errorBoundaryChecks` проверяются исходники и полнота матрицы `failureChecks`;
сценарии отказов, сохранность данных и реальные команды дополнительно проверяют
критики heavy-задач и общий независимый обзор с итоговой приёмкой проекта.
Для light нет отдельных task critics/acceptor. Матрица фиксирует намерение
и не доказывает выполнение.
Порядок — [отказные проверки](../skills/aispa/references/failure-checks.md).

## Открытые пользовательские и модельные проверки

Следующая матрица — историческая программа испытаний маршрута 0.1.0.
Она не объявлена выполненной целиком и не является очередью автоматических
запусков. Для новых прогонов применяются [lean](plan-lean-control.md) и
[режимы проверки](spec-check-modes.md); старые runtime сохраняют свой контракт.
Конкретные оставшиеся проверки и запрет новых полных прогонов без отдельной
команды владельца — в [текущем статусе](status.md#что-ещё-не-подтверждено).

Для Codex, Claude Code и Cursor отдельно:

1. Открытие установленного пакета: первым идёт update-check, затем выбор режима.
   Проверить отсутствие Release, offline и продолжение без установки.
2. Прогоны auto, important, interview: вопросы только на этапе брифа.
3. Малый реальный проект с 5–10 требованиями и хотя бы двумя волнами.
4. Одно забытое требование вне реестра: независимый проверяющий должен найти его.
5. Новая команда владельца в середине задачи: прежняя приёмка устаревает,
   старые слова остаются, изменения проходят новый план и сверку.
6. Потеря контекста и возобновление без повторного интервью.
7. Отсутствующий доступ: независимые задачи продолжаются, интеграция остаётся блокером.
8. Рабочее ядро с остатком: честный итог, остаток присутствует в следующем запуске.
9. Перезапуск для пересмотра решения агента: сохранённая история и новые доказательства.
10. Авторский дашборд: широкое и мобильное окно, длинные требования, ошибки сервера,
    устаревшее состояние, отсутствие противоречия между заголовком и данными.

11. Нативные отдельные worker и, у heavy, critic1, acceptor и при необходимости critic2:
    записанные ID совпадают с ответами инструментов; свежесть подтверждается средой.
    У light проверить verified completion без фиктивных ролей и отдельный
    общий integration-review при финальной light.
12. В heavy adaptive первый строгий PASS идёт сразу отдельному acceptor без critic2
    и без фиктивного второго отчёта. WARN/BLOCK/FAIL требует адресной перепроверки,
    ремонта всех обязательных ID и свежего critic2. Отдельно проверить legacy
    `two_rounds`: после первого PASS второй критик остаётся обязательным.
13. WARN/BLOCK/FAIL второго критика или приёмщика блокирует попытку без третьего
    раунда; неизвестный verdict и ложный PASS не расходуют раунд. После финального ответа
    новые слова владельца открывают новую историю через new-attempt.
14. Приёмщик находит несоответствие исходной цитате и нарушение критерия предка,
    даже если исполнитель и критики считают результат достаточным.
15. Возобновление по context/memory и полным источникам; пользовательские
    AGENTS/CLAUDE/Cursor правила сохраняются, hand-edit конфликт не затирается.
16. Для каждого нового Release, включая stable: проверка настоящих ресурсов GitHub,
    просмотр подготовленного кандидата, явная установка и откат в тестовой
    копии. Публикация ресурсов сама по себе не подтверждает этот сценарий.
17. Аварийный останов между переименованиями: сохранность соседнего backup,
    восстановление по receipt и отсутствие перезаписи активного runtime.

18. Изучение существующего проекта: выводы подтверждены реальными файлами,
    неизвестное отмечено, нужные нестандартные модули добавлены через include.
    Изменение источника и новый подходящий файл требуют обновить исследование.
19. Второй и третий прогон: остаток виден без нового интервью, но не включён
    в текущий scope без решения; map сохраняет смысл и критерии, resolve требует
    новых доказательств. Переименование не обходит исчерпанную попытку.
20. Большой проект: адресный пакет сохраняет все критерии и ссылки; исполнитель
    действительно читает вынесенные разделы. Зафиксировать реальные usage,
    если среда их возвращает, без выдуманной оценки экономии.
21. Проверяющий в новом контексте запускает продукт из чистого клона сначала
    по исходному брифу, затем сверяет наблюдения с реестром. Проверить отсутствие
    локальных секретов, недостающую зависимость и изменение исходного commit.

## Сохраняющиеся ограничения

- Смысловое соответствие брифу и достоверность наблюдений не вычисляются по
  хешу. Нужны реальный сценарий и отдельный проверяющий. Поле `independent`
  фиксирует заявление процесса, не удостоверяет личность модели. Native ID и
  session записываются координатором; криптографической аутентификации агента нет.
- Цитата решения владельца проверяется на присутствие в сохранённом брифе.
  Кто произнёс слова и действительно ли это разрешение, проверяет агент по диалогу.
- Проверка кода учитывает Git-файлы и неигнорируемые новые файлы. Игнорируемые
  зависимости, внешние сервисы и данные проверяются отдельными сценариями.
  Для символической ссылки фиксируется сама ссылка, не внешнее содержимое.
- Git submodules и tracked symlinks в clean-clone пока отклоняются явно.
  Нативная Windows для 0.3.5 подтверждена адресной матрицей её выпуска;
  новый commit требует своей Windows CI. Сетевые файловые системы, WSL и все
  пользовательские конфигурации Windows этим результатом не покрываются.
- После аварийного завершения может остаться `.aispa/.lock`: сверить PID и
  отсутствие активного процесса, затем убрать только этот lock-файл.
  Повреждённый журнал нельзя автоматически заменить новым.
- Обновления доверяют опубликованным ресурсам фиксированного GitHub-репозитория
  и их хешам, без независимой подписи издателя. CAS защищает от изменения
  пакета после подготовки, но не обещает recovery после SIGKILL; порядок
  восстановления — [updates.md](updates.md).
- Автоматической миграции между версиями движка пока нет. Продолжать можно
  сохранённой копией runtime, новый прогон использует новую установленную версию.
- История локальных прогонов не публикуется автоматически. Архивирование и
  перенос приватных брифов между машинами требуют отдельной процедуры.
- В alpha.2 внедрён дизайн владельца; проверены узкие размеры 320/390 px и
  чтение тестового прогона движка. Проверка на реальных телефонах остаётся
  отдельным шагом. Внешние шрифты Google Fonts имеют системный fallback.
- Сбор discovery ограничен безопасными источниками, их фрагментами и явными
  include; он не читает весь репозиторий. Oversized-источники учитываются по
  размеру/mtime. Хеш доказывает происхождение, а не истинность архитектурного
  вывода. Фильтр секретов распознаёт известные признаки и не гарантирует полноту.
- Чистый клон — отдельная проверяемая копия с очищенным окружением, без sandbox
  ОС и без изоляции сети. Запуск по первоначальному брифу до чтения реестра
  обеспечивается координатором; поле отчёта не доказывает слепоту модели.
- Размер пакетов измеряется в байтах. Usage необязателен и охватывает только
  реально записанные вызовы. Снижение расходов на полном проекте не подтверждено.
  Новый сравнительный прогон light/heavy в этой итерации не проводится.
- Время — интервал между отмеченными событиями. Простой без явно записанной
  паузы включён в него. ETA — эвристика по завершённым задачам; точность на
  длительных реальных модельных прогонах ещё не измерена.

## Дополнение alpha.6

Для alpha.6 отдельно проверяются YAML-заголовки и каталог: точный SHA, изменение
текста той же длины, устаревшее описание, повторное чтение, проверку ожидаемого SHA перед
записью заголовка, сохранность брифа/чужого frontmatter/readonly-файла, Unicode
и CRLF, файловые ссылки, ограничение размера, пропуски и отсутствие каталога
в blind-пакете. Реальную экономию токенов и соблюдение регистрации произвольных
внешних чтений моделью подтверждает отдельный модельный прогон.

Для inline-заголовка проверки SHA не атомарны относительно внешнего редактора.
При одновременной записи использовать каталог; поддержка транзакционного
редактирования внешних файлов в текущий механизм не входит.

## Условие выпуска 1.0

Успешные автоматические проверки, подтверждённые модельные прогоны выбранных
сред, пользовательские испытания и отдельная команда владельца на выпуск.
Публичный main и стабильная 0.1.0 не заменяют отдельное решение о 1.0.
