# Спецификация: режимы проверки

Источник — [бриф владельца](brief-check-modes.md). Ветка `work/lean-control`,
выпуск вместе с [экономным контролем](plan-lean-control.md).

## Ручки и состояние

- `init --check fast|balanced|max` (параметр обязателен, как `--mode`: навык
  спрашивает человека и передаёт ответ явно; см. SKILL). Значение — `state.checkMode`, история
  смен — `state.checkModeHistory`. Доступно только с `leanControl`.
- Выбор при старте показывается вместе с режимом вопросов, двумя отдельными
  вопросами: «Быстро — в разы дешевле, без проверок по ходу, проблемы — в
  итоговом отчёте»; «Сбалансированно — система сама решает по каждой задаче»;
  «Максимум — долго и дорого: каждая задача доводится до PASS».
- Смена: `check-mode <режим> --file <файл со словами человека>`. Слова хранятся
  дословно отдельной записью (`mode-requests/`, любые непустые, без секретов,
  повтор допустим); бриф, `scope_basis`, `plan_basis` и фиксация не меняются,
  прогон не останавливается. Запись видна на панели и в итоговом отчёте
  (`checkModeHistory`, `remaining.checkModeChanges`). Система смену не предлагает.
  Уже завершённые задачи и попытки с начатой критикой не меняются. Задачи `pending`,
  `blocked` без начатой критики и сдачи и запущенные без сдачи получают новую попытку
  (`authorization.kind: check-mode`, `request` — ссылка на запись слов) с классом
  нового режима; запущенной нужен новый исполнитель (идентичность участника не
  переиспользуется). Прогон, закреплённый без `leanControl`, смену не поддерживает:
  навык говорит об этом человеку в ответе на просьбу, без встречных вопросов, и
  продолжает в прежнем режиме.
- Термины: `balanced` в `--depth` (глубина сценариев, человек её не выбирает) и
  «Сбалансированно» (режим проверки) — разные ручки. Если человек назвал режим
  вопросов или проверки в самом вызове, второй раз вопрос не задаётся.

## Класс задачи по режиму

| Режим | Класс всех задач | Маршрут |
|---|---|---|
| fast | `fast` | worker → проверка → submit → verified completion |
| balanced | объявленный в плане light/standard/heavy | как в экономном контроле |
| max | `heavy` | worker → критик → (ремонт → critic2) → доп. волна |

Объявленный в плане класс сохраняется как `plannedTier` и возвращается при
переходе в balanced.

## Быстро (`fast`)

- Класс `fast` — завершение исполнителем, изменения только в зонах задачи;
  ограничение чувствительных путей не действует (решение агента).
- Не требуются: тестовый контракт и RED, критики задачи, сверка брифа после
  волны (волна, открытая в fast, помечается и не проверяется), отдельный
  `integration-review` при сдаче, если текущий режим fast.
- Сценарии: только `main` и `error`.
- Остаётся: адресная проверка задачи (тесты исполнителя), handoff, чистый
  клон, слепая приёмка. Проблемы приёмки не чинятся: прогон завершается `finish`
  со статусом `delivered_with_remaining`; итоговый отчёт перечисляет проблемы и
  прямо называет пропущенные режимом проверки (критики задач, RED, сверки волн,
  обзор версии) — `remaining.skippedChecks`.

## Максимум (`max`)

- Все задачи heavy, сценарии deep (все восемь с контрпримерами), сверка брифа
  после каждой волны; итоговая волна не переиспользуется (`finalWaveReuse`
  отключён).
- Два круга критики. После non-PASS второго критика — одна дополнительная
  волна: `extra-wave T01` создаёт новую попытку задачи (полную, с до двух кругов
  критики; `authorization.kind: extra-wave`) без новых слов владельца — одна
  дополнительная волна в `max` — исключение из правила `new-attempt`,
  разрешённое решением владельца 22.10.
  Это не волна плана: отдельной сверки брифа после неё нет. Вторая запрещена.
- Если и она не прошла — задача остаётся `blocked` с пометкой `deferred`
  (отложена после дополнительной волны; выводится из истории: последняя попытка
  `terminal` и в истории есть `extra-wave`; не путать с `defer` — переносом
  требования владельцем по цитате) и уходит в остатки следующего прогона.
  Потомки стартуют после того, как дополнительная волна не прошла: их старт и
  приёмка исключают отложенную зависимость (`deferredDependencies` в попытке),
  критерии отложенной задачи не входят в их проверку, пометка видна на панели и в
  отчёте. Частичный код отложенной остаётся в дереве, на него можно опираться;
  итоговая слепая приёмка оценивает её критерии как невыполненные — они уходят в
  остатки, прогон завершается «с остатками»; финальная задача проверяет весь
  diff, включая код отложенной.

## Модели (все режимы новых прогонов)

Рекомендация `routing` — дешёвая модель для всех ролей; сильная — только для
задач с путями безопасности, ключей, секретов, сертификатов, доступа, платежей и
личных данных (`task_tiers.strong_model_path`). Высокий риск и ремонт сильную
модель больше не включают; «новый worker» при ремонте — это свежий контекст, не
другая модель. Уровень мышления выбирает среда под задачу. Это совет: AISpa не
выбирает модель сама.

## Без изменений

Журнал, реальные участники и usage, handoff, clean clone, blind, знания;
закреплённые прошлые прогоны.

## Проверки

Модульные тесты на каждый режим, смену режима, дополнительную волну,
отложенную зависимость, сценарии и маршрут моделей; полный набор Python и
Node; критика code, logic, skeptic; одна финальная CI перед слиянием.
