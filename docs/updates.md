# Обновления AISpa · 0.1.0-alpha.4

Обновляется установленная папка навыка. Текущий прогон продолжает работать
с собственной закреплённой копией runtime. Для alpha.4 владелец разрешил
публикацию предварительного Release после проверок. Установки пользователей
обновляются только после их выбора; глобальная установка на машине автора
не выполняется автоматически.

## Порядок при явном вызове

Первой операцией агент выполняет из установленного пакета:

```text
python3 <skillDir>/tools/aispa.py update-check
```

Проверка read-only. Источник — опубликованные GitHub Releases репозитория
`alexfisenkov/aispa`. Draft, main и tag без опубликованного Release не подходят.
Сравнение — SemVer: установленная alpha рассматривает подходящие prerelease
и stable; стабильная версия рассматривает только stable. Проверяется не
только последняя запись по дате: список выпусков ограниченно просматривается
страницами, чтобы более старый stable не потерялся среди новых prerelease.

| Status | Действие агента |
|---|---|
| available | При installAllowed подготовить кандидата |
| current / no_release | Продолжить установленной версией |
| offline | Кратко сообщить недоступность проверки и продолжить |
| invalid_release | Сохранить текущую версию; не обходить проверку метаданных |

Git checkout с отслеживаемыми файлами пакета, закреплённый runtime и каталог
пакета, содержащий `.aispa`, защищены от установки. Check сообщает
installAllowed/installReason. Ошибка проверки Git также может запрещать запись.

```text
python3 <skillDir>/tools/aispa.py update-prepare
```

Prepare скачивает ресурсы выпуска, проверяет manifest, SHA-256 архива, состав,
размеры, права и контрольные суммы файлов; связывает commit с tag опубликованного
Release. Кандидат хранится рядом с установленным каталогом в
`.aispa-update-<id>/package`. Текущий пакет остаётся неизменным.

Квитанция включает candidateId, установленную и новую версии, releaseUrl,
commit, archiveSha256, expectedCurrentDigest, candidateDigest и diff
(added/removed/changed/unchangedCount). Агент показывает эти конкретные сведения,
затем предлагает **«Установить обновление»** или **«Продолжить с текущей версией»**.
Ошибка подготовки не блокирует работу с текущим пакетом.

Только после явного выбора установки:

```text
python3 <skillDir>/tools/aispa.py update-apply --candidate <candidateId> --confirm
```

Apply заново проверяет кандидата и сравнивает установленный пакет со снимком
prepare. Если появились пользовательские изменения, установка отказывается
их затирать: нужна новая подготовка и просмотр. Старый пакет сохраняется рядом
в `.aispa-backup-<id>/package`; receipt.json хранит путь, версии и хеши.
При обычной обработанной ошибке замены код пытается вернуть исходный пакет.
Подтверждение флагом не заменяет реальный выбор пользователя в диалоге.

После успешной установки агент перечитывает SKILL.md. Активный прогон не
мигрируется; в нём используются прежние инструкции и движок. Новый прогон
использует новый установленный пакет.

## Откат и аварийное восстановление

Штатный откат после явного выбора пользователя:

```text
python3 <skillDir>/tools/aispa.py update-rollback --backup <backupId> --confirm
```

Он разрешён, только если сохранённая и текущая версии не изменились после
установки. Новая версия при откате остаётся в backup/replaced. Повторное
применение использованной квитанции запрещено.

SIGKILL или потеря питания между переименованиями не дают Python выполнить
обработчик отката. Установленная папка в этот момент может отсутствовать,
а receipt иметь status installing. Штатный update-rollback такую незавершённую
установку не принимает. Восстанавливай её отдельной локальной операцией:

1. Убедись, что процесс обновления остановлен. Не удаляй lock активного процесса.
2. Найди соседнюю `.aispa-backup-<id>/receipt.json` с точным target. Проверь
   наличие `package`, candidate и фактическое состояние target; ничего не удаляй.
3. Сверь исходный пакет с backupDigest из receipt. Используй `_snapshot` из
   доступной сохранённой копии движка либо проведи эквивалентную сверку состава,
   размеров, прав и SHA-256. При расхождении остановись и сохрани все копии.
4. Если target отсутствует и исходная копия подтверждена, верни именно
   `backup/package` на записанный target. Если target уже существует, сначала
   разберись, завершилась ли установка; не перезаписывай его вслепую.
5. Проверь версию и состав восстановленного пакета. Только после подтверждения
   отсутствия активного процесса убери оставшийся соседний
   `.aispa-update-lock-<hash>`. Сохрани receipt и результаты восстановления.

Это ручной recovery, не обещание атомарности при аварийном завершении.
Соседние backup/candidate каталоги автоматически не очищаются: их состояние
нужно учитывать при дальнейшем обслуживании.

## Подготовка ресурсов будущего Release

Из корня репозитория, после сохранения нужного commit:

```text
python3 tools/package_update.py --commit <точный-commit-SHA> --output <свободный-каталог>
```

Команда читает только Git-объекты выбранного commit, берёт `skills/aispa/` и
корневой LICENSE. Незакоммиченные изменения не включаются. Фиксированные ZIP
метаданные дают воспроизводимый архив для того же commit. Команда **не публикует**
Release. Его будущие ресурсы должны называться ровно `aispa.zip` и
`aispa-update.json`; каждый присутствует один раз и имеет состояние uploaded.

## Прикрепление ресурсов после публикации Release

Подготовлен [.github/workflows/release.yml](../.github/workflows/release.yml).
Он запускается только на `release.published`, включая публикацию prerelease.
Такой тип события охватывает и prerelease из draft; это соответствует
[документации GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#release).
Push, создание tag и ручной запуск workflow не включены. Сейчас Release не
создаётся, workflow не запускается и ресурсы никуда не отправляются.

При будущей разрешённой публикации тег должен указывать на commit с этим
workflow и `tools/package_update.py`. Имя тега обязано точно совпадать с версией
пакета, с необязательным начальным `v`: для текущего пакета это
`0.1.0-alpha.4` или `v0.1.0-alpha.4`. Workflow сверяет commit тега с commit
события и checkout, затем собирает пакет именно из него. Ветка main при сборке
не подставляется. Версия и commit manifest проверяются до загрузки.

Workflow прикрепляет только `aispa.zip` и `aispa-update.json` к уже существующему
Release `alexfisenkov/aispa`; сам Release он не создаёт. Право `contents: write`
выдано только job release. Если хотя бы один из этих ресурсов уже существует,
загрузка останавливается; `--clobber` не применяется. Этот флаг удаляет старый
ресурс перед загрузкой, поэтому здесь он исключён.
[Справка GitHub CLI](https://cli.github.com/manual/gh_release_upload).
После загрузки перечитываются имена, состояние uploaded и размеры обоих файлов.

Между публикацией Release и успешной загрузкой обоих ресурсов есть промежуток.
В это время update-check может вернуть invalid_release; установленный пакет
сохраняется, работа продолжается. Выпуск становится доступен механизму
обновления после появления обоих корректных ресурсов. Если загрузка оборвалась
частично, повторный запуск не заменяет уже загруженный файл: сначала отдельно
разберите состояние ресурсов и результаты workflow, не включайте clobber
для обхода отказа.

## Формат ресурсов

Архив содержит файлы под `aispa/`. Manifest schema 1:

```json
{
  "schema": 1,
  "repository": "alexfisenkov/aispa",
  "version": "0.1.0-alpha.4",
  "commit": "<40 строчных hex-символов>",
  "archive": {"name": "aispa.zip", "sha256": "<64 строчных hex-символа>"},
  "files": [
    {"path": "SKILL.md", "sha256": "<SHA-256>", "size": 1234, "mode": 420}
  ]
}
```

Пример неполный: files должен перечислять весь фактический пакет, включая
SKILL.md, tools/aispa.py, tools/aispa_core/__init__.py и LICENSE. Mode — 420
(0644) или 493 (0755). Версия кода, manifest и Release совпадают; commit
manifest совпадает с commit опубликованного tag.

Пределы: 2048 файлов, 16 MiB на файл, 64 MiB распакованного пакета, 32 MiB
архива, 2 MiB метаданных. Ссылки, специальные файлы, небезопасные пути,
повторные записи и лишние файлы отклоняются. HTTPS и хеши привязывают ресурсы
к manifest доверенного репозитория; это не независимая цифровая подпись
издателя. Проверки с синтетическим транспортом не заменяют испытание реального
опубликованного Release.

Для нового прогона alpha.4 разрешён read-only handoff завершённой истории
schema 1 из alpha.1–alpha.3. Это не обновляет старый runtime и не переносит
старые PASS в новые задачи. Активный старый прогон продолжается своей копией.
