# План: экономный контроль (lean control)

Ветка `work/lean-control`. Слияние в `main` и выпуск — только после
локальных проверок, критики и одной финальной CI по решению владельца.

## Зачем

Замеры показали, что AISpa тратит в 1,9–4× больше времени и токенов, чем
референс, при одинаковом внешнем результате
([повтор Pulsefold](validation-lean-service-single-repeat.md),
[три проекта](validation-context-optimization-paired-test.md)).
Разбивка повтора Pulsefold по участникам (вход вне кэша):

| Участник | Доля |
|---|---:|
| координатор | 36,7% |
| critic1 | 21,0% |
| итоговый blind | 12,0% |
| приёмщик задачи | 9,7% |
| исполнитель | 6,6% |
| сверка покрытия, разбор брифа, знания | 14,0% |

Код пишется на 6,6% бюджета. Сокращение текста предыдущей итерации дало
−1,6% в одном повторе. Гипотеза этой ветки: расход определяют число
проверяющих ролей, число перечитываний одних источников и число служебных
вызовов координатора, а не размер отдельных файлов. Причинность замеры не
устанавливают.

Какую долю затрагивает каждое изменение (по повтору Pulsefold, план из одной
задачи, она же финальная):

| Изменение | Затрагиваемая доля | Ожидание |
|---|---:|---|
| 1. Критик закрывает задачу | приёмщик задачи 9,7% | роль снимается целиком |
| 3. Критик читает изменения | critic1 21,0% | меньше перечитываний; у финала — весь diff |
| 5. `batch` | часть доли координатора 36,7% | меньше ответов модели на служебные шаги, если координатор пакетирует; число событий журнала то же |
| 4. Сценарии по глубине | часть координатора | меньше текста подготовки |
| 2. Standard | 0% в Pulsefold | эффект только при двух и более нефинальных задачах |

Это прогноз, не измерение.

## Что меняется в новых прогонах

Новый `init` закрепляет `policy.leanControl: true`. Закреплённые прогоны
и прежние попытки сохраняют свои правила: политика берётся из журнала, а не из
версии пакета. Ручная миграция активного журнала запрещена.

### 1. Критик закрывает задачу (`reviewPolicy: lean`)

- Роли heavy-попытки: worker, critic1, условный critic2. Отдельного
  приёмщика задачи нет.
- Критик lean берёт обязанности приёмщика: все критерии замыкания задачи,
  ограничения проекта, `trace` к точным цитатам владельца, поиск обещанного в
  брифе, но потерянного в реестре (`unmapped`), документы передачи; переносит
  ссылки `inheritedProofs` на доказательства зависимостей (у standard-предков —
  проверенное выполнение, их код критик финала читает в общем обзоре).
- PASS первого критика сразу завершает задачу (`completionKind:
  critic_acceptance`). WARN/BLOCK/FAIL → диагностика → ремонт → свежий critic2;
  его PASS завершает задачу, любой non-PASS блокирует. Третьего круга нет.
- Расхождение trace (`drift`) несовместимо с PASS и требует обязательного
  замечания по критерию соответствия исходному запросу.
- Итоговая независимая приёмка проекта по брифу (blind) и clean clone
  остаются без изменений.

### 2. Класс `standard`: код без точечной критики

- Кроме `light` (только документация и оформление) и `heavy` появляется
  `standard`: обычная задача с кодом без отдельного критика задачи.
- Маршрут: worker → test-intent (RED/GREEN) → адресная проверка → `submit` →
  `verified_completion`. Изменения не выходят за объявленные зоны задачи.
- Ограничения: риск `low` или `normal` с причиной; зависеть от неё может
  только финальная задача, зависящая от всего плана (фундамент остальных —
  heavy); зоны не касаются правил агента, секретов, авторизации, платежей,
  миграций, схем и контрактов. Standard может быть и финальной задачей — тогда
  общий обзор делает отдельный `integration-review`.
- Покрытие: обязательный общий обзор всей версии. Финальная heavy-задача
  проверяет всю ветку своим критиком (`branchReview`); если финальная задача
  не heavy — отдельный `integration-review`, как у light.
- Зоны standard-задач включаются в зоны записи финала: дефект, найденный
  общим обзором, исправляется штатным ремонтом финальной задачи.
- Сомнение или новый риск → `promote-task` до heavy с сохранением истории.
  Понижение после старта запрещено.

### 3. Критик читает изменения, а не всё заново

- Пакет критика lean содержит `zoneChanges` — файлы зон задачи, изменённые
  относительно исходного снимка прогона (у финальной задачи — весь diff версии,
  `zoneChangesScope: branch`), и правило чтения: сначала карточка,
  изменения зоны, test-intent и цитаты trace; бриф, spec, discovery, план и
  знания — по необходимости для конкретной находки.
- Полнота проверки сохраняется: все `expectedChecks` и вся строка trace
  обязательны; изменённые файлы читаются целиком.

### 4. Сценарии по глубине

- В lean `balanced` требует измерения `main`, `empty`, `error`,
  `persistence`; `strict` — `main` и `error`; `deep` — все восемь
  с контрпримерами. Дополнительные измерения допускаются, неизвестные — нет.

### 5. Пакетные служебные вызовы

- `aispa.py batch --file steps.json` выполняет до 25 подкоманд по очереди
  в одном вызове и останавливается на первой ошибке. Каждый шаг — отдельная
  обычная команда со своей блокировкой и событием журнала; запрещены
  обновления, сервер, панель, восстановление журнала и вложенный batch.
- Ответ каждого шага сохраняется полностью; в вывод попадает краткая
  квитанция (как `--compact`).

## Отличия от предложенного владельцу

Владелец поручил сделать четыре предложения агента. Отличия реализации:

- **«Задачу проверяет итоговая слепая приёмка».** Отдельный приёмщик снят,
  но его проверка задачи (trace, критерии предков, `unmapped`, документы
  передачи) перенесена на критика, а не в blind: blind смотрит продукт целиком
  и не видит границы задачи. Часть стоимости приёмщика поэтому остаётся у
  critic1; доля 9,7% — верхняя оценка экономии.
- **«Один аналитик и один независимый читатель брифа».** Так устроено с 0.1.0:
  автором `brief-extract` может быть координатор, `brief-review` и `brief-map`
  делает один отдельный проверяющий. Ветка это не меняет. Объединить два прохода
  проверяющего в один не стали: карта сверяет два независимых разбора и без
  второго теряет смысл.
- **«Сценарии только в глубоком режиме».** Сделано мягче: balanced требует 4
  измерения из 8, strict — 2. Полный отказ от сценариев в обычном режиме убрал
  бы единственную проверку пустых данных и ошибок до плана.
- **«Регистрация, usage, квитанции — пакетом».** Сделано общей командой
  `batch` для любых служебных шагов; квитанции по-прежнему пишет каждая
  команда. Экономия зависит от того, пакетирует ли координатор.
- **«Точечная критика только фундаменту и рискованному».** Сделано классом
  standard, но поле по умолчанию осталось heavy: экономия появляется, только
  если план явно размечает обычные задачи как standard.

## Что не меняется

- Исходный бриф, два независимых разбора до `seal`, сверка покрытия spec.
- Журнал, SHA, квитанции, реальные native ID и usage всех участников.
- test-intent с реальным RED/GREEN, отказные границы, clean clone, blind,
  handoff, знания.
- Light-маршрут и его ограничения.

## Проверки

- Новые модульные тесты на lean-цепочку, standard, сценарии, batch, пакет
  критика; прежние тесты legacy/adaptive/light не ослабляются.
- Полный локальный набор Python и Node; `git diff --check`.
- Критика изменений (code, logic, skeptic) до слияния.
- Модельный замер экономии этой веткой не выполняется: оценка эффекта
  остаётся прогнозом до отдельного поручения владельца на повтор.
