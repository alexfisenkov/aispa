# Модельный пилот AISpa alpha.10

Проверен локальный учебный Python-проект: команда CSV→JSON без сети и сторонних пакетов. Исходный бриф B001 и уточнение B002 написаны для тестового сценария; B002 дал автор сценария после обнаруженного дефекта. Это не новые слова владельца настоящего проекта. Локальный архив прогона хранится в исключённой из Git `.проверки/alpha10/native-pilot/`; опубликованный документ не содержит личных путей, нативных идентификаторов агентов и исходных журналов.

Новый `init` закрепил runtime `0.1.0-alpha.10` с SHA-256 пакета `ad8f41aa1e17be981ef408eef3884ea976a225f1e2e2934936c781b71a42a446`. Все 14 флагов политики нового прогона были включены. Позднейшие изменения рабочего пакета не меняли закреплённую копию, которой выполнены все команды пилота.

Два независимых читателя отдельно разобрали полный исходный текст до фиксации требований; после B002 оба обновили разбор. Координатор записал идею, исследование источников, спецификацию, сценарии по восьми измерениям для шести требований, интерфейсный контракт, покрытие спецификации и план. План состоял из двух зависимых задач в двух волнах; последняя читала всё дерево. После каждой волны весь бриф проверял отдельный reviewer. В первой волне README было явно `not_tested`; после второй все девять условий R01–R06 получили `passed`.

Первая попытка T01 показала полезную границу: два независимых критика дали PASS, но отдельный приёмщик нашёл, что CSV из одной пустой строки ошибочно создаёт `[]`. AISpa сохранил FAIL и закрыл попытку. Новое разрешение B002 принадлежало только автору синтетического сценария; штатный `new-attempt` сохранил прежнюю историю. Во второй попытке новый тест дал настоящий RED (код 1, один ожидаемый провал), исправление одной функции — GREEN (9 тестов, код 0). Два **новых** критика и новый приёмщик приняли результат. Это подтверждает путь отказа приёмщика и новой разрешённой попытки; путь `repair-plan` между первым FAIL-критиком и вторым критиком здесь не испытывался.

Для T02 отдельный исполнитель подготовил обычный Git README, затем два свежих критика независимо проверили полный diff по поведению, взаимодействию частей, сопровождаемости, данным и безопасности, качеству тестов. Отдельный приёмщик принял задачу. Локальный Git commit учебного проекта — `4d1c8487a5f8cb8b9da1a9c466c1b6e3f03e8601`. После commit свежая общая проверка и handoff прошли; движок подготовил клон именно этого commit. `clean-verify` завершился кодом 0: 9 тестов, без усечения вывода, таймаута и изменения исходников или клона. После handoff последняя волна была повторно проверена, потому что прежнее основание стало устаревшим.

Слепой итоговый приёмщик сначала увидел только B001/B002 и чистый клон. Девять первичных наблюдений были записаны до раскрытия реестра; затем все девять сопоставлены с требованиями. Процедурную историю B002 приёмщик проверил отдельно по журналу после слепого этапа. Итоговая `acceptance` прошла, новый автор знаний сохранил пять записей, `finish` вернул `accepted`. Повторное чтение статуса подтвердило две завершённые задачи, шесть действующих принятых требований и отсутствие остатка.

Границы результата: прогон выполнен на macOS с локальными синтетическими CSV. Нативная Windows, иные файловые системы, сбои диска, изоляция сети и испытание владельцем не проверялись. Чистый клон — проверка исполнения из зафиксированного Git-снимка, не sandbox. Действительные агентские роли подтверждены ответами `collaboration`; host не раскрыл session ID, необходимый для адресной привязки доступных native token logs к зарегистрированным участникам. Поэтому `usage` показывает 0 измеренных вызовов из 19 зарегистрированных участников, `complete=false`; расход токенов и экономия полного прогона неизвестны. Этот пилот подтверждает указанный сценарий разработки и сдачи, а не все возможности AISpa и не выпуск пакета.

## Отдельное упражнение: ремонт между критиками

На втором маленьком fixture с тем же закреплённым runtime проведена **узкая** проверка `critic1 FAIL → repair-plan → свежий worker → repair → critic2 → acceptor`. Её подготовка помечена как synthetic: координатор создал бриф и исходный код, а покрытие спецификации и план до задачи были подготовлены без независимых моделей. В этом упражнении включена только политика `repairDiagnosis`; остальные политики alpha.10, в том числе `testIntent`, намеренно выключены. Оно не является вторым полным пилотом и не получило итоговый `finish`.

Подготовительный реальный запуск сначала дал RED для `ready`, затем GREEN одного теста happy path. Отчёт подготовительного исполнителя прямо назвал проверку неизвестных аргументов незавершённой. Первый **настоящий** независимый критик обнаружил: `--unknown` возвращал код 0 и печатал `ready`; он записал два блокирующих замечания. `repair-plan` поставил диагноз `wrong_approach` и потребовал свежего исполнителя. Новый исполнитель добавил регрессионный тест (RED: один провал), исправил обработку аргументов (GREEN: 2 теста), и штатный `repair` связал оба замечания с диагнозом и новой проверкой. Свежий critic2 подтвердил обе резолюции; отдельный приёмщик проверил исходные R01/G01 и принял задачу. Повторное чтение журнала дало `directProofCurrent=true` и `historicalProofValid=true` для этой задачи.

В упражнении изменение теста после первого критика видно из файлов и настоящих RED/GREEN-квитанций, но отдельный gate `testSourceChanges` **не проверялся**, потому что `testIntent` выключен. После приёмки задачи координатор испытания закрыл этот узкий прогон через `close cancelled` с явной пометкой о завершении упражнения: это останавливает часы и не заменяет полную сдачу. Повторное чтение показало завершённую T01 с `proofCurrent=true` и `acceptance=false` для всего прогона. Волна, handoff, клон, слепая итоговая приёмка, знания и `finish` здесь не запускались; их проверяет основной пилот выше. Ни одна синтетическая подготовительная стадия не считается нативным суждением критика или приёмщика.
