# Изучение проекта, память и контекст · 0.1.0-alpha.4

AISpa хранит разные сведения отдельно: исходные слова и решения владельца,
исследование существующего проекта, текущий план и доказательства исполнения.
Они имеют разные сроки актуальности. Историческая приёмка остаётся исторической;
новый план требует актуальных источников, а задача — актуальных проверок кода.

## Изучение существующего проекта

Init фиксирует имена найденных файлов и создаёт ссылки в правилах среды.
Этого недостаточно для выбора архитектуры. До spec и plan нового прогона
координатор выполняет следующий порядок через закреплённый runtime прогона:

1. `discover` собирает ограниченный набор документов, манифестов и фрагментов
   кода. Команда возвращает путь к JSON-артефакту, который нужно прочитать.
2. Если важные бизнес-модули или тесты имеют другие имена, перечислить их
   повторяемым `discover --include src/order_totals.py --include tests/test_order_totals.py`.
   Это пример синтаксиса: пути должны существовать в изучаемом проекте.
3. Изучить реальные источники, связи и ограничения. Сохранить отчёт JSON и
   передать его через `discover --file <report.json>`.
4. `discovery` показывает записанные выводы, ссылки и свежесть. Общие выводы
   переиспользуют все роли; конкретные входы задачи дополнительно задаёт readZones.

Отчёт содержит basis из сбора, summary, observations и uncertainties. Семь
областей: architecture, data, entrypoints, dependencies, commands, conventions,
risks. Для каждой нужно наблюдение либо явная причина неопределённости.
Наблюдение содержит area, text и непустой sources; каждая ссылка — path и
точный sha256 собранного файла. Необязательная excerpt должна дословно
присутствовать в собранном фрагменте. Наблюдение commands дополнительно содержит
command, дословно извлечённую из указанного источника. Полный формат —
[contracts.md](../skills/aispa/references/contracts.md).

Сборщик извлекает реальные строки scripts из package.json, поддержанные
команды pyproject.toml, Makefile, tox.ini и командные фрагменты Markdown.
Он не выводит команду проверки из названия языка или пакета и ничего не
исполняет. Наличие команды в документе ещё не означает успешную проверку.

По умолчанию выбираются обычные проектные документы и узнаваемые точки входа.
Явный include допускает дополнительные исходники и Markdown, в том числе тесты.
Включённые пути сохраняются в includedPaths и используются при следующем
сборе без --include. Новый непустой набор --include заменяет прежний явный набор.
Обычные автоматически выбираемые источники при этом сохраняются.

Git-игнорируемые файлы исключены, даже если уже отслеживаются. Сборщик не читает
пути с секретами, .env, пользовательскими данными, архивами, vendor, сгенерированным
содержимым или символическими ссылками. Скрытое исключено, кроме явно разрешённой
обычной конфигурации .editorconfig. Include не отменяет эти границы; небезопасный,
неизвестный или игнорируемый путь вызывает отказ. Распознаваемые секреты внутри
обычного документа не попадают в артефакт. Это консервативный фильтр известных
признаков, а не доказательство отсутствия любого возможного секрета.

В сборе не более 48 источников; файл читается в пределах 256 KiB. Фрагмент
одного файла ограничен 6 000 символами, общие фрагменты — 96 000 символами.
Документы, манифесты и код чередуются, чтобы длинная папка документации не
заняла весь сбор. Для усечённых фрагментов записывается omittedChars; для
исключённых кандидатов — причины, количества и число невыведенных деталей.
Команды также имеют лимит и счётчик пропусков. Пропуск важного источника нужно
разобрать до выводов; короткая выдержка не означает изучение всего файла.

Обычные источники связаны с полным SHA-256, включая файлы, фрагменты которых
не вошли из-за лимита. Файлы больше 256 KiB не читаются и явно отмечаются;
для их изменений используются размер и время модификации. Добавление нового
подходящего источника, удаление или изменение выбранного файла делает снимок
устаревшим. Произвольный новый модуль с нераспознаваемым именем автоматически
не становится источником — его включают явно, если он важен для задачи.

Сохранённый отчёт доступен в `.aispa/context/project-study.md`; полные фрагменты
и учёт пропусков лежат в неизменном артефакте сбора. После реализации прежний
снимок остаётся контекстом принятого плана. Он не останавливает задачи только
потому, что исполнитель изменил код: задачи проверяются по своим zones,
readZones, зависимостям и общим входам. Перед новой спецификацией или новым
планом требуется обновить устаревшее исследование.

Валидатор подтверждает происхождение ссылок и команд. Смысловые выводы агента
об архитектуре или рисках проверяются чтением источников и независимой критикой;
один правильный хеш не доказывает правильность вывода.

## Память между прогонами

При новом допустимом init AISpa сохраняет историю предыдущих прогонов,
исходные тексты, решения, требования, попытки, доказательства и остатки в
неизменной передаче с проверяемым происхождением. Повреждение старого журнала
или источников вызывает отказ вместо тихой потери истории.

Команда `memory` показывает полный реестр передачи; производное представление
находится в `.aispa/context/carryover.md`. Принятые раньше требования отмечены
как исторические. Текущие briefs, requirements и tasks начинаются по новому
заданию: старый scope и отметки PASS не переносятся автоматически.

Каждое открытое обязательство имеет устойчивый ID. Команда `carry` позволяет
записать дальнейшее решение:

| Действие | Что означает |
|---|---|
| keep | сохранить остаток открытым; новая работа и приёмка не заявляются |
| map | связать с текущим требованием по новому разрешению владельца |
| resolve | закрыть после свежей приёмки всех соответствующих текущих задач |
| drop | снять обязательство по новым словам владельца |
| defer | сохранить перенос по новым словам владельца |

Для map, drop и defer нужны --brief и --quote: ссылка на новый текущий бриф
владельца и точная цитата. Копия старого брифа под новым ID разрешением не
считается. Для map также нужен --requirement; исходный текст и вид требования
должны совпадать, обязательность ядра сохраняется, прежние критерии остаются
в новом наборе. Сопоставление выполняется до сдачи и критики новой задачи.
Переименование требования само по себе не снимает старое обязательство.

Resolve проверяет свежие текущие доказательства, новые нативные роли и создание
попытки после разрешения. Историческое completed не заменяет эти проверки.
Открытые и отложенные остатки сохраняются при итоговой сдаче и приводят к
`delivered_with_remaining`, даже если весь новый объём принят.

Проверка точной цитаты подтверждает её наличие в брифе. Координатор отвечает
за то, что это действительно новые слова владельца и соответствующее решение.

## Адресный контекст и выбор модели

`context --write` сохраняет адресный пакет для роли. Его основной JSON-файл
занимает не более 16 000 байт. Если полный контекст больше, крупные разделы
записываются целиком отдельно; пакет содержит пути и SHA-256. Эти разделы
могут быть больше лимита основного файла. Требования, исходные слова,
expectedChecks и ограничения не обрезаются, и роль обязана прочитать нужные
ссылки. Экономия возникает от выбора релевантного контекста и повторного
использования источников, а не от потери условий приёмки.

Рекомендация standard допускается для worker явно низкорисковой задачи с
riskReason, когда от неё не зависят другие задачи и это не повторная попытка.
Другие исполнители и все critic1, critic2, acceptor получают рекомендацию
strong. Два сильных независимых критика и отдельный сильный приёмщик сохраняются
в каждой попытке. Координатор выбирает реальные модели, доступные среде и
разрешённые правилами проекта; движок не назначает выдуманные model ID.

Если среда возвращает usage, его можно записать через `usage --file` с actor,
callId, source, inputTokens, outputTokens и cachedInputTokens. Это необязательные
реальные измерения отдельных вызовов. Отсутствующие значения не считаются нулём;
байты пакета не пересчитываются в якобы измеренные токены. Сводка usage не
обещает полноту и не рассчитывает неподтверждённую экономию.

## Проверка чистой копии

Для новых init alpha.4 финальная приёмка требует успешного актуального
clean-verify. Сначала сохранить код в Git, затем выполнить clean-prepare и
запустить реальную команду продукта через clean-verify. Рабочая папка,
игнорируемые зависимости, .env и пользовательская конфигурация не подмешиваются
в подготовленный клон. Отчёт связан с точным HEAD и снимком файлов.

Пакет `context --kind blind --write` предназначен новому проверяющему: сначала
исходные брифы и продукт в чистом клоне, затем самостоятельные наблюдения,
после сохранения этих наблюдений — полный пакет acceptance для сверки реестра
и доказательств. До записи первоначальных наблюдений пакет сверки недоступен.
Движок не может проверить, что модель никогда не видела план: это обязанность
координатора при создании нового контекста.

Clean-verify — проверка воспроизводимости в отдельной копии с очищенным
окружением. Она не изолирует операционную систему или сеть. Зависимости,
установка и внешние сервисы должны быть доступны по явному сценарию проекта.
Неуспех нельзя заменить проверкой только в старой рабочей папке.

Поле openReasons хранит исторические причины: часть замечаний могла быть
исправлена позже. Их актуальность определяют статус пункта и свежие доказательства,
а не само наличие старой причины. Полный текст остаётся по ссылке на исходный отчёт.
