## Проверки

Из корня: `python3 -B -m unittest discover -s tests -v`.
Нативная Windows: `python -X utf8 -B -m unittest discover -s tests -v`
(или `py -3` с теми же аргументами); Python 3.11+, Git for Windows.
Правила Windows и PowerShell — `docs/windows.md`. Нельзя исключать из Windows
clean-run, полный CLI, blind или реальную offline-установку pip.
Пропуски допустимы только для проверки механизма, специфичного для другой ОС;
ссылочные и файловые guards проверяются реально. Локальный PASS macOS/Linux
не подтверждает нативную Windows: нужен результат CI для точного commit.
Интерфейс: `node --test tests/dashboard.test.cjs` (Node 18+, без npm-зависимостей).
До отправки проверить состав коммита, отсутствие секретов и локальных путей.
Промежуточные push не запускают Actions; один ручной запуск после целевого
локального набора проверок. Ошибка CI требует исправления и нового подтверждения.

Честно разделять проверку библиотечного кода, полный сценарий движка,
поведение LLM и пользовательское тестирование. Зелёные тесты не подтверждают
работу полного навыка, пока соответствующий сценарий не выполнен.

## Контракты рабочей версии и совместимость

Новые политики включаются только новым `init` из Git-кандидата. Опубликованная
alpha.10 и её закреплённые runtime сохраняют прежние правила. Не мигрировать
активный журнал сменой policy вручную. Исторические отчёты не переписывать.

Роли задач создаются по проекту и задаче, сохраняются в журнале и неизменных
карточках. Нативных агентов создаёт среда; ID берут из реальных ответов её
инструментов. Новые прогоны ветки lean-control закрепляют `leanControl`
(`reviewPolicy: lean`, класс standard, сценарии по глубине); ниже описан
маршрут 0.1.0, который сохраняют закреплённые прогоны, а отличия lean —
в `docs/plan-lean-control.md`. Новые прогоны 0.1.0 закрепляют `taskTiers`. По умолчанию задача
heavy; light требует низкого риска, предметного обоснования и точных безопасных
файлов. Light завершается через проверку и worker-report с `verified_completion`,
без отдельных critic1/critic2/acceptor. Это не итоговая приёмка проекта.
У heavy первый свежий критик с PASS ведёт прямо
к отдельному приёмщику. WARN/BLOCK/FAIL требуют ремонта и второго свежего
критика; любой его non-PASS либо отказ приёмщика закрывает попытку блокировкой.
Информационный note не равен требующему исправления warning. Не назначать
critic2 до ремонта и не придумывать ему отчёт при первом PASS.
Reset, replan и новое имя задачи не обходят исчерпанный
лимит; новую попытку разрешают только новые записанные слова владельца.
При новых рисках `promote-task` повышает light до heavy, сохраняет прошлую
попытку и снимает прежнее доказательство. Понижение класса после старта запрещено.
Обзор всей версии обязателен: у финальной heavy входит в её критику, у финальной
light требует отдельного свежего `integration-reviewer` и `integration-review`
до handoff/clean clone. Итоговый независимый приёмщик по брифу остаётся отдельным.

Первое действие при явном вызове установленного навыка — update-check.
Источник обновлений — опубликованные Releases alexfisenkov/aispa. Подготовка
кандидата предшествует предложению установить; apply/rollback требуют явного
выбора. Git checkout, активный runtime и каталоги с прогонами не заменяются.
Последний подтверждённый предварительный выпуск — `0.1.0-alpha.10`. Его публикация и
проверка ресурсов подтверждены в `docs/validation-alpha.10.md` и
`docs/pilots/alpha.10/release-verification.json`; стабильный 0.1.0
опубликован после финальной CI; его свидетельства — `docs/validation-0.1.0.md`.
Первый установщик 0.1.0 выбирает stable SemVer вместе с GitHub
`prerelease=false`; явный опубликованный tag может выбирать prerelease.
Завершённая alpha.10 допускается только для read-only handoff; активная история
не мигрирует на новую версию, её байты и pinned runtime сохраняются.

Корневые ссылки контекста стабильны; обычный refresh пишет только скрытые
представления. Канон — журнал и неизменные источники, не memory.md. Конфликты
пользовательских правил и ссылки за пределы проекта не обходят перезаписью.

Перед spec и plan нового прогона обязателен свежий отчёт discovery с источниками
по семи областям. Имена файлов не заменяют изучение. После реализации сохранённый
снимок остаётся контекстом плана; актуальность задач обеспечивают readZones и
проверки кода. При новом планировании исследование обновляется.

Новый init сохраняет историю и остатки, но не переносит текущий scope и старые
PASS. Сопоставление carry map требует нового брифа владельца и точной цитаты;
исходный текст, вид, ядро и критерии не ослабляются. Финальная приёмка нового
прогона требует свежего clean-verify. Чистый клон не является sandbox.

Экономия допускается через ссылки, повторное использование исследования и
обоснованный low-risk worker. Для heavy сохраняются сильный независимый критик
и отдельный сильный приёмщик; для light — проверяемое завершение и обязательные
общепроектные проверки. Байты пакета и число ролей не выдавать за измеренные
токены; новые полные модельные замеры этой итерацией не разрешены.

Заголовки и каталог документов служат навигации. Изменённый SHA снимает
актуальность прежнего описания. Исходные брифы, доказательства, пользовательские
поля YAML и файлы только для чтения не переписываются ради индексации.
Обычный refresh меняет только скрытые представления; запись заголовка в
прикладной Markdown требует адресного --write-header и проверки прочитанного SHA.
Это не атомарный CAS с внешним редактором; при совместной записи используй каталог.

Новые прогоны alpha.9 требуют разбора идеи до seal/spec, разбора размера плана
до запуска задач и записи знаний после итоговой приёмки перед finish.
Компактный разбор всё равно рассматривает проблему, пользователя, результат,
альтернативы и малый эксперимент. Assessed не означает доказанный спрос.
Укрупнение сохраняет каждое исходное условие, включая одинаково названные
критерии с разными исходными ID; маршрут проверки определяется закреплённым
классом задачи и не ослабляется при укрупнении.
Знания пишет отдельный свежий участник по коду и действительным свидетельствам;
историческая команда не является текущим PASS. Контрольные точки ограничивают
контекст, но сохраняют исходную историю в проверяемом архиве.

Новые прогоны alpha.9 дополнительно требуют пять продуктовых challenge и их
независимую сверку со spec, delivery-разбор сквозных результатов и миграций,
диагностику перед ремонтом после первого FAIL и проверенный handoff.
Обычные Git-документы создаются в задачах до окончательной проверки кода,
чистого клона и приёмки; после неё пишется только приватная память.
Входной SKILL маршрутизирует шесть фаз по мере надобности. Сокращение байтов
входного файла не объявлять измеренной экономией токенов полного прогона.
