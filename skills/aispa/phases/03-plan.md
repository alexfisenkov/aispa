# Исследование, архитектура и план

Читай после [основного маршрута](../SKILL.md) перед спецификацией и планом.
До `spec` выполни `discover`; при необходимости укажи адресные
`--include src/module.py`. Собранные свидетельства передай
[исследователю](../prompts/project-researcher.md) либо изучи их как координатор
авторской фазы discovery. Фактический автор подтверждает по источникам
архитектуру, данные, входные точки, зависимости, команды, соглашения и риски
либо явно сообщает неизвестное. Сохрани `discover --file …`. Общие заметки
получат исполнители; всем перечитывать весь код не нужно. Перед новым планом
движок проверяет актуальность исследования.

Из решения по идее сделай `spec` и план с полными требованиями.
`plan-check --file <черновик>` нужен до `plan --file <план> --review <разбор>`: объединяй
мелкие куски одного проверяемого результата или объясни границу. Сохраняй
каждый исходный критерий, включая одинаково названные с разными ID, зоны
чтения/записи, внешние зависимости, риски и дословные объяснения. Для heavy экономия
числа задач не отменяет независимого критика: в lean его PASS закрывает задачу,
иначе после ремонта нужен второй свежий критик. Базовые роли — 1 для light и
standard, 2–3 для heavy lean (3–4 в закреплённых adaptive), не верхняя граница
реальных запусков: замены исполнителя и подготовка считаются отдельно.
Формат: [product-development](../references/product-development.md),
[contracts](../references/contracts.md).

После `spec` и независимой `coverage` заполни файл из `template scenarios --write`. Для
каждой действующей функции сценарии охватывают измерения выбранной глубины.
В новых прогонах `strict` — `main`, `error`; `balanced` — `main`, `empty`,
`error`, `persistence`; `deep` — все восемь: `first`, `main`, `empty`, `error`,
`retry`, `access`, `persistence`, `effects`. Форма уже содержит нужный набор;
дополнительное измерение добавляй, только если оно реально меняет план или
тесты. Закреплённые прежние прогоны требуют все восемь.
Режим проверки переопределяет глубину: `fast` — только `main` и `error`, `max` —
все восемь с контрпримерами, `balanced` — по `--depth`. Форма уже учитывает режим.
`balanced` в `--depth` (глубина сценариев) и «Сбалансированно» (режим проверки) —
разные ручки.
Статус `not_applicable` требует конкретной причины; пустое поле шаблона не
проходит проверку. В `strict` нельзя добавить инициативную функцию, в `deep`
для покрытого измерения нужен контрпример. Сохрани `scenarios --file …`.
Затем `template interfaces --write` и `interfaces --file …` фиксируют сигнатуру,
владельца зоны, потребителей, тестовый шов, требования и происхождение
материалов. Пустой интерфейсный список допустим только с объяснением.
Формы редактируй по выданным путям; не перепечатывай их через координатора.
План связывает владельца каждого интерфейса с задачей, а потребителя — с её
зависимостью. `preparation` показывает структурную актуальность отчётов.

Планируй **законченные видимые владельцу срезы**, а не набор слоёв без
работающего пути. Для нового контракта или данных сохраняй безопасную
последовательность: расширить совместимый интерфейс → перенести всех известных
потребителей → закрепить новый контракт. Укажи зависимости между задачами,
проверки на каждом шаге и путь отката. При изменении API, схемы, конфигурации
или интеграции найди очевидных потребителей, миграции, read models, ошибки и
fallback. Изменение backend и frontend одной функции должно сходиться в одном
проверяемом сценарии.

Для новых прогонов в плане нужна **одна финальная задача**, которая зависит от
остальных и читает всё дерево кода (`readZones: ["."]` уместно). Для heavy в её
выполненных кругах критики проверят весь diff от исходного снимка по поведению,
интеграциям, сопровождаемости, данным/безопасности и качеству тестов.
Первый PASS не требует второго круга. Дополнительного третьего нет.
Для light- или standard-финала отдельный независимый участник выполнит общий
`integration-review` перед передачей и чистым клоном. Это общий обзор версии,
а не критик каждой такой задачи; именно он покрывает standard-задачи без
собственного критика.

В новых прогонах задавай `tier`, `tierReason`, `changeKind` по
[классам задач](../references/task-tiers.md). Неуказанный класс — heavy;
`risk: low` сам по себе не выключает критиков. Поле по умолчанию — heavy;
обычную нефундаментную задачу с кодом явно размечай `standard`. `heavy` —
фундамент, от которого зависят другие задачи (кроме финальной), высокий риск,
чувствительные зоны и задачи, где ошибку дорого найти поздно. Чтобы дефект,
найденный общим обзором в standard-коде, можно было исправить в штатном ремонте
финальной задачи, включай зоны standard-задач в зоны записи финала: он зависит
от них, поэтому пересечение разрешено. Риск, а не дефект, — `promote-task`.
`plan` готовит одну карточку worker для light и standard; для heavy lean —
worker, critic1, critic2 (адаптивные прогоны добавляют acceptor). Если нужна
специализация, используй `team --file …` до первой критики. Не выдумывай
модель или участника: агент создаётся инструментом среды, затем его реальный
native ID и session фиксируются через `assign`. Для общих фаз используй
`participant`; одно native ID нельзя представить независимым проверяющим
под другой session. Изолированная реализация может
быть `risk: low` с обоснованием и рекомендацией standard. Модель задачи — по
правилу ниже (`routing.modelRule`); это совет, не отмена проектных настроек.
Если для Codex недоступна разрешённая Terra, фиксируй capability gap; для остальных
сред учитывай их действующие правила выбора. Токены считай через `usage` и `usage-import` только
по настоящим данным среды для всех ролей; байты пакета не называй токенами.
Если не все участники и вызовы покрыты, итоговую стоимость помечай неполной.

Класс в плане — объявленный. Эффективный класс задаёт режим проверки: в `fast`
все задачи получают `fast`, в `max` — heavy (объявленный сохраняется как
`plannedTier` и возвращается при `balanced`), в `balanced` действует план. Размечай
классы честно в любом режиме. Модели: карточка несёт совет `routing.modelRule` —
в прежней lean-политике для других сред дешёвая модель по умолчанию, сильная —
для путей безопасности, ключей, секретов, сертификатов, доступа, платежей и
личных данных (`task_tiers.strong_model_path`). Managed-политика учитывает
сложность и предлагает профиль конкретного host. Модель выбирает среда, не AISpa. Для новых субагентов Codex выбирай последнюю разрешённую
Terra из фактического каталога host; при отсутствии — capability gap без молчаливой
замены на Luna. Reasoning по сложности и риску: low для механики, medium/high для
обычной работы, high/xhigh для критики и безопасности. Запрос не подтверждает
фактическую модель. Правило живёт здесь; другие файлы ссылаются на него.

Карточка critic2 — возможная ветвь, не приказ создать участника: назначай
его только после первого non-PASS. План может написать сам координатор;
`plan --actor <id>` сохранит действительного автора без второго учёта tokens.
Сама критика и независимая coverage остаются чужой проверкой.
