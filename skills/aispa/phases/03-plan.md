# Исследование, архитектура и план

Читай после [основного маршрута](../SKILL.md) перед спецификацией и планом.
До `spec` выполни `discover`; при необходимости укажи адресные
`--include src/module.py`. Собранные свидетельства передай
[исследователю](../prompts/project-researcher.md) либо изучи их как координатор
авторской фазы discovery. Фактический автор подтверждает по источникам
архитектуру, данные, входные точки, зависимости, команды, соглашения и риски
либо явно сообщает неизвестное. Сохрани `discover --file …`. Общие заметки
получат исполнители; всем перечитывать весь код не нужно. Перед новым планом
движок проверяет актуальность исследования. Входы исследования — включённые
источники без путей из зон задач плана: их изменения покрывают доказательства
задач, поэтому правка внутри зон исследование не устаревает, а правка вне зон —
да. Повторный `discover` на тех же входах ничего не записывает и возвращает
прежний сбор (`reused: true`) — это не ошибка.

Из решения по идее сделай `spec` и план с полными требованиями.
`plan-check --file <черновик>` нужен до `plan --file <план> --review <разбор>`: объединяй
мелкие куски одного проверяемого результата или объясни границу. Сохраняй
каждый исходный критерий, включая одинаково названные с разными ID, зоны
чтения/записи, внешние зависимости, риски и дословные объяснения. Экономия
числа задач не отменяет критика там, где его требует режим: его PASS закрывает
задачу, иначе после ремонта нужен второй свежий критик. Число ролей задачи — не верхняя
граница реальных запусков: замены исполнителя и подготовка считаются отдельно.
Формат: [product-development](../references/product-development.md),
[contracts](../references/contracts.md).

После `spec` и независимой `coverage` заполни файл из `template scenarios --write`. Для
каждой действующей функции сценарии охватывают измерения выбранной глубины.
В новых прогонах `strict` — `main`, `error`; `balanced` — `main`, `empty`,
`error`, `persistence`; `deep` — все восемь: `first`, `main`, `empty`, `error`,
`retry`, `access`, `persistence`, `effects`. Форма уже содержит нужный набор;
дополнительное измерение добавляй, только если оно реально меняет план или
тесты. Глубину сценариев задаёт только `--depth`; режим проверки её не меняет.
`balanced` в `--depth` (глубина сценариев) и «Сбалансированно» (режим проверки) —
разные ручки.
Статус `not_applicable` требует конкретной причины; пустое поле шаблона не
проходит проверку. В `strict` нельзя добавить инициативную функцию, в `deep`
для покрытого измерения нужен контрпример. Сохрани `scenarios --file …`.
Затем `template interfaces --write` и `interfaces --file …` фиксируют сигнатуру,
владельца зоны, потребителей, тестовый шов, требования и происхождение
материалов. Пустой интерфейсный список допустим только с объяснением.
Формы редактируй по выданным путям; не перепечатывай их через координатора.
План связывает владельца каждого интерфейса с задачей, а потребителя — с её
зависимостью. `preparation` показывает структурную актуальность отчётов.

Планируй **законченные видимые владельцу срезы**, а не набор слоёв без
работающего пути. Для нового контракта или данных сохраняй безопасную
последовательность: расширить совместимый интерфейс → перенести всех известных
потребителей → закрепить новый контракт. Укажи зависимости между задачами,
проверки на каждом шаге и путь отката. При изменении API, схемы, конфигурации
или интеграции найди очевидных потребителей, миграции, read models, ошибки и
fallback. Изменение backend и frontend одной функции должно сходиться в одном
проверяемом сценарии.

В плане нужна **одна финальная задача**, которая зависит от остальных и
читает всё дерево кода (`readZones: ["."]` уместно). Всю ветку в конце
проверяют отдельные ревьюеры по линзам режима ([сдача](05-accept.md)); критик
финальной задачи проверяет её собственные изменения.

### Тяжесть задачи и проверки

Задавай `tier`, `tierReason`, `changeKind` по [классам задач](../references/task-tiers.md)
честно. Тяжесть задачи определяет движок, а не объявление: heavy — от задачи
зависят другие, хоть одна зона попадает под фундамент (правила агентов,
промпты, CI, Docker, deploy, lock-файлы, схемы, контракты), задача касается
денег, ключей, доступов или личных данных, или у её требований есть
обязательный пользовательский поток; иначе standard (light — явно ограниченная
правка документации или оформления низкого риска). Объявленный класс ниже
вычисленного движок отклонит с причиной. Риск, найденный позже, — `promote-task`.

Режим задаёт только число ревью. `fast`: отдельный критик — только у задач с
деньгами, ключами, доступами, личными данными или обязательным пользовательским
потоком. `balanced`: критик у всех heavy. `max`: критик у каждой задачи и второй
свежий круг у heavy. Тестовый контракт с RED нужен heavy во всех режимах;
standard и light закрывает квитанция адресной проверки исполнителя.

### Модели и участники

Модель и усилие роли — по [таблице маршрутов](../references/model-routing.md);
класс исполнителя вычисляет движок. Для механической задачи
(`model_need: mechanical`), результат которой проверяет команда, объяви в плане
`scriptCheck` — строку этой команды: её закрытие требует квитанцию
`verify --task` с ней. Если утверждённой модели роли в среде нет, движок пишет
блокер `BLOCKED_MODEL_CAPABILITY`: другую модель не подставляй, независимую
работу продолжай. Не выдумывай модель или участника: агент создаётся
инструментом среды, затем его реальный native ID и session фиксируются при
назначении. Для общих фаз используй `participant`; одно native ID нельзя
представить независимым проверяющим под другой session. Токены считай через
`usage` и `usage-import` только по настоящим данным среды для всех ролей; байты
пакета не называй токенами. Если не все участники и вызовы покрыты, итоговую
стоимость помечай неполной.

`plan` карточек ролей не создаёт: карточка появляется при назначении роли
(`task-open` или `assign`) и пересоздаётся, только если изменился контракт
задачи. Критика назначай, только когда до него дошло; critic2 — только после
первого non-PASS. План может написать сам координатор; `plan --actor <id>`
сохранит действительного автора без второго учёта tokens. Сама критика и
независимая coverage остаются чужой проверкой.

### Повторная сдача плана

План с тем же содержимым и теми же входами (покрытие, сценарии, интерфейсы,
разбор размера) возвращает `unchanged: true` и ничего не пересобирает — не
повторяй его ради уверенности. Изменённый план пересобирает только задачи с
изменённым определением. После новых слов владельца, `brief` и повторного
`seal` сдай план заново: `plan` сам вернёт в работу задачи, у которых
изменились требования, и их потомков; отдельный `new-attempt` на каждую не
нужен. План, меняющий уже проверенную задачу без изменения её требований,
движок отклонит — тогда нужен `new-attempt` с цитатой владельца
([решение владельца](../references/owner-task-attempt.md)).
