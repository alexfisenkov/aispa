# Финал: проверка ветки, ремонт и слепая приёмка

Читай после [основного маршрута](../SKILL.md), когда все задачи плана
закрыты, заблокированы или отложены. Финал одинаков во всех режимах проверки;
режим меняет только число ревьюеров ветки. Сверок брифа по волнам нет: бриф
проверяют на входе (`seal`) и в слепой приёмке, команда `wave` отвечает отказом.
Непрерывность: в Codex, закрыв волну, в том же ходе открой следующую; ход
заканчивай только финалом, блокером или вопросом, который разрешает режим.

Порядок: проверка ветки по линзам → ремонт находок (если есть) → Git и
`handoff` → `clean-prepare` → `clean-verify` → `blind` → сопоставление →
при расхождениях ремонт и перепроверка только расходившихся пунктов.

## 1. Проверка всей ветки по линзам

`integration-review` без аргументов выдаёт контекст, форму и линзы режима:
`fast` — одна линза со всеми пятью осями, `balanced` — две, `max` — три. Каждой
линзе — свой свежий независимый `integration-reviewer` по
[его инструкции](../prompts/integration-reviewer.md): не исполнитель, не критик и
не приёмщик задач, не ревьюер другой линзы. Ревьюеров разных линз запускай
параллельно. Отчёт с полем `lens` сохраняй
`integration-review --file <отчёт> --actor <id>`. Ревьюер линзы `behavior`
разбирает накопленные предупреждения критиков (`findings`): подтверждает или
снимает с причиной. Собственные warning и блокирующие находки ревьюеров ветки
подтверждены сразу. Проверка ветки пройдена, когда записаны все линзы
кандидата и разобраны все предупреждения. Изменение кода отменяет её свежесть.

## 2. Ремонт находок

Если есть подтверждённые находки, все они чинятся одним ремонтом `final-repair`:
`final-repair open --file <выбор>` с `{"kind": "findings", "items": […], "zones": […]}`
(зоны — конкретные пути, не всё дерево), затем
`final-repair assign --role worker …` с реальными ID участника, исправление,
`final-repair submit --file <отчёт>`. Проверяет свежий участник, не автор
ремонта: `final-repair assign --role checker …` → `final-repair check --file …`
по diff между кандидатами и списку находок. Не больше двух кругов; неисправленное
уходит в остатки итога. Ремонт не меняет план и задачи.

## 3. Передача и чистый клон

Обычные документы передачи готовь внутри задач, чтобы их проверили вместе с
поведением: README, архитектуру, решения и словарь в объёме проекта. Исходный
бриф и приватные материалы не экспортируй. Сохрани проверенные код и документы
в Git, выполни свежий `verify --purpose check` текущего кода (не полный набор,
если его выполнит `clean-verify`) и `handoff --file …`. Затем `clean-prepare` и
`clean-verify -- <реальная установка, сборка и полный набор тестов>`: это
единственный полный прогон тестов финального кандидата.

Чистый клон точного commit не получает локальный `.env` и зависимости. Это
проверка исполнения в изоляции исходников, не security sandbox. Windows
clean-run выполняется нативно; локальный macOS/Linux PASS его не заменяет. Сверь
вывод, exit code, SHA, кандидата и актуальность квитанции. Exit code 0 не даёт
PASS при timeout, усечённом выводе, изменении клона или найденном секрете. Если
`clean-prepare` или `clean-verify` не удались (нет git, таймаут, ненулевой код),
квитанция называет причину, `blind` не открывается, прогон получает понятный
блокер, а цикл ремонта не расходуется: исправь окружение и повтори. Ручной
протокол помогает диагнозу, но не заменяет квитанцию движка.

## 4. Слепая приёмка

Итоговую приёмку проводит отдельный свежий проверяющий по
[acceptance](../prompts/acceptance.md), не участник задач и ремонтов. Сначала
дай ему только `context --kind blind --write`: исходные слова и чистый клон без
спецификации, реестра и каталога. Сохрани независимые наблюдения
`blind --file …`, затем выдай `context --kind acceptance --write` для
сопоставления с требованиями и сохрани `acceptance --file …`. Весь бриф
принимается отдельно. Приёмка проекта не заменяется приёмкой задач.

Проверяющий сам проходит обещанную цепочку: роль → запрошенные видимые
элементы → действие → результат → попытки запрещённых действий других ролей.
Контекст приёмки выдаёт контракт `productFlows` и формы; каждый passed поток
требует наблюдения `schema: 2`, `scope: final-product-flow` на текущем
кандидате, включая заявленные `placement`, `persistence` и `positiveCase`. Для
web-ui нужен browser с URL/viewport, native-ui проверяют на настоящей нативной
поверхности. Команда CLI не заменяет кнопку без отдельной цитаты решения
владельца. Пустая форма и общий smoke не подтверждают действие. Наблюдение о
заранее зафиксированном сроке связывается с записью
[обязательства исполнения](../references/execution-obligations.md). Если
независимый контекст недоступен, назови ограничение; не приписывай себе
независимость.

## 5. Ремонт расхождений и перепроверка

Если сопоставление не прошло, расхождение чинится: `final-repair open` с
`"kind": "blind"` берёт все расходившиеся пункты сразу, дальше тот же порядок
исполнителя и проверяющего, что в п. 2. После ремонта — новый чистый клон
(`clean-prepare`, `clean-verify`) и новый свежий приёмщик: он получает бриф и
дословные цитаты расходившихся пунктов, без спецификации и реестра, и
перепроверяет только расходившиеся пункты; отчёт `blind` несёт `recheckOf` и
`items`. Сопоставление берёт прежние наблюдения для совпавших пунктов и новые —
для перепроверенных. Ремонт расхождений — не больше двух циклов на прогон;
третий движок не откроет.

## 6. Исход

Приёмка прошла — переходи к [знаниям и итогу](06-continuity.md). Если оба цикла
ремонта израсходованы или чинить нечего (остались только несопоставленные
запросы или наблюдения без требования), `finish` сдаёт прогон со статусом
`delivered_with_remaining`: итог перечисляет расхождения, непройденные
обязательные пользовательские потоки и несопоставленные запросы. Пока хоть один
обязательный пользовательский поток не пройден, статус «принято» невозможно
получить ни в каком режиме — поток уходит в остатки, а не смягчается.
Отложенные задачи (`deferred`) называй в итоге поимённо: их критерии слепая
приёмка оценивает как невыполненные, они переходят в остатки следующего
прогона. Если отложена или заблокирована сама финальная задача, сдача
невозможна.

Сквозные интеграции проверяй на реальных стыках задач; успех одного модуля не
доказывает путь пользователя целиком. Тест с зелёным кодом возврата не
подтверждает сценарий, которого он не исполнял. Отдельно назови то, что
осталось без внешнего доступа или пользовательского испытания; не создавай для
этого фиктивный PASS. Не правь receipt, контрольные суммы или Journal вручную.
Точные поля — [contracts](../references/contracts.md).
