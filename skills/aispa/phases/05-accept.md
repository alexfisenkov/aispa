# Волна, документация и итоговая приёмка

Читай после [основного маршрута](../SKILL.md), когда задачи волны завершены.
После каждой промежуточной волны выполни общую проверку кода и отдельно сверь
**весь бриф** через [reviewer](../prompts/reviewer.md). Для последней волны
сначала выполни подготовку передачи по порядку ниже. Ни один PASS задачи не
подменяет сверку требований. Обнови адресные описания изменённых документов
через [маршрут документов](01-start.md).

Обычные документы передачи готовь **внутри задач**, чтобы требуемые критики и
приёмщик проверили их вместе с поведением: README, архитектуру, решения и
словарь в объёме, подходящем размеру проекта. Для маленькой работы допустимы
разделы одного README. Документы объясняют запуск, структуру, решения,
обязанности оператора, ограничения и открытые вопросы. Исходный бриф и
приватные материалы не экспортируй.

После проверенного завершения light и приёмки heavy последней волны
для light-финала получи `integration-review` без аргументов. Передай выданные
контекст и форму свежему независимому участнику `integration-reviewer` по
[его инструкции](../prompts/integration-reviewer.md), затем сохрани
`integration-review --file <report> --actor <id>`. Должны пройти все пять
осей общего обзора. Это обязательный барьер перед handoff/clean clone;
работник не проверяет собственную версию. Изменение кода отменяет свежесть
общего обзора. Для heavy его подтверждает штатный branchReview критика.

Сохрани уже проверенные код и документы
в Git. Выполни свежий `verify --purpose check` на текущем коде; затем
`handoff --file …` связывает tracked документы с подлинными receipts.
При `finalWaveReuse` и ровно одной завершённой задаче в одной волне переходи
сразу к чистому клону и итоговой blind-приёмке: отдельную `wave` перед ней
не запускай. Если все продуктовые критерии и исходные наблюдения пройдут,
`acceptance` создаст связанную с её отчётом последнюю контрольную точку.
При нескольких задачах, промежуточных волнах или старой политике отдельная
сверка последней волны по всему брифу обязательна. Исключение не позволяет
скрыть остаток продукта или `unmapped`; точные условия —
[contracts](../references/contracts.md#производная-последняя-сверка-волны).
Не запускай ещё одну общую verify после свежей сверки без изменения или
конкретного сомнения: каждый её receipt меняет basis, даже при прежнем SHA кода.
Если проверку нужно повторить, новый basis требует новой сверки — старый PASS
не переносится. При изменении файлов повтори затронутые приёмки, commit,
общую проверку и handoff с соблюдением лимита попытки. Точные поля:
[contracts](../references/contracts.md). Далее выполни `clean-prepare`,
`clean-verify -- <реальная установка/сборка/проверка>`.
Чистый клон точного commit не получает локальный `.env` и зависимости.
Это проверка исполнения в изоляции исходников, не security sandbox.
Windows clean-run выполняется нативно, а локальный macOS/Linux PASS его не
заменяет. Сверь вывод, exit code, SHA, candidate и актуальность receipt.
Даже exit code 0 не даёт PASS при timeout, усечённом выводе, редактировании
источника, изменении клона или обнаруженном секрете. Если автоматическая
подготовка чистого клона не запустилась, сохрани причину, проверь Git HEAD,
доступность Git/Python и отсутствующие зависимости внутри клона, исправь
окружение и повтори `clean-prepare`/`clean-verify`. Ручной протокол помогает
диагнозу, но не заменяет действительную квитанцию движка.

Сквозные интеграции проверяй на реальных стыках задач; успех одного модуля
не доказывает путь пользователя целиком. Перед итоговым PASS явно запиши
намерение теста, его источник, проверенный сценарий и границы покрытия.
Тест с зелёным кодом возврата не подтверждает сценарий, которого он не
исполнял. Проверь [отказные границы](../references/failure-checks.md): связь
с источником и заполненная декларация не доказывают исполнение теста.
Не расширяй заданный контракт ради выдуманного ошибочного сценария.
Отдельно назови то, что осталось без внешнего доступа или
пользовательского испытания; не создавай для этого фиктивный PASS.

Итоговую приёмку проводит отдельный проверяющий по
[acceptance](../prompts/acceptance.md). Сначала дай ему только
`context --kind blind --write`: исходные слова и чистый клон без реестра и
каталога. Сохрани независимые наблюдения через `blind --file …`, затем выдай
`context --kind acceptance --write` для сопоставления с требованиями.
Первоначальные blind-наблюдения должны сохраниться при этом сопоставлении.
Наблюдение о заранее зафиксированном сроке связывается с исходным SHA записи
[обязательства исполнения](../references/execution-obligations.md), без
смены цитаты или превращения продуктового FAIL в исключение. Срок движок
оценит только при фактическом `finish`; будущая отправка host остаётся pending.
Приёмка проекта не заменяется приёмкой задач. Если независимый контекст
недоступен, назови ограничение; не приписывай себе независимость.

Отрицательная проверка, изменённый код или неполная передача возвращают к
исправлению и повторению затронутых проверок. Не правь receipt, контрольные
суммы или Journal вручную. После успешной итоговой приёмки переходи к
[знаниям и итогу](06-continuity.md).
