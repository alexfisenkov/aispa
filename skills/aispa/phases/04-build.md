# Разработка и проверка задачи

Читай после [основного маршрута](../SKILL.md) для активной задачи. Готовые к
старту задачи независимы между собой: веди их подряд или параллельно, каждую
своим участником. Непрерывность: в Codex, закрыв волну, в том же ходе открой
следующую; ход заканчивай только финалом, блокером или вопросом, который
разрешает режим.

## Открыть задачу

Порядок для координатора: создай участника → `task-open` → передай пути.

1. Создай нативного участника доступным инструментом Codex, Claude Code или
   Cursor с моделью и усилием из [таблицы маршрутов](../references/model-routing.md)
   для класса роли (класс исполнителя движок вычисляет сам; запасной ход, если
   агента нет, — [адаптеры сред](../references/native-agents.md)).
2. `task-open T01 --role worker --runtime … --native-id … --session … --model …
   --reasoning …` с реальными ID из ответа среды. Для исполнителя команда
   делает пакет `context`, `start` (если задача ещё не running), `assign`,
   карточку роли и пакет роли; для критика — `assign`, карточку и пакет с
   формой. Start фиксирует начало реализации и её часы, поэтому работу
   участнику передавай только после ответа `task-open`.
3. Передай участнику пути `context`, `card` и (критику) `template` из ответа:
   передавай `context`, `card`, `template` по их `absolutePath` без перепечатки
   тел. Исполнителю — [worker](../prompts/worker.md), критикам —
   [task-critic](../prompts/task-critic.md).

Отдельные команды остаются допустимыми: `context --kind task --task T01 --role
worker --write` → `start T01 --context <basis>` до первой правки → `assign` →
`context … --role <роль> --write --with-template`. `context` и `template` только
пишут файлы: агента они не назначают и отчёт сами не сдают — это делают
`assign` и `task-close` (или `submit`). Assign фиксирует участника,
start — начало реализации и таймер; не заменяй одно другим. Если задача уже
running, не запускай её повторно. При отказе start сначала устрани указанную
зависимость или устаревший пакет.

Повторная `task-open` или `task-close` продолжает с упавшего шага: выполненные
шаги уже записаны своими событиями, повтор их пропускает (запущенную задачу не
стартует, назначенного участника не назначает). Ошибка называет шаг и причину:
устрани причину и повтори ту же команду. Повторный `discover` на тех же входах
ничего не записывает и отвечает `reused: true` — это не ошибка.

## Работа исполнителя

Исполнитель работает в объявленных зонах, не откатывая чужую работу, и гоняет
тесты своей зоны (`verify --task T01 -- <команда тестов зоны>`), а полный
набор — один раз в `clean-verify` финального кандидата: общий `verify` перед
handoff его не повторяет, если тот же код проверит `clean-verify`. Правило экономии:
то, что считается командой или скриптом, не отдаётся модели — форматирование,
сверку, раскладку файлов, подсчёт и сборку из канона делает команда, агента
зовут думать. Механическая задача со `scriptCheck` закрывается квитанцией
`verify --task` с командой из плана.

Heavy-задача: тестовый контракт → RED → реализация (GREEN) → адресная проверка
→ сдача. Standard и light: реализация → адресная проверка → сдача; их закрывает
квитанция `verify --task` исполнителя, тестовый контракт не обязателен. Выход
standard за свои зоны или в чувствительные пути отклоняется; при новом риске —
`promote-task T01 --reason …` и новый исполнитель по полной карточке.

Форму отчёта исполнитель получает после проверки: bundle с формой — только
после успешной адресной проверки (`template worker --task T01 --write`). Затем
`task-close T01 --role worker --file <отчёт> [--usage <лог>]`: команда делает
`submit` (после отказа критика — `repair`), `documents --refresh`,
`usage-import` и возвращает следующий шаг — роль этой задачи (`next.role`) или
список готовых к старту задач (`next.ready`).

Тестовый контракт heavy: до реализации `test-intent --task T01 --file …`. В
`behavior_change` новый тест с SHA сначала должен получить подлинный RED:
`verify --task T01 --purpose check -- <argv>` с ожидаемой ошибкой, затем
квитанция из `commands` в отчёте `test-intent`. После реализации — свежий
GREEN. Для документации, конфигурации, интеграции или уже существующего
поведения `not_applicable` требует отдельной конкретной причины и
файла-источника для **каждого** критерия. Если контракт опирается на проверку
до изменений, сними её квитанцию `verify --task` до первой правки и впиши
`prechangeExecution` в контракт до первой критики. После начала критики
допустима одна ревизия, которая только добавляет `prechangeExecution`; любая
другая правка контракта отклоняется.

Для `mixed` сохрани полный точный `criteria` и `routes` со строками
`{criterion,kind,reason,procedure,expected}`; маршруты `automated|browser|process`.
RED относится только к автоматической группе; если она пуста, укажи
`newTestFiles: []`, `redExecution: null`. Browser/process требуют фактических
наблюдений текущего кандидата по формам `observationTemplates` контекста, а в
отчётах всех ролей — полных `routeChecks`. Маршруты не удаляют и не понижают;
добавления разрешены до первой сдачи. При `errorBoundaryChecks` контракт
включает матрицу `failureChecks` по [отказным границам](../references/failure-checks.md);
форма — `template failure-checks --mode mixed`. Матрица сама не подтверждает
выполнение; нужны актуальные свидетельства.

## Критика

Роли задачи видны в пакете (`criticRoles`): их выбрал движок по режиму и
тяжести. Без критика задачу закрывает проверенная сдача исполнителя; не
создавай фиктивный PASS. С критиком: создай участника → `task-open T01 --role
critic1 …` → передай пути; критик читает `zoneChanges` целиком, `criteriaFiles` —
по необходимости, и сдаёт отчёт через `task-close T01 --role critic1 --file …`.

Блокирует только короткий список (`blockingClass`): `brief_drift` (в том числе
подмена заказанных кнопок командами), `broken_scenario`, `security`,
`data_loss`, `failing_tests`. Остальное — `warning`: копится в списке прогона
(`findings`) и чинится одним ремонтом перед финалом, задачу не держит. Отчёт с
одними warning — PASS, его PASS закрывает задачу, кроме heavy в `max` (ниже). Каждый критик явно
заполняет `verdict: PASS|WARN|BLOCK|FAIL`; неизвестный verdict и противоречивый
PASS отклоняются без расходования круга.

После блокирующего замечания установи причину до ремонта: пробел реализации
исправляет тот же worker; недостающий контекст или ошибочный подход — новый
worker с полным контекстом, точной находкой и обновлёнными источниками.
Сохрани диагностику `repair-plan T01 --file …`, после исправления повтори
адресную проверку и `task-close T01 --role worker …`. Второй **новый** критик
проверяет только изменения ремонта и блокирующие ID первого отчёта; его PASS
закрывает задачу. Не запускай и не назначай critic2 заранее. Любой non-PASS
второго критика блокирует задачу. В `max` у heavy второй свежий круг
обязателен и после PASS первого — по изменениям всей попытки.

Reset, replan, новое имя и новый прогон не обнуляют лимит. Новую попытку
открывают только новые слова владельца через `new-attempt`
([решение владельца](../references/owner-task-attempt.md)); не выпрашивай их.
Исключение — `max`: после non-PASS второго критика одна `extra-wave T01` (новая
попытка этой задачи с новым исполнителем, разрешена решением владельца 22.10).
Не прошла и она — задача `deferred`: остаётся `blocked`, её критерии уходят в
остатки, потомки стартуют без них (`deferredDependencies` в карточке). Не путай
с `defer` — переносом требования по цитате владельца.

## Смена режима

Смена режима — только по новым словам человека, в любой момент: запиши их
дословно в файл и выполни `check-mode <режим> --file <файл>`. Бриф не меняется,
фиксация не снимается, прогон не останавливается; запись видна на панели и в
итоге (`checkModeHistory`). Завершённые задачи и задачи с начатой критикой не
меняются. Смену режима по ходу не предлагай.

## Команды, расход и контекст

`verify` выполняет argv как реальный процесс; `clean-verify` — в подготовленном
клоне. Purpose `install|run|check|test` — по фактической цели. Каждый
выполненный запуск, включая неуспешный, получает квитанцию в `commands` с
точным argv, SHA вывода, кандидатом и временем. Не придумывай исполнение в
отчёте. Прошлый успешный запуск не даёт текущий PASS: при изменении кода
повтори команду.

После ответа среды сохраняй расход по реальному participant ID:
`usage-import --file <лог> --format codex|claude` (или `--usage` у
`task-close`). Отсутствие метрик не восполняй оценкой по байтам контекста.

Агент сохраняет полный JSON-отчёт в файл, в чат возвращает путь и не более
25 строк выводов. Каждый обязательный источник пакета читается целиком; для
крупного файла — частями с проверкой отсутствия обрезки. Читай доказательства
по конкретной находке, а не весь журнал. При неясном поле открой только нужный
раздел [contracts](../references/contracts.md). После задач переходи к
[сдаче](05-accept.md).
