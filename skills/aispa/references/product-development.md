# Идея, размер задач и знания по готовому коду · 0.2.0

Читай нужный раздел на соответствующем этапе. Разбор идеи выполняется до
фиксации брифа, проверка размера задач — перед планом, запись знаний — после
приёмки. Для них не требуется повторно загружать все инструкции навыка.
Команды ниже передаются закреплённому `tools/aispa.py --root <проект>`.

В alpha.10 до `seal` действует отдельная независимая карта полного исходного
текста, а после spec — сценарии каждой функции (по глубине: strict — main, error;
balanced — main, empty, error, persistence; deep и закреплённые прежние прогоны —
все восемь) и контракт её интерфейсов. Этот маршрут описан в [фазе продукта](../phases/02-product.md),
[фазе плана](../phases/03-plan.md) и [контрактах](contracts.md). Идея,
сценарии и интерфейсы связаны источниками, но не подменяют друг друга.
Новые policy применяются только к новым `init`, старые runtime не мигрируют.
Для idea и plan допустим исходный actor координатора без создания псевдоролей;
порядок и ограничения — [авторство фаз](runtimes.md#авторство-фаз).
Отдельный срок исполнения учитывается до seal по
[узкому контракту](execution-obligations.md); продуктовое ядро туда не переносят.

## До фиксации брифа: понять, какой результат нужен

Аналитик читает полные исходные слова и действующие требования. Сначала он
формулирует проблему, пользователя и наблюдаемый результат: что человек сможет
сделать и по какому признаку поймёт, что получилось. Затем сравнивает хотя бы
два подхода, включая простой существующий способ, и выбирает решение с учётом
всех ограничений владельца. Вариант, нарушающий обязательное требование, нельзя
принять ради удобства; полезно записать, почему он не подходит.

Проверяются 13 областей:

| Ключ | Что выяснить |
|---|---|
| problem | Какую конкретную проблему решаем и почему она важна |
| user | Кто пользуется результатом, в каких условиях и с какими ограничениями |
| outcome | Как выглядит успешное действие пользователя |
| alternatives | Какие способы решения сравнили и почему выбран текущий |
| small_test | Самый малый эксперимент, наблюдаемый результат и признак неудачи |
| contradictions | Противоречия между желаниями, ограничениями и выбранным способом |
| onboarding | Что нужно человеку для первого успешного действия |
| empty | Что видит пользователь без данных и как начинает работу |
| failure | Ошибки, отмена, повторное действие и восстановление |
| data | Происхождение, хранение, изменение и потеря данных |
| safety_access | Доступы, личные данные, опасные действия и границы полномочий |
| growth | Что изменится при росте данных, числа пользователей или нагрузки |
| return_visit | Что сохранится и как человек продолжит при следующем запуске |

Статус области — `assessed`, `unknown` или `not_applicable`. В `text` нужен
конкретный вывод либо причина неопределённости/неприменимости. Не заполняй
все строки одинаковым общим обещанием. Отсутствие данных о спросе честнее
выдуманного «рынок подтверждён». `sourceObservations` подтверждает содержание
источника, а не истинность любого вывода о мире.

Alpha.9 добавляет пять обязательных `challenge`: `adoption` (причина начать и
проверка идеи без пользователей), `value_cost` (измеримая польза против затрат),
`operations` (поставка данных и оператор), `lifecycle` (вторая неделя и
повторное использование), `actors` (другие участники, права и интересы).
Для каждого нужны `probe`, `status` (`resolved`, `assumption`, `blocker` или
`not_applicable`), `finding`, `decision`, `validation`, `requirements` с
действующими ID. `resolved` уместен только при действительном основании;
неизвестный спрос отмечай `assumption`. `not_applicable` требует конкретного
объяснения, а не одинакового N/A для удобства. Код проверяет полноту и форму,
но не удостоверяет рынок или качество вывода.

Глубину выбирает агент, обосновывая `depthReason`:

- `compact`: небольшая понятная доработка. Короткие выводы, до 480 символов
  на область, только действительно полезные предположения и добавления.
- `deep`: новая или неоднозначная идея, несколько пользовательских ролей,
  важные интеграции или последствия ошибки. До 1600 символов на область.

Оба режима требуют `assessed` для problem, user, outcome, alternatives и
small_test: компактность сокращает изложение, но не пропускает суть идеи.
Это означает «содержательно разобрано», а не «рыночный факт доказан»; допущения
внутри разбора остаются явными предположениями. Остальные области допускают
обоснованные unknown/not_applicable. Все требования сохраняются. Глубина не добавляет новый
опрос: `auto` принимает решения самостоятельно; `important` спрашивает о
существенных развилках, `interview` проходит все известные вопросы брифа,
включая влияющие на результат предпочтения. После
`seal` новые технические вопросы решаются агентом и попадают в решения/итог.
Неопределённость не даёт права снять обязательное требование. Если без доступа
или разрешённого внешнего действия результат недостижим, сохраняй препятствие
и продолжай независимые части.

### Запись и источники

```text
idea
idea --file .aispa/inbox/idea.json --actor <ID автора>
idea --full
```

`idea` возвращает текущий `basis`, список областей и краткое состояние.
`--full` нужен только для адресного чтения полного отчёта. По умолчанию вывод
ограничен 8000 символами, содержит ссылку на артефакт и счётчики `omitted`.
Пропуски представления не означают, что их разрешено потерять в спецификации.

Ниже пример формы для локального CLI планирования. Заменяй все заполнители
фактическими значениями текущего прогона; это не готовый отчёт чужого проекта.

```json
  ],

```

В `anchors` по одной точной цитате из каждого текущего брифа с его SHA.
`coverage` содержит каждое действующее требование ровно один раз: requested →
`outcome`, constraint → `constraint`, addition → `addition`. `proposal`
объясняет, как выбранный вариант сохранит требование. Совпадение ID проверяется
кодом; смысловое соответствие проверяют аналитик, проверяющий покрытия и критики.

Новые идеи записываются в `additions` как `{parent, text, rationale}`. Parent —
действующее исходное требование, не другое добавление. Этот список ничего сам
не добавляет в scope. Выбранную полезную функцию сначала зарегистрируй через
`requirements` с kind addition и core false; затем обнови разбор и спецификацию.
Невыбранные предложения остаются предложениями. Причины решений сохраняй через
`decision`; original requested/core не заменяй гипотезой аналитика.

При ссылках на изученный код добавь `collection` — точную квитанцию сохранённого
discoveryCollection, а в `sourceObservations` — строки формы:

```json
{
  "text": "README описывает локальный ввод; это ещё не доказательство поведения программы.",
  "sources": [{"path": "README.md", "sha256": "<SHA из коллекции>", "quote": "<точная цитата собранного фрагмента>"}]
}
```

Коллекция проверяется по происхождению, цитируемые файлы — по текущим SHA.
Изменение брифа, требований или этих файлов требует нового разбора перед
seal/spec. `sealed` и вычисленный список core сами по себе основание не меняют.
Отчёт ограничен 48 000 символами JSON; неизвестные поля отклоняются. Новая запись
добавляет артефакт и `ideaHistory`, не переписывает прежние источники.

## Перед планом: проверяемый результат вместо россыпи мелких действий

Сначала составь черновик с полным покрытием требований и зависимостями:

```text
plan-check --file .aispa/inbox/plan-draft.json
plan --file .aispa/inbox/plan.json --review .aispa/inbox/plan-review.json --actor <ID автора>
```

Plan-check ничего не меняет. Он возвращает `basis`, нормализованный `draft` и
`suggestions`. Подсказки рассматривают соседние связанные задачи, если хотя бы
у одной меньше трёх критериев; high-risk и уже прошедшие критику задачи не
получают такую подсказку. Это повод проверить границу, не команда объединить
всё или искусственно добавить критерии.

Объединяй части одного результата, когда исполнитель может удержать их контекст
и единая проверка остаётся понятной. Разделяй самостоятельные результаты,
независимые риски, разные доступы и слишком большие области чтения. Критерий
экономии — меньше повторных передач контекста при той же полноте проверки.

Отчёт сохраняет исходный `draft` из plan-check без изменений. Пример оболочки
для двух объединённых задач; вместо пустого draft подставь полный полученный
массив, а в `delivery` — точный criterion итоговой задачи. Пустой draft
валидатор не принимает:

```json
{
  "basis": "<из plan-check>",
  "draft": [],
  "groups": [
    {"task": "T01", "from": ["T01", "T02"], "reason": "Ввод и его валидация образуют один пользовательский сценарий с общей проверкой."}
  ],
  "separate": [],
  "delivery": {
    "profile": "small", "reason": "Один локальный пользователь и одна функция.",
    "slices": [{"id": "S01", "kind": "user", "outcome": "Пользователь получает план без пересечений.", "tasks": ["T01"], "demonstration": {"task": "T01", "criterion": "План без пересечений"}, "supports": []}],
    "migrations": [], "migrationReason": "Нет прежнего формата и потребителей для переноса."
  }
}
```

Если подсказка `T01+T02` рассмотрена, но задачи оставлены раздельными, группы
будут `T01 ← [T01]`, `T02 ← [T02]`, а `separate` содержит:

```json
{"suggestion": "T01+T02", "reason": "Вторая задача меняет отдельный формат хранения и требует самостоятельного сценария миграции."}
```

Каждая исходная задача входит ровно в одну группу. Объединённая группа должна
быть связной по зависимостям, общим продуктовым требованиям или зонам. Итоговые
requirements, zones и readZones — точные объединения исходных наборов.
Каждый исходный критерий сохраняется отдельно. Если у объединяемых задач
совпал текст, в итоговом criteria нужны обе строки с исходными ID:

```json
["T01: Ошибочный ввод отклоняется", "T02: Ошибочный ввод отклоняется"]
```

Остальные критерии переносятся дословно. Одинаковые подписи не означают одну
проверку: префикс сохраняет происхождение каждого условия. Итоговый riskReason
содержит все непустые исходные обоснования дословно; их можно соединить в один текст.
Внешние зависимости пересчитываются через группы без потери или добавления;
внутренние исчезают как отдельные рёбра. Риск нельзя понизить. При необходимости
изменить сам объём сначала обнови исходный черновик, а не маскируй это укрупнением.

Новый план и запуск задач требуют актуального planReview. Ни переименование,
ни объединение не сбрасывает использованные попытки и раунды критики.
В lean и adaptive поле `taskRoleStarts` равно null при диапазоне; при совпадении
минимума и максимума оно содержит точную плановую оценку, не реальный usage.
`taskRoleSlots` содержит
`minimum: (light + standard) + 2 × heavy`, `maximum: (light + standard) + 3 × heavy`
в lean и `3 × heavy` / `4 × heavy` в adaptive; у plan review это
`taskRoleSlotsBefore/After`. Общий обзор light- или standard-финала учитывается отдельно.
Классификация — [task-tiers.md](task-tiers.md). У heavy lean первый PASS критика
закрывает задачу (в закреплённом adaptive ведёт к отдельному acceptor),
WARN/BLOCK/FAIL — к ремонту и свежему critic2. Предел — два раунда.
Legacy сохраняет четыре ролевых места. Это оценка назначений, не фактическое
число native-запусков или измерение токенов; замена исполнителя ремонта
может добавить участника сверх оценки.

`delivery` новых прогонов содержит профиль `small|feature|system|migration`,
причину выбора глубины, непустые `slices`, `migrations` и содержательную
`migrationReason` при пустом списке. Каждый срез имеет `id`, `kind: user|enabler`,
наблюдаемый `outcome`, непересекающиеся `tasks`, демонстрацию
`{task, criterion}` из задачи и `supports`. Каждая задача входит ровно в один
срез; нужен хотя бы один пользовательский. Срез-enabler указывает, какие
пользовательские срезы он обеспечивает. Это план доставки, а не утверждение,
что интерфейс уже существует.

Для действительной миграции каждая строка содержит `id`, `reason`, непустые
раздельные списки задач `expand`, `migrate`, `contract`, список потребителей
`{path, task}`, а также `compatibility` и `rollback` как списки
`{task, criterion}`. Критерии compatibility и rollback одного шага различны.
Каждая задача migrate должна перенести известного
потребителя в своей зоне записи. Все migrate зависят от всех expand, все
contract — от всех migrate. Проверки совместимости и восстановления покрывают
каждый шаг. `profile: migration` требует хотя бы одну миграцию; для других
профилей пустой список допустим с конкретной причиной. Движок проверяет
структуру и зависимости; он не удостоверяет, что перечислены все реальные
потребители. Их ищет координатор по коду и контрактам.

Ошибочные сценарии связывай с исходными критериями и тестами по
[карте отказных границ](failure-checks.md). Заполненная декларация не означает
исполнения или достаточности теста; не придумывай поддержку вне заданного
контракта ради формального покрытия границы.

## После приёмки: сохранить проверенные знания о реализации

После успешной актуальной acceptance создай нового независимого автора знаний.
Передай [knowledge-writer.md](../prompts/knowledge-writer.md) и только пакет
готового кода; прежний исполнитель, критик и итоговый приёмщик эту роль не занимают.

```text
knowledge-assign --runtime codex --native-id <реальный-ID> --session <реальная-сессия>
context --kind knowledge --write
knowledge-record --file .aispa/inbox/knowledge.json
knowledge --path src/planner.py --kind trap --limit 4
```

Вход отчёта: `basis` — снимок кода из writer-пакета, `writer` — назначенный
внутренний ID, `entries` и `uncertainties`. Каждая запись содержит стабильный
key, kind, text и точные относительные sources с SHA прочитанных файлов.
Пример для одной установленной особенности; значения SHA и basis берутся
из текущих источников, а не копируются из примера:

```json
{
  "basis": "<снимок кода из knowledge-пакета>",
  "writer": "<ID назначенного автора>",
  "entries": [
    {"key": "planner.empty-input", "kind": "trap", "text": "Пустой файл должен обрабатываться до вычисления расписания; путь ошибки проверяется отдельным тестом.", "sources": [{"path": "src/planner.py", "sha256": "<SHA кода>"}, {"path": "tests/test_planner.py", "sha256": "<SHA теста>"}]}
  ],
  "uncertainties": {
    "command": "Подходящее актуальное свидетельство команды не включено в эту запись.",
    "decision": "Причина выбора алгоритма не зафиксирована в доступном источнике.",
    "glossary": "Специальных терминов, требующих отдельного пояснения, не обнаружено."
  }
}
```

Четыре вида знаний: `command` — действительно выполненная проверка, `trap` —
существенный крайний случай или ловушка, `decision` — причина технического
решения, `glossary` — значение предметного термина. Для каждой категории нужна
хотя бы одна полезная запись либо конкретная причина в uncertainties. Не
изобретай термины и ловушки ради количества; все четыре причины допустимы,
если изучение не дало переносимых знаний.

Для command дополнительно нужны точный массив argv `command` и ссылка
`verification: {kind: "execution", sha256: "<SHA записи commands>"}` (можно
добавить `id`). Выбери подлинный успешный запуск текущего прогона из
`commands --purpose … --limit …`; `commands --receipt <SHA>` показывает
точную запись без выдуманного argv. Не копируй в публичный документ полный
реестр или локальные пути. Для старых прогонов сохраняются свидетельства
`kind: project|cleanrun` с digest текущего receipt. Команда из README без
успешного подлинного запуска не подходит. Исторический source candidate может
отличаться от текущего: evidence отмечает `currentAtCuration: false`, а
актуальная итоговая приёмка и общая проверка всё равно обязательны.

Автор читает фактические источники и результаты проверок; намерения плана не
выдаются за свойства готового кода. Секретные, игнорируемые и недопустимые файлы
не используются. Не включай абсолютные личные пути, доступы или чужую переписку
в текст записей. В одном отчёте до 32 записей; один артефакт ограничен 1 MiB.
Локально между контрольными снимками допускается до 64 отчётов автора знаний.
При достижении этого лимита выполни `knowledge-compact`, затем повтори запись.
Если артефакт приближается к пределу размера, делай снимок раньше.

Повторная запись с тем же key заменяет действующее знание через `supersedes`,
сохраняя прошлое в истории; вид знания не меняется молча. При новом init
контрольный снимок создаётся автоматически: рабочий набор содержит до 128
записей и 512 KiB их сериализованного содержимого, остальное
доступно через неизменный архив. Команда `knowledge-compact` делает такой
снимок внутри активного прогона. Исходные отчёты, карточки авторов, вывод
проверок и цепочка архивов сохраняются; старые каталоги прогонов нужны для
проверки происхождения. Компактизация сама не создаёт новую приёмку или знание.

Query требует явный `--path` или `--kind`: без них записи не подгружаются.
Обычный запрос рассматривает текущий рабочий набор без обхода архива.
По умолчанию до 8 записей и
6000 символов их текста JSON; `--limit` допускает 1–24. Если изменился хоть
один источник, знание исключается и учитывается в `omitted.stale`. Прежняя
редакция того же key не возвращается взамен устаревшей новой.

```text
knowledge-compact
knowledge-record --file .aispa/inbox/knowledge.json
knowledge --path src/planner.py --kind trap --archive --archive-depth 4
```

`--archive` включает ограниченный адресный поиск по прежним снимкам.
`--archive-depth` допускает 1–64, по умолчанию 4. Если дальше осталась история,
`archive.unread` содержит точную ссылку на следующий непрочитанный архив;
это явная неполнота поиска. `archive.archivedRecordCount` считает сохранённые
отчёты автора знаний, а не уникальные знания. Ни глубина поиска, ни счётчик
не разрешают выдавать старую команду за текущий PASS.

Адресный пакет задачи может содержать до четырёх коротких релевантных подсказок.
Blind-приёмщик их не получает. Подсказка помогает выбрать чтение, но не заменяет
текущий источник, тест или приёмку. Перед заявлением об успешной команде её
выполняют заново. `finish` требует актуальную запись знаний этого прогона;
сама запись знаний успешную приёмку не создаёт.
