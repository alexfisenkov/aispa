# Проверка отказных границ

Новая политика `errorBoundaryChecks` требует в `test-intent` краткую карту
ошибок. Это план реальных проверок, не ещё один текстовый PASS. Получи
`template failure-checks` и добавь объект `failureChecks` в обычный отчёт
test-intent. Старые закреплённые прогоны используют прежний контракт.

Нужно разобрать пять границ: `input`, `output`, `storage`, `protocol`,
`dependency`. Для применимой границы укажи конкретные сценарии, ожидаемый
результат, точный критерий задачи и тестовый файл с SHA. В режиме
`behavior_change` это один из объявленных `newTestFiles`, проверенных RED.
Для неприменимых границ допустима одна сгруппированная причина с неизменным
источником. Не объявляй границу отсутствующей по одному размеру проекта.

```json
{
  "failureChecks": {
    "cases": [{
      "id": "E01",
      "boundary": "output",
      "scenario": "Разрешённая команда получает настоящий отказ записи результата",
      "expected": "Требуемый код ошибки; старый файл и вход сохранены; временный файл убран",
      "criterion": "ТОЧНЫЙ КРИТЕРИЙ ИЗ ЗАДАЧИ",
      "test": {"path": "tests/test_output.py", "sha256": "SHA ПРОЧИТАННОГО ТЕСТА"}
    }],
    "notApplicable": [{
      "boundaries": ["protocol", "dependency"],
      "reason": "Конкретный исходный контракт не содержит протокола или внешних зависимостей",
      "source": {"path": "BRIEF.md", "sha256": "SHA ИСХОДНИКА"}
    }]
  }
}
```

Это неполный пример: `input` и `storage` ещё нужно разобрать. Движок требует
полное непересекающееся покрытие пяти границ, уникальные ID и действительные
SHA. Пустая заготовка, неизвестная граница, чужой критерий и фиктивный
`passed: true` отклоняются. Изменение тестового/опорного источника требует
актуализации намерения и затронутых доказательств, а не замены SHA в журнале.

## Что проверять по применимости

- Ввод: не только корректный пример, но неверные типы/кодировка, пустое
  значение, пограничное допустимое значение и ошибка после корректных данных.
- Вывод: настоящий отказ записи/закрытия/flush, а не только mock создания
  файла; stdout и путь вывода отдельно, если оба поддерживаются. Проверяй
  фактический exit code процесса и его окончательный stderr, включая flush
  интерпретатора после возвращения main. Один тест broken pipe не покрывает
  все причины OSError. На POSIX можно ограничить размер файла только дочернего
  процесса; отсутствие такого механизма на другой ОС — ограничение проверки.
- Хранение: отказ посреди изменения, rollback, сохранение прежних байтов,
  очистка временного файла, перезапуск и изоляция экземпляров по контракту.
  Для атомарного вывода используй также допустимое длинное имя назначения:
  сначала подтверди, что сама файловая система позволяет создать этот путь.
- Протокол: точная схема/заголовки/код ответа в объявленном диапазоне запросов,
  в том числе отказ парсера до обычного обработчика. Если контракт требует
  формат всех ответов об ошибке, проверь эту границу явно; не изобретай
  поддержку транспортов или версий вне заданного scope.
- Зависимости: отсутствие нужного ресурса, timeout и честный fallback,
  если такие зависимости есть. Недоступная инфраструктура не становится
  успешной проверкой или доказанным дефектом продукта автоматически.

## Роли и доказательства

Исполнитель сохраняет сценарии и тестовые источники до реализации. После
реализации он выполняет GREEN и показывает, какие случаи эта команда реально
исполняет. Критик читает `failureChecks`, тесты и receipts, воспроизводит
применимые отказы и проверяет, что тесты проверяют требуемый результат.
Особенно важны сохранность данных, код процесса и отсутствие лишнего вывода.
Недостающая обязательная проверка получает WARN/BLOCK с конкретной находкой,
а не PASS по общему зелёному exit code.

Схема доказывает связь с исходниками и полноту декларации границ. Она сама
не доказывает качество теста, его выполнение конкретной командой или отсутствие
неучтённой ошибки. Это остаётся задачей независимого критика (в закреплённых
adaptive/legacy — и приёмщика).
