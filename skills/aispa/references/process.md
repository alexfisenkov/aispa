# Выполнение AISpa

Команды ниже вызываются как `python3 <skillDir>/tools/aispa.py --root <repo> …`.
Все пути с пробелами заключай в кавычки. `<skillDir>` — папка открытого навыка.
После `init` используй сохранённую копию
`.aispa/runs/<run>/runtime/tools/aispa.py`. Это закрепляет инструкции и движок
на время прогона. Статус содержит `run` и `runDirectory`.

## 1. Подготовка

Выбери режим по SKILL.md. Изучи существующий код и правила проекта. Создавай
новый Git-репозиторий только если это действительно новый проект. Рабочая
альфа требует обычного корня Git и пока не поддерживает submodules.

```text
init --slug example --title "Название проекта" --mode important
```

`init` создаёт локальный журнал, копию движка и временный экран состояния;
добавляет `.aispa/` в `.gitignore`. Этот каталог может содержать частный бриф,
поэтому автоматически в публичный Git не отправляется. Код проекта и
обезличенные инженерные решения сохраняй отдельными коммитами по его правилам.

Дашборд запускается отдельным процессом командой `serve --port 0`.
Она печатает URL и слушает только `127.0.0.1`. Открой точный выданный адрес.
Падение дашборда не меняет результат проверок. `status` пересчитывает его данные.

## 2. Бриф

`brief --file .aispa/inbox/brief.md` записывает полный исходник и возвращает
ID `B001`. Каждый ответ и уточнение добавляй новым `brief`; не исправляй
предыдущие сохранённые файлы. В режиме auto сразу извлекай требования;
в остальных сначала закончи вопросы соответствующей глубины.

Составь атомарные требования с цитатами, проверяемыми критериями и признаком
`core`. Не только функции: сроки, запреты, поведение интерфейса и ограничения
данных тоже учитываются. Общие ограничения отмечай `kind: constraint` и
передавай всем исполнителям. Номер не должен исчезнуть из реестра.

`requirements --file …` добавляет записи. Повторное использование ID запрещено.
Покажи пользователю ядро и границы одним понятным сообщением; дополнительного
согласования этапов не требуй. `seal` фиксирует ядро и закрывает брифинг.
Далее решения принимаешь сам и записываешь через `decision "…"`.

Новая команда владельца по ходу работы становится новым `brief`, затем
новыми требованиями и повторной проверкой затронутого плана. Вопросы заново
не открывай, если владелец не попросил об этом. Для изменения или отмены
старого требования нужна точная цитата нового решения:

```text
scope R02 drop --brief B002 --quote "Экспорт больше не нужен"
```

Техническая невозможность не даёт права выполнить эту команду. `defer` также
требует решения владельца. Удаление записей вручную запрещено.

## 3. Спецификация и план

Составь спецификацию: пользовательские сценарии, границы модулей, данные,
ошибки, интеграции, способы проверки. `spec --file …` сохраняет снимок.
Полезные новые функции учитывай как `kind: addition` с родителем. Их добавление
обновляет контракт: повтори `seal` и сверку спецификации.

Получи `context --kind coverage`. Новый независимый проверяющий сначала
выделяет требования из полных брифов, затем сравнивает их со спецификацией
и реестром. Отдельно ищет то, чего вообще нет в реестре (`unmapped`).
Запиши его результат через `coverage --file …`. Код 2 означает отказ,
а не успешное продолжение. Исправь расхождения и повтори проверку.

План — JSON задач. `plan --file …` проверяет покрытие всех действующих
требований, зависимости и зоны, вычисляет волны. Ничего не запускай на
невалидном плане. Сначала задачи исходного брифа, потом самостоятельные
дополнения. Плановые изменения возвращают изменённые задачи в pending.

## 4. Разработка

Перед запуском задачи прочитай её цитаты и все ограничения, получи
`context --kind task --task T01`, затем `start T01 --context <basis>`.
Передай исполнителю этот пакет, требования, спецификацию, исходные цитаты,
общие ограничения и prompt worker. Проверяй его изменения по зоне.

После реализации выполни реальную команду проверки:

```text
verify -- python3 -m unittest discover -s tests -v
```

Движок записывает фактический код завершения, вывод и состояние кода до/после.
Не подменяй проверку командой `true`, `echo` или тестом, подтверждающим сам себя.
Код 0 — лишь одно свидетельство; нужны проверки всех критериев и сценария.

После проверки снова получи context задачи и создай отчёт по каждому критерию.
`complete T01 --file …` принимает только полный успешный отчёт с файлами
доказательств. Недостающий доступ: `block T01 --note "…"`; требование остаётся.
Продолжай независимые задачи. Для исправления завершённой задачи используй
`reset T01`: её зависимые задачи также теряют завершённость.

Когда все задачи волны завершены или явно заблокированы, отдельный проверяющий
сверяет весь бриф: `context --kind wave`, затем `wave 1 --file …`.
Будущие требования могут быть `not_tested`; выполненные задачи не должны
противоречить брифу. Без сверки предыдущей волны следующая не открывается.

## 5. Приёмка

Сохрани изменения кода и документации в Git. Выполни итоговую команду проверки,
затем обнови сверку последней волны. Получи `context --kind acceptance`.
Независимый проверяющий запускает продукт и проверяет все критерии брифа.
Его отдельное первоначальное чтение брифа не должно быть заменено отчётом
исполнителя. Подробнее — prompt acceptance.

`acceptance --file …` принимает ядро только с положительными проверками.
Файл проверки должен перечислять также все второстепенные требования —
успешные, непроверенные и заблокированные. Они не исчезают ради зелёного статуса.
`finish` дополнительно проверяет свежесть доказательств, завершённость задач
ядра и чистоту Git. Наличие второстепенных остатков меняет формулировку сдачи.

Если ядро не работает, исправляй. При непреодолимом препятствии выполняй
`close blocked --note "…"` и показывай доступный результат с точным ограничением.
`close paused` — только по просьбе владельца. Новый запуск для пересмотра
решений начинается с `resume`, чтения истории и дополнений к брифу.
