# Выполнение AISpa · 0.2.0

Новые `init` 0.1.0 добавляют `taskTiers` к прежним обязательствам:
light и standard проходят worker → проверка → submit → verified completion, без
отдельных критиков и приёмщика задачи; heavy в новых прогонах идёт через
worker → critic1 (условный critic2) без отдельного приёмщика.
См. [классы задач](task-tiers.md). Ранее введены
`sourceAccounting`, `designContract`, `allRoleUsage`, `integrationReview`,
`testIntent`. Старый активный прогон
продолжают его закреплённым runtime и контрактом; обновление пакета не
вкладывает новые обязательные поля в прежний Journal задним числом.

Команды ниже вызываются как `python3 "<skillDir>/tools/aispa.py" --root "<repo>" …`.
`<skillDir>` — именно открытая папка навыка, `<repo>` — физический корень Git.
На Windows замени python3 на выбранный python.exe/py -3; примеры PowerShell
и UTF-8 — [runtimes.md](runtimes.md).
После init все команды прогона выполняй сохранённым
`.aispa/runs/<run>/runtime/tools/aispa.py`. Для обновления установленного навыка
нужен его исходный каталог, а не закреплённый runtime.

## 1. Проверка обновления и подготовка

Первое действие при явном вызове — `update-check`. Источник — опубликованные
Releases `alexfisenkov/aispa`; main, tags без Release и drafts не подходят.
Если доступен новый выпуск и установка разрешена, выполни `update-prepare`.
До выбора пользователя пакет не меняется. Покажи подготовленный diff и
предложи установить либо продолжить текущую версию. Только после выбора
установки: `update-apply --candidate <candidateId> --confirm`.
Недоступность сети, выпуска или безопасной установки не блокирует текущую
версию. Автоматической установки и миграции активного прогона нет.

Выбери режим по SKILL.md. Найди действующие правила и исходники проекта.
Проверь Git, Python 3.11+ и доступность нативных агентов. Новый Git-репозиторий
создавай только для действительно нового проекта. Git submodules не поддержаны.

```text
init --slug example --title "Название проекта" --mode important --runtime codex --check balanced --depth balanced
```

Среду указывай по фактическому host. Инициализация сохраняет журнал и копию
пакета, добавляет `.aispa/` в `.gitignore`, инвентаризирует существующие файлы.
Depth выбирается из `strict|balanced|deep` и задаёт глубину сценариев, но не
разрешает терять исходный текст или пропускать проверки выбранной политики.
Новый init закрепляет `policy.leanControl`; попытка и карточки получают
`reviewPolicy: lean`. Критик проверяет и то, что раньше проверял приёмщик, и
его строгий PASS сразу закрывает задачу; WARN/BLOCK/FAIL ведёт к ремонту и
свежему второму критику, чей PASS закрывает задачу. Максимум два раунда.
Закреплённые adaptive-попытки ведут PASS к отдельному приёмщику; старые
попытки без поля политики сохраняют legacy `two_rounds` и требуют двух
критиков и приёмщика. Изменение политики прогона не меняет их задним числом.
Ссылки на контекст добавляются в AGENTS.md; для Codex также в существующий
AGENTS.override.md, для Claude Code — в CLAUDE.md, для Cursor — в собственный
`.cursor/rules/aispa.mdc`. Чужие правила и структура не заменяются.
Изменённые существующие правила сохраняются в `.aispa/backups/`.

Если подготовка контекста оборвалась на конфликте правил, исправь именно
конфликт с сохранением пользовательского текста и повтори
`project-context --runtime <среда>` закреплённым движком. Не повторяй init
поверх активного прогона. `context-refresh` восстанавливает производные
документы без изменения корневых правил. Обычные записи журнала обновляют
контекст автоматически.

`.aispa/context/INDEX.md` связывает brief.md, spec.md, plan.md, decisions.md,
progress.md, memory.md, requirements.json и source-map.json. Журнал и
неизменные источники остаются каноном. Короткая память ограничена по размеру;
полные сведения доступны по ссылкам. Частные исходники не отправляй в Git.
Корневые инструкции с новыми ссылками включи в обычную проверку и коммит проекта.

`dashboard start` поднимает локальный экран или возвращает уже действующий
сервер; `dashboard status` и `dashboard stop` управляют этим экземпляром.
`dashboard archive` сохраняет явно исторический снимок без опроса и часов.
Старый `serve --port 0` остаётся передним планом для ручной диагностики.
Дашборд отображает журнал, не определяет приёмку.

`batch --file steps.json` выполняет список до 25 шагов-argv (без `--root` и
`--compact`) по очереди; у каждого шага своё событие журнала и краткая квитанция,
на первой ошибке пакет останавливается. Запрещены init, update-*, serve,
dashboard, resume, seal, journal-recover и вложенный batch. Подходит для шагов, которые не
зависят от ответа друг друга.

## 2. Изучение проекта и память между запусками

`memory` показывает унаследованную историю. При новом init предыдущие
принятые/сданные с остатками/отменённые прогоны образуют handoff с происхождением.
Активный, заблокированный или приостановленный прогон продолжается через resume;
новый init не скрывает его. Прежние PASS не подтверждают текущий код.

```text
discover --include src/domain.py --include tests/test_domain.py
discover --file .aispa/inbox/project-study.json
discovery
```

Первая команда возвращает путь к ограниченному набору исходных свидетельств.
Исследователь читает источники и составляет отчёт по семи областям, затем
вторая команда проверяет происхождение и сохраняет заметки. Include можно
повторять; секретные, игнорируемые и символические ссылки не допускаются.
При повторном collect без include сохраняется прежняя адресная выборка.
Полные источники прочитываются адресно, если фрагмента недостаточно; пропуски
сборщика не выдаются за изученный код. Команды из документов не исполняются
автоматически. Подробнее — [continuity.md](continuity.md).

Старое обязательство, вновь порученное владельцем, сопоставляется до плана:
`carry <C-id> --action map --requirement R01 --brief B001 --quote "Новая команда"`.
Текст, вид, ядро и критерии прежнего требования не ослабляются. После новой
приёмки задач: `carry <C-id> --action resolve`. Keep оставляет пункт открытым;
drop/defer требуют нового источника владельца. Незакрытые старые пункты
попадают в остатки финального ответа даже вне текущего объёма.

## 3. Бриф, ядро и спецификация

Новые прогоны требуют в `idea --file` пять `challenge`: adoption,
value_cost, operations, lifecycle, actors. В `auto` аналитик самостоятельно
помечает факты и гипотезы; `important`/`interview` задают существенные
вопросы только до `seal`. После `seal` самостоятельное решение записывается,
но обязательное ядро не уменьшается. Независимый `coverage` добавляет
`ideaChecks` с цитатами решений/неопределённостей из текущего spec.

`brief --file .aispa/inbox/brief.md` сохраняет полный источник. ID B001 и
последующие бери из журнала/контекста. Уточнения добавляй отдельными источниками.
Входные файлы держи в `.aispa/inbox/`, чтобы не менять проверяемый код.

`requirements --file …` добавляет атомарные требования с дословными цитатами,
условиями приёмки и признаком core. Общие запреты — kind constraint.
До `seal` независимый учёт исходного текста обязателен:

```text
participant --role brief-analyst --runtime codex --native-id <ID> --session <session>
participant --role brief-reviewer --runtime codex --native-id <другой-ID> --session <другая-session>
brief-source --write
template brief-extract --actor <ID аналитика> --write
brief-extract --file <absolutePath заполненной формы аналитика>
template brief-review --actor <ID проверяющего> --write
brief-review --file <absolutePath заполненной формы проверяющего>
brief-map-context --write
template brief-map --actor <ID проверяющего> --write
brief-map --file <absolutePath заполненной карты>
```

`template --write` сохраняет форму с пустыми смысловыми полями и возвращает
её `absolutePath`; участник заполняет файл сам, без перепечатки координатором.
Аналитик и проверяющий независимо читают полный `brief-source`; проверяющий
не получает разбор аналитика или требования до своего сохранённого отчёта.
Только после обоих разборов он открывает `brief-map-context`. Карта связывает **каждый** исходный фрагмент с действующим
требованием или помечает контекст/расхождение. Только согласованная полная
карта пропускает `seal`; хеши и позиции не удостоверяют смысл.
До фиксации брифа выполни разбор идеи по [product-development.md](product-development.md):

```text
idea
idea --file .aispa/inbox/idea.json
seal
```

Первая команда возвращает текущее основание и состояние разбора. Аналитик
сохраняет исходные намерения, варианты решения, предположения и малый эксперимент;
вторая проверяет цитаты, полноту областей и связь со всеми требованиями.
Небольшая задача получает compact, сложный продукт — deep с обоснованием.
В auto дополнительных вопросов нет; important/interview работают только до seal.
Покажи ядро и границы одним сообщением. Вопросы по обычным
техническим решениям после этого не задавай, решения сохраняй через decision.

Новая команда владельца становится новым brief и требует пересверки контракта.
Для снятия, переноса или восстановления требования нужен источник решения:

```text
scope R02 drop --brief B002 --quote "Экспорт больше не нужен"
```

Составь спецификацию со сценариями, данными, ошибками и способами проверки.
Перенеси в неё решения из разбора идеи; выбранные дополнительные функции
сначала внеси отдельными addition, затем обнови idea и seal. Новые слова или
изменённые требования делают предыдущий разбор неактуальным. Свежий разбор
обязателен перед seal/spec нового прогона. Сохрани спецификацию командой
`spec --file …`. Получи `context --kind coverage --write` и передай полные
источники независимому проверяющему. Он ищет также потерянное вне реестра
(unmapped). `coverage --file …` записывает его отчёт; код 2 означает отказ.

## 4. План и карточки команды

Отчёт `plan --review` новых прогонов включает `delivery`: завершённые
проверяемые пользовательские срезы и, где нужна миграция, последовательность
expand → migrate всех известных потребителей → contract с зависимостями,
совместимостью и откатом. Объясни пустой список миграций предметно.
Схема — [contracts](contracts.md); проверка структуры не находит потребителей
сама, их надо установить по проекту.

После `spec` и `coverage` до `plan` выполни `template scenarios --write`.
В файле по `absolutePath` заполни измерения каждой действующей функции по глубине
(strict: main, error; balanced: main, empty, error, persistence; deep: все восемь;
закреплённые прежние прогоны требуют все восемь) и сохрани `scenarios --file …`.
Следом `template interfaces --write` → заполнение файла → `interfaces --file …` закрепляет сигнатуры,
зоны владельца и потребителей, тестовые швы и ссылки на материалы. Сценарии
не позволяют заменить исходную функцию инициативой агента; план должен
связать владельца интерфейса с задачей, а потребителей — с её зависимостями.
`preparation` показывает актуальность этих источников.

Сначала проверь размер задач, затем запиши итог с явным разбором границ:

```text
plan-check --file .aispa/inbox/plan-draft.json
plan --file .aispa/inbox/plan.json --review .aispa/inbox/plan-review.json
```

Координатор рассматривает связанные мелкие задачи: объединяет их в законченный
результат либо объясняет самостоятельный риск, зависимость или другой смысл границы.
Подсказка о менее чем трёх критериях — эвристика, не требование раздувать критерии.
Все исходные задачи должны попасть в группы ровно один раз; при объединении
сохраняются полные наборы требований, критериев и зон, внешние зависимости,
риск не понижается. Совпавшие тексты критериев сохраняются отдельно как
`<исходный ID>: <текст>`; riskReason сохраняет все непустые исходные обоснования.
Подробный формат — [product-development.md](product-development.md).

`plan --file … --review …` проверяет покрытие требований, зависимости и зоны; вычисляет
волны и создаёт карточку worker для light и standard, для heavy — worker, critic1 и
условный critic2 (в закреплённых adaptive/legacy ещё и acceptor). Карточка critic2
не означает назначение или запуск второго критика. Поле readZones перечисляет
прочие входы. Зависимость обязательна при пересечении записи с чужой записью
или чтением, включая транзитивные зависимости и общие файлы проекта.
Автоматическая раздача разных волн не заменяет dependsOn.
Нужна одна финальная задача с зависимостями от всех остальных и обзором
всего дерева кода (`readZones: ["."]` подходит). Для heavy каждый фактически выполняемый
критик проверяет полный diff по всем пяти осям в `branchReview`, включая
единственный раунд при первом PASS; дополнительного круга нет. Для light- или
standard-финала до handoff нужен отдельный общий `integration-review`; его подписывает
независимый участник, не worker. Команды и форма — [task-tiers](task-tiers.md).

`team` возвращает карточки. `team --file …` задаёт специализации и дополнительные
проверки под конкретный проект. Формат — в contracts.md. Подготовь специализации
до назначения исполнителей; после первого критика карточки и контракт попытки
заморожены. Смена специализации до критики требует новых назначений.

## Режимы проверки

Человек выбирает режим при старте (`init --check`) и меняет только своими словами
(слова в файл → `check-mode <режим> --file`; бриф не меняется). `fast`: задачи класса `fast` завершаются
`submit` без критиков и сверок волн; проблемы итоговой приёмки не чинятся —
прогон завершается `delivered_with_remaining`, отчёт называет пропущенные проверки
(`remaining.skippedChecks`). `balanced` — экономный
контроль по классам плана. `max`: задачи heavy, все восемь сценариев, сверка
после каждой волны без переиспользования итоговой; после non-PASS второго критика
одна `extra-wave <id>`, далее `deferred` с переносом в остатки, зависимые задачи строятся без её критериев
(`deferredDependencies`). Что остаётся всегда: журнал, usage, handoff, чистый
клон, blind. Подробнее: [04](../phases/04-build.md), [контракты](contracts.md).

## 5. Одна задача

Light и standard после адресной проверки и worker-report завершаются через `submit`.
Ниже критики относятся к heavy, а `complete` и acceptor — только к закреплённым
adaptive/legacy попыткам. При новом риске
`promote-task <id> --reason …` повышает класс с сохранением истории.


Получай свежий пакет для текущей роли, не копируй старый basis:

```text
context --kind task --task T01 --role worker --write
start T01 --context <basis>
```

Это начальный пакет worker без формы: `--with-template` допустим только после
успешной адресной проверки текущего кандидата и реального назначения.
Создай нативного исполнителя инструментом фактической среды. Передай ему
карточку worker, путь пакета, правила проекта и границы записи. Сразу запиши:

```text
assign T01 --role worker --runtime codex --native-id <реальный-ID> --session <реальная-сессия>
```

Ответ assign содержит внутренний `receipt.actor`; именно он идёт в reviewer
отчёта, а не произвольное имя. Подтверди назначение в пакете исполнителю.
Координатор последовательно записывает журнал; агенты сохраняют результаты
в своих объявленных зонах и доказательства текущего прогона.

В `behavior_change` для задачи с изменением поведения сначала сохрани новые тесты, запусти
реальный RED через `verify --task T01 --purpose check -- <argv>` и возьми
его ref из `commands`. До реализации и первого `submit` запиши
`test-intent --task T01 --file …`:
точные критерии, пути и SHA тестов, ожидаемую ошибку и ссылку на RED.
После реализации выполни свежий GREEN; RED не должен быть таймаутом,
усечённым выводом или ошибкой запуска. Для чистых docs/config либо
уже существующего поведения integration используй `mode: not_applicable` только с
отдельной причиной и неизменным файлом для каждого критерия. Отчёт можно
обновить до критики; изменённым тестам нужен новый RED. История не стирается.

Сам `changeKind: integration` не освобождает новое поведение от RED.
В новом `init` с `incrementalTestIntent` используй адресные RED по источникам:
неизменённая строка ссылается на проверенный предыдущий intent, изменённая
получает новый RED. Форма, семантический SHA и границы repair —
[адресная история RED](contracts.md#адресная-история-red-incrementaltestintent).
Закреплённую schema 1 этим маршрутом не переписывают.

При `errorBoundaryChecks` включи в test-intent привязанную к исходникам матрицу
`failureChecks`: применимые отказы, ожидаемое поведение и причины неприменимости.
Матрица задаёт намерение; реальные отрицательные сценарии и сохранность данных
у heavy проверяют критики (в закреплённых adaptive/legacy ещё и приёмщик) по
актуальным свидетельствам; для light и standard исполнитель сохраняет адресные доказательства, затем их проверяют общий
независимый обзор и итоговая приёмка. Подробности —
[failure-checks.md](failure-checks.md).

После реализации выполни подходящую **адресную** проверку:

```text
verify --task T01 --purpose test -- python3 -m unittest discover -s tests -p 'test_feature.py' -v
context --kind task --task T01 --role worker --write --with-template
submit T01 --file <absolutePath заполненной формы worker>
```

Команда проверки здесь — пример: замени её реальной проверкой проекта.
Не используй true/echo или самоподтверждающий тест. Точный output-файл
находится в verification пакета. Bundle возвращает ссылки `context`, `card` и
`template`; передай их участнику по `absolutePath`. Он заполняет форму, затем
координатор отдельно записывает submit. Отчёт покрывает каждую пару expectedChecks.

Создай нового независимого critic1, сразу запиши assign, передай его карточку
и свежий пакет с формой через
`context --kind task --task T01 --role critic1 --write --with-template`. Запиши отчёт:

```text
critic T01 --round 1 --file "<absolutePath заполненной формы critic1>"
```

В lean и adaptive отчёт каждого критика (и приёмщика в adaptive) содержит явный
`verdict: PASS|WARN|BLOCK|FAIL`. PASS требует всех passed checks, пустого
unmapped и отсутствия обязательных или нерешённых замечаний. Только
информационный finding с severity `note` может сопровождать PASS; требующее
действия замечание имеет severity `warning` или `blocking`. В отчёте критика
каждая непрошедшая проверка получает обязательный finding ID. Неизвестный verdict и противоречивый
PASS отклоняются без расходования раунда.

Критик lean сверх обычных проверок смотрит критерии всех задач замыкания,
ограничения проекта, `trace` каждой исходной цитаты (`aligned|drift`) и точные
`inheritedProofs`. Пакет начинай с `zoneChanges` (изменённые файлы зон задачи от
исходного снимка, читаются целиком) вместе с карточкой, test-intent,
expectedChecks и цитатами trace; поля `onDemand` (брифы, spec, discovery, план,
знания) открывай по конкретной находке. `drift` несовместим с PASS и требует
обязательного замечания по критерию «Результат задачи соответствует исходному
запросу и ограничениям». Строгий PASS критика сразу закрывает задачу
(`completionKind: critic_acceptance`): `complete`, acceptor, critic2, ремонт и
фиктивный второй отчёт не нужны и не разрешены.

В закреплённой adaptive-попытке после первого PASS сразу создай отдельного
acceptor: critic2, ремонт и фиктивный второй отчёт не нужны и не разрешены.
Кандидат до приёмки не меняется.

После WARN/BLOCK/FAIL прочитай `repair-plan T01` без `--file`: он выдаёт актуальный basis,
task, attempt, firstReport, requiredFindingIds и requiredFindings. Затем сохрани диагноз
`repair-plan T01 --file …` с этим basis,
причиной, всеми обязательными blocking/warning ID и маршрутом. `implementation_gap` исправляет
исходный worker; при `missing_context` или `wrong_approach` назначь нового
worker с полным контекстом и передай адресный контекст. `external_blocker`
остаётся blocked до снятия препятствия. Затем повтори `verify --task T01`,
получи свежий пакет worker с `--write --with-template` и сохрани `repair T01 --file …`.
Repair связан с SHA первого отчёта и всеми обязательными finding IDs.

После ремонта создай второго критика отдельным новым нативным участником:
assign critic2 → `context --kind task --task T01 --role critic2 --write --with-template`
→ заполнение формы → `critic T01 --round 2 --file …`.
Он независимо проверяет кандидат, связь с первым отчётом и результаты
исправлений. Resolutions охватывает каждый обязательный ID; unresolved
блокирует PASS. В lean PASS второго критика закрывает задачу
(`critic_acceptance`); WARN/BLOCK/FAIL второго раунда блокирует задачу; третьего
раунда нет. Только legacy `two_rounds` требует второго критика также после
первого PASS: без ремонта, с repairReceipt null и неизменным кандидатом.

В закреплённых adaptive/legacy попытках после PASS последнего обязательного критика
создай отдельного acceptor, запиши assign и выдай пакет
`context --kind task --task T01 --role acceptor --write --with-template`.
Приёмщик сначала читает полные оригинальные брифы, затем
проверяет задачу, все критерии предков, ограничения и точные исходные цитаты.
Он записывает verdict, trace и inheritedProofs; previousReport ссылается на
реальный последний обязательный отчёт критика. Basis должен совпадать с этим
кандидатом. Только отчёт приёмщика передаётся в:

```text
complete T01 --file "<absolutePath заполненной формы acceptor>"
```

WARN/BLOCK/FAIL приёмщика блокирует задачу. В lean этого шага нет: задачу
закрывает PASS критика. Для обычного препятствия используй
`block T01 --note "…"` и продолжай независимые задачи. Reset допустим только
до расходования раундов и не сбрасывает лимит критики у зависимых задач.

## 6. Волна и итог

Когда задачи волны завершены или заблокированы, выполни общую проверку кода
без --task, затем передай независимому проверяющему весь бриф. Для последней
волны сначала пройди Git/verify/handoff в порядке ниже:

Для промежуточной волны:

```text
verify -- <реальная общая команда проверки>
context --kind wave --write
wave 1 --file .aispa/inbox/wave-1.json
```

Перед открытием следующей волны последняя сверка должна быть актуальна.
Принятый потомок может подтверждать предка после его изменения только при
явной зависимости, сохранённых inheritedProofs и повторной проверке всех
критериев предка. Соседняя задача такого права не даёт.

Обычные проектные документы готовь в задачах: README/архитектуру/решения/
словарь по размеру проекта. Для heavy их проверяют требуемые политикой
критики (в закреплённых adaptive/legacy и приёмщик) вместе с кодом; для light и standard — worker и затем общий обзор
версии и итоговая приёмка. Покажи реальные команды установки, запуска, общей проверки и
отдельного теста либо объясни применимое N/A. Исходный бриф не экспортируй
в публичные документы.

После каждого выполненного `verify`/`clean-verify`, включая FAIL, движок
добавляет подлинную запись истории. `commands --purpose test --kind task
--limit 8` даёт короткую выборку с точными refs; `commands --receipt <SHA>` —
один подробный receipt. Это исторический факт, не свежий PASS; список не
подменяет `verified` и не входит целиком в публичную передачу.

После приёмки задач последней волны сохрани код и документы в Git. Проведи свежую
общую `verify --purpose check` на текущем коде, затем
`handoff --file .aispa/inbox/handoff.json` с подлинными успешными receipts.
Handoff проверяет tracked status, SHA, разделы и связь с командой, но не
удостоверяет смысл и приватность прозы. Теперь проведи сверку последней волны.
Не запускай новую общую verify после неё без нового основания: даже при
прежнем коде новый receipt меняет basis и требует повторной сверки.
При настоящем изменении повтори затронутые проверки по прежним правилам.
Только затем:

```text
clean-prepare
clean-verify --purpose check --timeout 600 -- <реальная команда установки/сборки/проверки>
context --kind blind --write
blind --file .aispa/inbox/blind-observations.json
context --kind acceptance --write
acceptance --file .aispa/inbox/final.json
```

Clean-prepare создаёт отдельный локальный клон точного HEAD. Clean-verify
запускает команду внутри него с отдельными HOME/TMP и сокращённым окружением.
Это изоляция копии, не песочница: выбирай безопасные команды. Не копируй .env,
локальные node_modules/venv и не используй абсолютные пути исходного проекта.
Поставь зависимости по зафиксированным манифестам, затем проверь пользовательский
сценарий. Если шаг недоступен, сохранится отказ; зелёной замены через echo нет.
Ссылки, submodules и tracked credential-файлы в этой альфе отклоняются.

Новому приёмщику сначала передаётся только blind-пакет. Он фиксирует наблюдения
по исходным словам, не видя реестра, спецификации или чужих ревью. Только после
blind доступен acceptance-пакет. Тот же приёмщик сопоставляет каждое наблюдение
с требованием через blindMapping, указывает SHA blindReport и cleanrun.
Потерянные наблюдения или непринятое ядро запрещают успешный итог. Кандидат
и чистый клон должны оставаться актуальными до finish.
Непроверенное ядро не сдаётся; второстепенные остатки сохраняются.

После успешной acceptance создай нового автора знаний по
[knowledge-writer.md](../prompts/knowledge-writer.md). Он отличается от всех
исполнителей, критиков и итогового приёмщика. Запиши реальное назначение и
передай ему пакет готового кода:

```text
knowledge-assign --runtime codex --native-id <реальный-ID> --session <реальная-сессия>
context --kind knowledge --write
knowledge-record --file .aispa/inbox/knowledge.json
finish
```

Пакет даёт снимок кода, подписанного автора, настоящие receipts проверок и их
digest. Автор читает соответствующие файлы и сохраняет применимые знания четырёх
видов; для отсутствующих категорий пишет причины неопределённости. Полная схема —
[product-development.md](product-development.md). `finish` нового прогона требует
актуальную запись знаний; она не подменяет итоговую приёмку или clean-verify.

При достижении 64 локальных отчётов выполни `knowledge-compact`, затем повтори
knowledge-record. Контрольный снимок сохраняет рабочий набор и ссылку на
неизменный архив; исходники не удаляются. При новом init снимок создаётся
автоматически. Для адресного поиска за пределами рабочего набора используй
`knowledge --path … --archive --archive-depth 4` и учитывай `archive.unread`.

`close blocked --note …` фиксирует непреодолимый блокер; close paused применяют
только по просьбе владельца. Не подделывай успех ручным редактированием журнала.

## 7. Новая попытка по словам владельца

После финального ответа владелец может разрешить новую попытку. Если объём
прежний, используй [отдельный источник решения](owner-task-attempt.md),
сохранив вопрос и точный ответ. Для закрытого прогона сначала выполни `resume`
отдельно, затем `new-attempt --owner-source-file … --source-sha256 …
--owner-decision-id … --quote …`. Бриф, критерии и история сохраняются.

Если изменяется сам объём, сохраняется прежний маршрут дополнения брифа:

```text
new-attempt T01 --brief B002 --quote "Исправь поиск по этому замечанию"
```

В этом legacy-маршруте цитата должна реально содержаться в новом источнике
после предыдущей попытки. Пересверь бриф, спецификацию, coverage и план; подготовь новые карточки и новых
участников. История предыдущей попытки не удаляется. Это не способ автоматически
спросить разрешение на третий раунд во время разработки или обойти блокировку.

## 8. Короткие пакеты и расход

Для обычных команд записи и status поставь `--compact` перед подкомандой:
полный результат сохранится по возвращённым адресу и SHA. Коды выхода
и блокировки прежние; команды чтения остаются полными.
После assign и при допустимом этапе роли получи
`context --kind task --task T01 --role <роль> --write --with-template`:
выдача содержит адреса пакета, карточки и формы, без их тел. Worker на старте
получает обычный пакет без формы, а после успешного адресного verify — bundle.
Передавай `absolutePath`, который не зависит от рабочего каталога участника;
`path` формы сохраняет путь относительно корня проекта для совместимости.
Отдельный `template <роль> --task T01 --write` остаётся совместимым маршрутом
только для формы. Bundle дополнительно проверяет наличие успешного актуального
verify worker; отдельная команда сохраняет прежние условия выдачи формы.
В обоих случаях следуй порядку verify → форма → отдельная сдача отчёта.
Форма заполняет вычисляемые поля, а не результаты проверки или независимость.
Не печатай заготовку в главный диалог и не проставляй PASS автоматически.

Поля sections в context --write — обязательные адреса полных данных, а не
необязательные приложения. Конверт ≤16 000 байт, источник не усечён. Не
вставляй полные JSON-отчёты субагентов в главный диалог: сохраняй файл и передавай
путь, краткий итог и блокеры. Обязательные проверки политики попытки,
критик heavy-задачи (в закреплённых adaptive/legacy — и приёмщик) и полный бриф на границах волн/финала сохраняются.
Одинаковые разделы получают стабильные адреса по SHA. В сохранённом контексте
того же участника разрешено повторно использовать уже прочитанный полный
текст с неизменным SHA. Это не разрешение свежему критику или приёмщику
пропускать свои источники и не замена восстановления после потери контекста.

Risk low требует riskReason. Standard рекомендуют только изолированному
исполнителю малорисковой задачи. Правила legacy и managed-политик описаны в
[03-plan](../phases/03-plan.md); реальные возможности и разрешения задают среда
и проект. Для новых субагентов Codex выбирай последнюю разрешённую Terra из
каталога host; её недоступность — явный capability gap без молчаливой замены
на Luna. Другие среды сохраняют свои разрешённые профили.

`taskRoleSlots` оценивает одну роль light или standard, 2–3 роли heavy lean,
3–4 heavy adaptive и 4 legacy; это не верхний
предел нативных запусков. Подготовка, замены исполнителей и новые разрешённые
попытки в диапазон не входят. Фактические вызовы и токены подтверждает native
usage; `maximumCriticRounds: 2` не подменяет `actualCriticRounds`.

Assign --model сохраняет запрошенный ID; actual model остаётся unknown без provider metadata.
`usage --file` сохраняет измерение конкретного native-вызова;
`usage-import --file <локальный-лог> --format codex|claude` привязывает
записи к зарегистрированным участникам и отмечает пропуски. `usage` без файла
показывает только измеренное и покрытие всех ролей, без догадок о пропущенных
вызовах. Для полного итога нужна финальная контрольная точка с ответом
координатора; неполную сводку не называй полной стоимостью.

## 9. Оборванный журнал

`journal-inspect` читается до обычного `status`, который при повреждённом
журнале закономерно откажет. Он предлагает восстановление только неполной
последней строки после целой цепочки. После просмотра исходного SHA применяй
`journal-recover --sha256 <journalSha256> --confirm`: точные исходные байты
остаются в резервной копии, событие восстановления переводит прогон в paused.
Повреждённую середину и неоднозначную полную строку этот маршрут не обрезает.

Затем зарегистрируй свежего `recovery-reviewer`, запусти `journal-verify --
<argv>` и получи `journal-context`. Отчёт `journal-reconcile --file …`
должен содержать этот basis, отдельные неизменные свидетельства осмотра
файлов и классификации внешних эффектов. Неизвестные эффекты — только blocked.
Успешная сверка снимает pending, но не меняет paused на running: для этого
нужен отдельный `resume`. Подробности — [фаза продолжения](../phases/06-continuity.md).

## Смешанные свидетельства (`mixed`)

Новые `init` с политикой `mixedEvidence` поддерживают `mode: mixed` в
`test-intent`. Закреплённые runtime и история активных проектов не мигрируют;
`behavior_change` и `not_applicable` сохраняют прежние контракты.
В `criteria` остаётся полный точный список критериев задачи. `routes` содержит
строки `{criterion,kind,reason,procedure,expected}`, где `kind` —
`automated|browser|process`. Каждому критерию нужны один или несколько способов;
пара `criterion/kind` уникальна. Причина, процедура и ожидаемый результат
обязательны. Процедура описывает намерение, а не уже полученный PASS.

Новые тесты `newTestFiles` и настоящий `redExecution` покрывают только критерии
с маршрутом `automated`. Без них поля имеют значения `[]` и `null`; выдумывать
RED для ручной проверки нельзя. Свежий `verify --task` кандидата перед сдачей
обязателен также без automated. Сборка или smoke с exit 0 сами по себе не
подтверждают браузерный либо процессный результат.

Контекст сохраняет неизменную ссылку `testIntent`, все критерии и trace;
`evidenceSummary` объясняет маршруты, `observationTemplates` даёт незаполненные
формы browser/process. В каждом отчёте worker, критика и приёмщика обязательны
все `routeChecks`: `{criterion,kind,status,note,artifact}`. Заготовки содержат
`not_tested`, пустые note/artifact. Общему критерию нельзя присвоить passed,
пока любой его маршрут имеет non-PASS. Недоступное наблюдение отражается честно.

Browser/process artifact — JSON `schema: 1`, привязанный к текущим `run`,
`task`, `attempt`, `candidate`, `kind`, `criteria`, `intentSha256`. Заполни
`procedure`, `observed`, `source` (browser: URL и viewport; process: reference
и scope), `attachments` с `file` и `sha256`. SHA подтверждает связь и сохранность
файла; смысл наблюдения независимо оценивают существующие критики/приёмщик.
Новая роль или интервью не создаётся. Старое наблюдение другого кандидата,
попытки или намерения не подтверждает текущий результат.

Первичная классификация записывается до первой сдачи. Объявленные маршруты
нельзя удалять или понижать через revisions; добавления допустимы только до
первого submit. Карточки, участники, попытки, раунды и прежние свидетельства
сохраняются. В mixed каждая строка `failureChecks.cases` содержит `kind`, прежние
`id,boundary,scenario,expected,criterion` и `test:{path,sha256}` для automated
либо `source:{path,sha256}` для browser/process; пять отказных границ сохраняются. Сквозной trace к брифу,
clean clone и независимая итоговая приёмка проекта остаются обязательными.
