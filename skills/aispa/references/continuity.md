# Исследование, память и экономия · 0.2.0

## Сначала изучение

`discover [--include относительный/файл.py …]` собирает ограниченный набор
свидетельств и возвращает путь к JSON. Он читает реальные документы, манифесты
и характерные точки входа. Нет автоматического вывода «архитектура изучена» по
именам каталогов. Для предметных модулей и тестов исследователь добавляет include.
Повтор без include сохраняет прежнюю выборку; новый список её заменяет.

Коллекция содержит basis, пути и SHA-256 источников, фрагменты, дословно найденные
команды и явные пропуски. Секреты, личные данные, архивы, vendor, игнорируемые
файлы и symlinks не читаются как источники. Лимиты сборщика: до 48 источников,
до 6000 символов фрагмента, до 96 000 символов всего; файлы свыше 256 KiB
отмечаются пропущенными. Непрочитанное не считается изученным. При недостатке
свидетельств исследователь адресно читает безопасный исходник и сохраняет
ограничения, а не делает вывод по обрезанному фрагменту.

Отчёт `discover --file … --actor <ID автора>` (для новой политики):

```json
{
  "basis": "<из коллекции>",
  "summary": "Что удалось установить о проекте",
  "observations": [
    {
      "area": "architecture",
      "text": "Конкретный вывод по изученному источнику",
      "sources": [{"path": "README.md", "sha256": "<из коллекции>"}]
    }
  ],
  "uncertainties": [
    {"area": "data", "text": "Схема данных пока не установлена"}
  ]
}
```

Автором может быть зарегистрированный координатор с тем же исходным ID.
Сбор источников сам по себе не создаёт receipt изучения. Авторство отчёта,
независимые роли и однократный учёт usage — [runtimes](runtimes.md#авторство-фаз).

Пример неполный: все семь областей architecture, data, entrypoints, dependencies,
commands, conventions, risks должны иметь наблюдение или явную неопределённость.
Каждое наблюдение ссылается на собранный источник. Для команд добавляется поле
command с точным значением из коллекции. Происхождение проверяется кодом;
смысловая достоверность вывода остаётся работой исследователя и критиков.

`discovery` показывает свежесть. Изменение выбранного источника или появление
нового характерного источника требует повторной сверки перед следующим планом.
Во время исполнения старый снимок остаётся историческим контекстом; исходники
задачи защищаются её readZones и проверками текущего кода.

## Между прогонами

Init поддерживает read-only перенос истории schema 1 из alpha.1–alpha.7 и
текущей версии. Активный старый прогон продолжает свой закреплённый runtime;
это не миграция его движка. Неизвестная версия отклоняется.

Init сохраняет неизменный handoff предыдущего завершённого либо отменённого
прогона до переключения active pointer. При ошибке переноса прежний указатель
остаётся. Лимиты: до 1 MiB на исходный текст и до 16 MiB на handoff; при превышении
перенос останавливается без усечения и смены активного прогона.
Сохраняются исходные тексты и их происхождение, решения, исторические
приёмки, накопленные остатки и сведения об использованных попытках.

Новый прогон не получает старые PASS как доказательство. История принятых
результатов и текущие обязательства различаются. `.aispa/context/carryover.md`
показывает полную переданную историю; короткая memory.md содержит указатель
и число открытых пунктов. `memory` возвращает проверенный ledger.

Остатки не исчезают и не входят в новый объём автоматически. Прочитай их до
интервью и сопоставь с текущим поручением. В auto техническое решение принять
можно самостоятельно, но повторная попытка ранее порученной работы требует
реальных новых слов владельца, а не выдуманной цитаты.

```text
carry C-<id> --action keep
carry C-<id> --action map --requirement R01 --brief B001 --quote "Продолжи оставшийся экспорт"
carry C-<id> --action resolve
carry C-<id> --action defer --brief B002 --quote "Экспорт пока отложить"
```

Map выполняется после requirements, до plan. Новое требование сохраняет исходные
текст, вид, ядро и критерии; новые критерии можно добавлять. Map хранит старую
цитату вместе с новым разрешением. Resolve требует новых ролей и актуальной
приёмки всех задач. Изменившийся после resolve код возвращает пункт в открытые;
старое свидетельство разрешения остаётся историей. Отмена прогона также не
перевозит его текущую приёмку как действующую.

Drop/defer требуют нового источника владельца; defer остаётся видимым остатком.
Переименование семантически той же работы не даёт права обойти происхождение:
движок распознаёт точное совпадение текста, за смысловую связь отвечает координатор.
Старые источники сопоставленной работы входят в blind-пакет отдельно, без статусов
и чужих оценок; applicableQuotes определяет относящиеся к новому поручению цитаты.

Отдельный слой `executionRemainders` переносит незавершённые обязательства
исполнения с исходной цитатой, SHA записи, началом, seal и результатом, если
он был. `memory` показывает ограниченную сводку и `executionOmitted`, полная
история доступна по `handoff`. В `status` это `remaining.inheritedExecution`;
остатки текущего прогона показаны отдельно в `remaining.execution`.
Они не становятся новым scope или PASS и не закрываются `carry resolve`.
Поздние host receipts пока не поддержаны. См.
[обязательства исполнения](execution-obligations.md#следующий-прогон).

## Полезные знания о реализации

После успешной итоговой приёмки отдельный свежий автор знаний читает готовый
код и фактические проверки. Координатор записывает `knowledge-assign`, передаёт
`context --kind knowledge --write`, затем сохраняет `knowledge-record --file …`
перед finish. Четыре категории — command, trap, decision, glossary; отсутствие
полезного знания по категории требует конкретной причины в uncertainties.
Это не пересказ замысла и не дополнительный PASS.

Для command автор может выбрать любой подлинный успешный запуск текущего
прогона из `commands --purpose … --limit …` и открыть одну запись через
`commands --receipt <SHA>`. Отчёт указывает точный argv и
`verification:{kind:"execution",sha256:"<SHA записи>"}`. Более ранний
source candidate допустим, но `currentAtCuration` сообщает, отличается ли
он от текущей основы. Это не снимает требования свежей acceptance и общей
проверки перед knowledge-record. Legacy project/cleanrun refs прежних
прогонов продолжают читаться. Не копируй полный список команд или их логи в
публичные документы; после acceptance записываются только приватные знания.

Знания хранятся отдельными неизменными артефактами и переносятся при новом init
с происхождением. Stable key связывает новые редакции через supersedes;
предыдущие записи остаются в истории. `.aispa/context/knowledge.md` указывает,
как получить нужное. Для текущего вопроса выбирай адресную выдачу:

```text
knowledge --path src/planner.py --kind trap --limit 4
knowledge --kind command --limit 3
knowledge --path src/planner.py --kind trap --archive --archive-depth 4
```

Без path/kind каталог не загружается. При наличии обоих фильтров запись должна
соответствовать и типу, и пути. Изменившийся SHA любого источника исключает
запись из действующей выдачи; счётчики omitted показывают пропуски. Старые
команды всегда исторические: перед заявлением о нынешнем успехе запусти их
заново. В пакете задачи допустимы короткие релевантные подсказки; независимому
blind-приёмщику они не передаются. Формат и лимиты —
[product-development.md](product-development.md#после-приёмки-сохранить-проверенные-знания-о-реализации).

При новом init знания получают контрольный снимок: до 128 записей и 512 KiB
в рабочем наборе, с точной ссылкой на неизменный архив. В активном прогоне
`knowledge-compact` освобождает место после 64 локальных отчётов; затем можно
повторить knowledge-record. Один артефакт ограничен 1 MiB, исходная история
и доказательства не удаляются. При необходимости снимок делают раньше лимита.

Обычная выборка читает рабочий набор. `--archive` добавляет адресный поиск
по архиву; `--archive-depth` задаёт глубину 1–64, по умолчанию 4. Непрочитанный
остаток обозначен точной ссылкой `archive.unread`. `archive.archivedRecordCount` считает
отчёты автора, а не разные знания. Более старая редакция key не подставляется
вместо новой, потерявшей актуальность.

## Контекст и модели

Контекст задачи содержит только её определения, нужные требования, зависимости,
ссылки на доказательства и карточку выбранной роли. История всей команды в него
не копируется. Большие поля выносятся в неизменные sections; конверт ограничен
16 000 байтами. Все необходимые sections обязательны к чтению. Исходные слова,
ограничения и критерии не обрезаются ради размера конверта.

Предпочитай задачи с законченным проверяемым результатом. Не дели один небольшой
результат на множество задач с повторной передачей контекста каждому участнику.
Разделяй при разных зависимостях/зонах, самостоятельном риске или чрезмерном
контексте исполнителя. Не сливай задачи через конфликт записи/чтения ради экономии.

`plan-check --file …` рассматривает размер исходного черновика. Перед `plan`
запиши группы объединения и объяснения сохранённых мелких границ; используй
`plan --file … --review … --actor <ID автора>`. Итог сохраняет требования,
критерии, зоны и внешние зависимости полностью, риск не понижается. Подсказки не являются измерением
токенов: новый план оценивает одно место для light и standard, 2–3 для heavy lean,
3–4 для heavy adaptive, legacy — четыре. Общий обзор light- или standard-финала
учитывается отдельно. У heavy lean первый PASS критика закрывает задачу
(в закреплённом adaptive ведёт к отдельному acceptor); остальные вердикты —
к ремонту и свежему critic2. Разбор не сбрасывает историю попыток и предел
двух раундов. Замена исполнителя ремонта может добавить ещё одного участника.

Совпавшие тексты критериев объединённых задач сохраняются по отдельности с
префиксом `<исходный ID>: <текст>`; остальные критерии — дословно. Итоговый
riskReason содержит все непустые исходные объяснения рисков.

План может добавить risk: low|normal|high и riskReason. Low допустим для
малорисковой изолированной реализации; объяснение обязательно. Для неё карточка
рекомендует standard. Сильная модель — только для задач с чувствительными путями (правило в
[03-plan](../phases/03-plan.md)); фундамент, критики, ремонт и высокий риск её
сами не включают. Это уровни, не названия провайдеров. Реальную модель выбирает host с учётом правил проекта. Недоступность выбора не обходят выдуманным
параметром; сохраняют текущую модель. Assign --model записывает фактический ID.

`usage --file …` принимает только реальные метрики native-вызова:

```json
{
  "actor": "<receipt.actor>",
  "callId": "<уникальный ID вызова>",
  "source": "<источник измерения среды>",
  "inputTokens": 1000,
  "outputTokens": 200,
  "cachedInputTokens": 700
}
```

Cached input входит в input, повторная запись того же вызова запрещена.
Без метрик возвращается unknown/null; байты не пересчитываются в придуманные
токены. Даже записанные метрики могут покрывать лишь часть прогона. Заявлять
экономию времени или денег можно только после сопоставимого измерения.

В alpha.10 `participant` дополняет прежние task `assign` и
`knowledge-assign`: coordinator, brief-analyst/reviewer, discovery, coverage,
planner, blind и recovery-reviewer получают настоящие ID из среды.
`participants` показывает их неизменные записи; одно native ID в новой session
не делает проверяющего независимым. `usage-import --file … --format codex|claude`
читает локальный журнал среды, проверяет ID вызова и связывает
его с зарегистрированным участником. Повтор native call ID и пересчёт
кешированных токенов как нового расхода запрещены. `usage` отдельно показывает
измеренные числа, missingParticipants/missingRoles и пропуски импорта.
Полный итог требует финальных контрольных точек после ответа координатора;
пока хотя бы одна роль или вызов без источника, `complete` остаётся false.

При оборванной записи `events.jsonl` память не пересоздаётся через `init`:
`journal-inspect` → просмотр исходного SHA → `journal-recover` с точной
резервной копией → paused → свежая проверка → независимая сверка эффектов.
После `journal-reconcile` успешный маршрут требует отдельного `resume`.
Историческая backup-копия и событие восстановления остаются в run; это не
переоценка старых PASS.
