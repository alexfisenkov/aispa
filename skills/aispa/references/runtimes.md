# Среды AISpa · 0.3.0

Один пакет aispa используется целиком. Команды модели берутся из доступного
реестра конкретной сессии: файл инструкции не подтверждает наличие инструмента.

| Среда | Проектная установка | Вызов | `--runtime` |
|---|---|---|---|
| Codex | `.agents/skills/aispa/` | `$aispa` | `codex` |
| Claude Code | `.claude/skills/aispa/` | `/aispa` | `claude-code` |
| Cursor | `.cursor/skills/aispa/` | `/aispa` | `cursor` |
| OpenClaw | `.agents/skills/aispa/` | `$aispa` или `/aispa` | `openclaw` |
| Gemini CLI | `.gemini/skills/aispa/` | явное «Используй AISpa» | `gemini` |
| Antigravity app/IDE | `.agents/skills/aispa/` | явное «Используй AISpa» | `antigravity` |

Глобальные каталоги, приоритет копий, независимые участники и измерения —
[нативные адаптеры](native-agents.md). Настройки host не включаются автоматически;
при отсутствии независимых контекстов соответствующий этап остаётся заблокированным.

На явном вызове сначала запускается update-check установленного пакета.
Обновление предлагается только после подготовки проверяемого кандидата;
устанавливается после явного выбора. Отсутствие сети не мешает продолжению.
Автоматическое обновление по содержимому main не допускается.
Первая установка из опубликованного Release проходит через отдельный
`install.py preview` → просмотр → `apply --confirm`;
[инструкция](../../../docs/install.md). Наличие исходного кода не означает
доступного опубликованного пакета. По умолчанию выбирается стабильный
Release; явный опубликованный `--tag` допускает предварительную версию.

## Проектные правила и постоянный контекст

Host передаёт фактическую среду в init явно, без угадывания по environment.
Если текущая среда известна, спрашивать пользователя о ней не нужно.

| Среда | Куда добавляется стабильная ссылка |
|---|---|
| Все шесть | AGENTS.md: существующий текст сохраняется; отсутствующий файл получает минимальную фактическую карту проекта |
| Codex | Также в существующий AGENTS.override.md, который может перекрывать AGENTS.md |
| Claude Code | CLAUDE.md с сохранением существующих инструкций |
| Cursor | Собственный `.cursor/rules/aispa.mdc` с `alwaysApply: true`; чужой одноимённый файл вызывает явный конфликт |
| OpenClaw | AGENTS.md в физическом root проекта; внешний workspace не изменяется |
| Gemini CLI | GEMINI.md с сохранением существующего текста; нестандартный `context.fileName` проверяет host |
| Antigravity | GEMINI.md и собственный `.agents/rules/aispa.md` с `trigger: always_on`; чужой одноимённый файл вызывает конфликт |

Перед записью проводится инвентаризация существующих имён файлов. Правила
тестовых фикстур и архивов не становятся каноном. Стек и команды не выдумываются;
прикладные каталоги автоматически не навязываются. Перед изменением существующих
правил сохраняется копия в `.aispa/backups/`. Ссылки и выход за корень запрещены.

`.aispa/context/` содержит производные документы и ограниченную краткую память
с указателями на полные данные. Обычный refresh меняет только эту скрытую
папку. Смена статуса не меняет корневые правила и хеш кода.

## Нативные участники

Для heavy-задач новых прогонов (`reviewPolicy: lean`) среда создаёт worker и critic1:
его строгий PASS закрывает задачу, отдельного acceptor нет. После WARN/BLOCK/FAIL
обязательны ремонт и свежий critic2, чей PASS закрывает задачу; максимум два
раунда. Закреплённые adaptive-попытки после PASS ведут к acceptor; старые
попытки `two_rounds` сохраняют обоих критиков и acceptor. Light и standard
получают только worker: адресная проверка и submit без task critics/acceptor.
Общий обзор версии и финальная приёмка
сохраняются независимо от класса задачи. Координатор
записывает assign с native ID и session из реального ответа инструмента.
Движок сохраняет роли и проверяет разделение записанных участников; он сам
не запускает агента и не обращается к провайдеру. Не имитируй отсутствующий
инструмент случайным ID или собственной проверкой с independent: true.

Критики и приёмщик получают новые контексты без истории убеждения исполнителя:
карточку роли, пакет, исходные брифы, код и необходимые доказательства.
Второй критик получает также первый отчёт и receipt исправления, когда он есть.
Настройки модели и доступов определяются host и правилами проекта.

В alpha.10 общие фазы (coordinator, аналитик и проверяющий брифа, discovery,
coverage, planner, blind, recovery-reviewer) используют `participant` с теми
же реальными runtime/native ID/session. Роль автора знаний остаётся за
`knowledge-assign`, роли задачи — за `assign`. Повтор native ID под новой
session не доказывает независимости; реестр отклоняет такую подмену в том же
runtime. Записанная карточка подтверждает происхождение ID, но движок не
аутентифицирует модель или свежесть контекста без среды. Учитывай usage всех
участников из native response/log; непокрытые роли остаются видимыми.

Codex использует доступные инструменты субагентов; agents/openai.yaml
отключает неявное применение навыка. Claude Code использует свои нативные
субагенты; disable-model-invocation сохраняет явный вызов. В Cursor наличие
агентов, shell, браузера и выбора зависит от режима; проверь возможности
до обещания независимой приёмки. При отсутствии опроса покажи варианты текстом.
При отсутствии независимых контекстов выполни доступное и зафиксируй блокер.

## Авторство фаз

Новый `init` включает `phaseReceipts`: сохранённый отчёт связывается с реальным
зарегистрированным actor, его текущим basis и неизменным artifact. Receipt
пишет движок вместе с отчётом; отдельной команды ручного создания нет.
Координатор может сам выполнять `idea`, `brief-analyst`, `discovery`, `planner`
под одним исходным ID. Это несколько фаз одного участника, а не новые агенты.
`brief-reviewer`, `coverage`, `blind` и остальные независимые роли нельзя
заменить псевдонимом координатора или повтором native ID с новой session.

В командах `idea --file …`, `discover --file …`, `plan --file … --review …`,
`coverage --file …` указывай `--actor <ID из participant>`. Без флага автор
должен определяться однозначно; coverage может определить его по `reviewer`. Простой сбор `discover`
не создаёт авторство изучения: нужен содержательный отчёт. В исходных разборах
и `brief-map` автор задан полем `actor`; blind/acceptance сохраняют исходного
`reviewer`. Не переименовывай автора ради прохождения проверки. Один и тот же
blind-приёмщик продолжает итоговое сопоставление после открытия реестра.

`status.phaseAuthorship` показывает `authors`, `missingPhases` и
`costAllocation: "none; usage counted once per actual actor and call"`.
Usage привязывается к настоящему участнику и вызову один раз, не распределяется
повторно между фазами. Форма receipt — [contracts](contracts.md#авторство-фаз-и-новая-политика).

## Закрепление версии и граница совместимости

Python 3.11+ и Git нужны движку. После init продолжай через runtime текущего
прогона: обновление установленной папки его не переписывает. Автоматической
миграции старого журнала на новую версию нет.
Adaptive-критика, авторство фаз, обязательства исполнения, повторное
использование финальной сверки и карта отказных границ включаются только
новым `init`. Не меняй сохранённые policy, попытки и receipts старого прогона.

Документация форматов сред: [Codex](https://learn.chatgpt.com/docs/build-skills),
[Claude Code](https://code.claude.com/docs/en/skills), [Cursor](https://cursor.com/docs/skills).
Это ссылки на форматы, не доказательство нативного запуска AISpa. Полные
модельные прогоны alpha.3 во всех трёх приложениях ещё требуют подтверждения.

## Дополнение alpha.4

Во всех средах обязательны изучение проекта перед планом, чтение переданной
истории, критика по закреплённой политике попытки (отдельный приёмщик задачи — в закреплённых adaptive/legacy). Для финала нужен чистый Git-клон
и первоначальные blind-наблюдения. Clean-clone имеет отдельные нативные пути
POSIX и Windows; результат каждого подтверждает соответствующая строка CI. Клон не является
сетевой/файловой песочницей. Выбор model tier — рекомендация; доступность
конкретной модели и фактические usage-метрики задаёт среда.

## Нативная Windows · alpha.5

Нужны CPython 3.11+ и Git for Windows. Используй python.exe или py -3,
доступные в текущей среде; скрипт сам выдаёт JSON/ошибки в UTF-8 и принимает
UTF-8 с BOM на внешней границе ввода. PowerShell5 перенаправлением `>` создаёт
UTF-16: сохраняй JSON/бриф через WriteAllText с UTF8Encoding либо PowerShell7.

```powershell
$Python = (py -3 -X utf8 -c "import sys; print(sys.executable)").Trim()
$Skill = 'C:\Work\Project\.agents\skills\aispa\tools\aispa.py'
& $Python $Skill update-check
```

После init используй закреплённый runtime. Чистая проверка запускает команду
в клоне: `.venv\Scripts\python.exe` допустим как clone-relative executable.
Создай venv и установи зависимости внутри клона, не используй source/.venv.
Для npm.cmd/скрипта .bat указывай cmd.exe либо PowerShell явно: shell не
подставляется молча. SystemRoot сохраняется, user HOME/AppData/TEMP изолированы.

```powershell
& $Python $Skill --root 'C:\Work\Project' clean-prepare
& $Python $Skill --root 'C:\Work\Project' clean-verify -- $Python -m venv .venv
& $Python $Skill --root 'C:\Work\Project' clean-verify -- '.venv\Scripts\python.exe' -m pip install --require-hashes -r requirements.lock
& $Python $Skill --root 'C:\Work\Project' clean-verify -- '.venv\Scripts\python.exe' -m unittest discover -s tests -v
```

В примере `$Skill` уже должен указывать на runtime текущего прогона. Каждая
команда должна завершиться с кодом 0; установка не заменяет финальный тест.
Пути в JSON zones/readZones и артефактах всегда относительные с `/`, не
`C:folder` и не `\folder`. Junctions и подмены управляемых каталогов запрещены.

Git LF/CRLF учитывается только как точная нормализация текстовых окончаний
строк; изменение содержимого, binary/-text, индекса и untracked файлов не
маскируется. Tracked symlinks, submodules, внешние Git-фильтры/encoding/ident
и Git SHA-256 repositories пока отклоняются. Это не sandbox; полная изоляция
системных пакетов и сетевые/нестандартные файловые системы не заявляются.

## Порядок передачи alpha.9

Обычные README/архитектура/решения/словарь создаются вместе с задачами до
критики. После проверок задач их сохраняют как tracked Git-файлы вместе
с кодом. Затем запускают свежий `verify --purpose check` и сохраняют
`handoff --file …` с подлинными execution refs. Порядок последней сверки
волны и clean-prepare/clean-verify → blind → acceptance описан один раз
в [фазе приёмки](../phases/05-accept.md): для одной завершённой задачи в одной
волне новая политика допускает производную сверку из итоговой приёмки. После неё публичные документы не дописывают
как часть private knowledge curation. Нативная Windows должна реально
выполнить этот путь; локальный POSIX PASS не заменяет Windows.

Python-команду в handoff отображай переносимо: `runner: "python3"`,
`"python"` или `"py -3"` только если выбранный alias реально доступен
в текущей среде и указывает на интерпретатор первого argv receipt. Для
`py -3` проверяется доступный launcher. Примеры с `python3` относятся к
POSIX; на Windows не предполагают его наличие.
Поле `display` должно буквально совпадать с вычисленным отображением и
находиться в указанном разделе документа. `runner: null` оставляет
платформенное quoting argv (на Windows — PowerShell); личный домашний путь
и абсолютный executable без проверенного переносимого alias тогда запрещены.
Подлинный
receipt проверяет исполнение, но не гарантирует удобство команды для других
машин. Проверка текущего alias не доказывает его наличие на другой ОС.
Неподдерживаемые нативные argv на Windows отвергаются, а не объявляются
исполняемой PowerShell-строкой. Нативное выполнение этого отображения
проверяется отдельно в Windows CI для точного commit.
Не переноси в публичный документ абсолютные пути исходной машины.
