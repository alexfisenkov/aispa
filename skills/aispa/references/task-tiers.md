# Классы задач · 0.1.0

Читай при классификации плана, повышении риска или сдаче light-финала.
Политика `taskTiers` включена только в новых прогонах. Старые попытки и их
контрольные суммы остаются на закреплённом runtime и прежнем маршруте.

## Выбор до исполнения

По умолчанию `tier: heavy`. `risk: low`, короткий diff или расширение файла
сами по себе не разрешают обход независимых проверок. Light требует явных
`tierReason`, `risk: low`, `riskReason` и одного `changeKind`:

- `documentation`: обычные `.md`, `.txt`, `.rst`;
- `formatting`: оформление этих документов или `.css`;
- `presentation`: `.css`, `.png`, `.jpg`, `.jpeg`, `.webp`.

В `zones` — 1–12 конкретных файлов, без каталогов, wildcard и `.`. Нельзя
менять исполняемые файлы, ссылки, логику, данные, доступы, зависимости,
публичные контракты, конфигурацию и инструкции агентам. Движок отсеивает
известные опасные пути, но не доказывает смысловую безопасность содержимого.
Если CSS скрывает обязательное предупреждение или текст меняет договорённый
контракт, выбирай heavy. При сомнении — heavy. ReadZones могут быть шире:
чтение не разрешает запись. Сохраняются требования, критерии и зависимости.

Пример полей задачи:

```json
{
  "tier": "light",
  "tierReason": "Исправляем опечатки в существующей справке без изменения инструкций запуска",
  "changeKind": "documentation",
  "risk": "low",
  "riskReason": "Обратимая правка текста, без кода и публичных контрактов",
  "zones": ["docs/help.md"]
}
```

Это фрагмент: обычные id/title/requirements/criteria/dependsOn/readZones
по-прежнему обязательны по контракту плана. Группировка задач не понижает
heavy и не стирает прежнюю критику.

## Исполнение

Light получает одну карточку worker. Сохрани настоящее назначение, выдай
контекст, запиши test-intent, выполни актуальную адресную проверку. Worker
заполняет свою форму с критериями и доказательствами. `submit` создаёт
неизменное `verifiedCompletion` и завершает задачу. Critic1, critic2,
task-acceptor и `complete` для неё не нужны. Это проверенное выполнение,
а не независимая приёмка продукта; фиктивных PASS критиков нет.

Heavy: worker → проверка → submit → critic1. PASS ведёт к отдельному
acceptor → complete. WARN/BLOCK/FAIL ведёт через repair-plan → исправление
→ проверка → repair → свежий critic2 → acceptor. Не более двух кругов.
Non-PASS второго критика или acceptor блокирует попытку. Legacy two_rounds
сохраняет прежний контракт. Новое имя, reset и replan не сбрасывают историю.

Новый риск требует `promote-task T01 --reason "конкретная причина"`.
Повышение сохраняет исходное объявление плана, историю и отдельное разрешение
эскалации; новая попытка получает heavy-карточки и новое назначение worker.
Старое завершение не переносится в неё. До назначения нового heavy-worker
разрешено перепланирование с явным heavy: прежние требования сохраняются
точно, критерии, зоны и зависимости можно только расширить, риск не снижается.
После назначения контракт вновь заморожен. Понижение после начала не разрешено.
Нельзя изменять журнал, tier или receipts вручную ради прохождения барьера.

Оценка ролей: одна для light, 3–4 для heavy; общие роли считаются отдельно.
Это структура процесса, не измеренная экономия токенов или лимит всех запусков.

## Общий обзор и приёмка

Для всего плана остаётся одна финальная задача, которая зависит от остальных
и читает всё дерево проекта. Если она heavy, общий `branchReview` проходит
в её штатных выполненных кругах критики. Если light, после текущих доказательств
всех задач нужен один отдельный общий обзор:

1. Зарегистрируй настоящего свежего `integration-reviewer` через `participant`.
   Он независим от всех исполнителей и итогового blind-приёмщика.
2. `integration-review --actor <id>` возвращает текущий контекст и пустой
   `template`. Сохрани их как JSON в служебной папке и передай проверяющему
   вместе с [инструкцией](../prompts/integration-reviewer.md).
3. Проверяющий читает весь diff и заполняет пять осей. Сохрани его файл через
   `integration-review --file <report> --actor <id>`.
4. Только актуальный PASS разрешает handoff и clean clone. FAIL сохраняется;
   нельзя переписать его вердикт для прежнего кандидата. Новый кандидат
   требует нового независимого проверяющего. Найденный риск повышает
   затронутую задачу до heavy; прежние доказательства нужно восстановить.

Структура отчёта ровно `basis`, `reviewer`, `independent: true`, `verdict`
(`PASS|FAIL`), `branchReview`. Вложенные basis/code/files/changes берутся из
текущей формы; каждая из осей behavior/integration/maintainability/data_security/
test_quality имеет реальную оценку, объяснение и доказательство. Пустая форма
не даёт PASS. Отчёт связан с полным текущим кодом, исходным снимком и actor.

Независимо от классов сохраняются сверка всего брифа на границах волн,
handoff, проверка точного commit в чистом клоне, blind-наблюдения по исходному
брифу и итоговая acceptance. Ни worker, ни общая схема отчёта не заменяют
проверяющего. Реальность native identity подтверждает среда, не декларация.
