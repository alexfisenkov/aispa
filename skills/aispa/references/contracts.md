# Данные и отчёты

Все JSON-файлы — UTF-8. Готовь их в `.aispa/inbox/`. Путь к текущему прогону
получи через `context`; `artifact` в отчёте указывает внутрь его `evidence/`.
CLI не принимает произвольный ручной статус «готово».

## Требования

```json
[
  {
    "id": "R01",
    "text": "Посетитель отправляет заявку",
    "kind": "requested",
    "brief": "B001",
    "quote": "посетитель отправляет заявку",
    "core": true,
    "acceptance": ["После отправки посетитель видит подтверждение"]
  },
  {
    "id": "A01",
    "text": "Сохранение черновика формы",
    "kind": "addition",
    "parent": "R01",
    "core": false,
    "acceptance": ["После обновления страницы введённый текст сохранён"]
  }
]
```

`requested` и `constraint` требуют дословной цитаты из названного брифа.
Для `addition` нужен существующий родитель исходного брифа; такие записи не
могут стать ядром. ID: R/G/A/X и минимум две цифры. Повторный ID запрещён.
`core` — boolean, не строка. Условия приёмки непустые и уникальные.

## План

```json
[
  {
    "id": "T01",
    "title": "Отправка заявки",
    "requirements": ["R01"],
    "dependsOn": [],
    "zones": ["src/form", "tests/form"],
    "criteria": ["Пользователь видит подтверждение отправки"]
  },
  {
    "id": "T02",
    "title": "Черновик формы",
    "requirements": ["A01"],
    "dependsOn": ["T01"],
    "zones": ["src/form", "tests/form"],
    "criteria": ["Ввод переживает обновление страницы"]
  }
]
```

Волны вычисляет движок. Пересечение зон переносит задачи в разные волны.
Все действующие требования должны иметь задачи. Неизвестный ID, цикл,
пустой план или потерянное требование отклоняются до записи плана.

## Покрытие спецификацией

Сначала выполни `context --kind coverage`. Впиши **точный** возвращённый `basis`:

```json
{
  "basis": "<из context>",
  "reviewer": "идентификатор отдельного проверяющего",
  "independent": true,
  "unmapped": [],
  "checks": [
    {"requirement": "R01", "status": "covered", "specQuote": "<точная цитата из спецификации>"},
    {"requirement": "A01", "status": "partial"}
  ]
}
```

Статусы: `covered`, `missing`, `partial`. Последние два и непустой `unmapped`
делают проверку неуспешной. Список включает каждое действующее требование
ровно один раз. `unmapped` — требования из брифа, которых нет даже в реестре.

## Задача, волна, финальная приёмка

Получай context соответствующего вида **после** последней проверки кода.
Пример финального отчёта с одним условием:

```json
{
  "basis": "<из context>",
  "reviewer": "идентификатор проверяющего",
  "independent": true,
  "unmapped": [],
  "checks": [
    {
      "requirement": "R01",
      "criterion": "После отправки посетитель видит подтверждение",
      "status": "passed",
      "artifact": "evidence/<реальный файл>.log",
      "note": "Выполнен сценарий отправки; подтверждение показано"
    }
  ]
}
```

`criterion` совпадает с условием из реестра дословно. В отчёте **задачи**
поле `requirement` содержит ID задачи (`T01`), а `criterion` — её критерий.
В отчётах волны и приёмки используются ID требований и их критерии.
Статусы: `passed`, `failed`, `not_tested`, `blocked`. Успех требует непустого
файла доказательства; остальные статусы требуют объяснения и остаются видимыми.
Все пары ID/критерий должны быть перечислены ровно один раз.

`verify` создаёт лог автоматически и возвращает его путь в `verification.output`.
Другие доказательства — скриншоты, записи воспроизведения, отчёты реального
запуска — можно сохранять в `evidence/` текущего прогона. Не подкладывай вместо
них бриф, собственное обещание или выдуманный вывод инструмента.

Слово `independent` — проверяемое обязательство организатора, а не
криптографическое удостоверение личности проверяющего. Движок проверяет схему,
полноту, источник цитат, существование и контрольные суммы файлов, текущую
редакцию проекта. Истинность наблюдений и смысл соответствия брифу требуют
независимого чтения и реального запуска продукта.

## Хранение и ошибки

`.aispa/runs/<run>/events.jsonl` — журнал с цепочкой контрольных сумм и
снимками состояния. `status.json` — производное представление, не источник
готовности. Брифы и спецификации сохраняются отдельными неизменными файлами.

Код 0 означает выполненную команду или пройденную конкретную проверку.
Код 2 — нарушение контракта либо отрицательную проверку. Не превращай его в
успех конвейером shell или ручной записью. Журнал защищает от обнаруживаемого
повреждения и случайного редактирования; это не защита от владельца файлов,
который намеренно перепишет всю историю и контрольные суммы.
