# Данные и отчёты · 0.1.0-alpha.4

JSON — UTF-8; входы готовь в `.aispa/inbox/`. Пакет контекста получай после
последней проверки кода. `context … --write` сохраняет его и возвращает file,
sha256, absolutePath и basis; обычный context печатает полный пакет.
Записывающие команды возвращают компактную квитанцию, не весь журнал.

## Требования

```json
[
  {
    "id": "R01", "text": "Посетитель отправляет заявку",
    "kind": "requested", "brief": "B001",
    "quote": "посетитель отправляет заявку", "core": true,
    "acceptance": ["После отправки посетитель видит подтверждение"]
  },
  {
    "id": "A01", "text": "Сохранение черновика формы",
    "kind": "addition", "parent": "R01", "core": false,
    "acceptance": ["После обновления страницы введённый текст сохранён"]
  }
]
```

Requested и constraint требуют дословную цитату указанного брифа. Addition
ссылается на исходного родителя и не становится ядром. ID: R/G/A/X и минимум
две цифры; повторное использование запрещено. Core — boolean. Критерии
непустые и уникальные. Scope меняется только отдельной командой с новой
цитатой владельца; техническая трудность не считается разрешением.

## План и зависимости

```json
[
  {
    "id": "T01", "title": "Отправка заявки", "requirements": ["R01"],
    "dependsOn": [], "zones": ["src/form", "tests/form"],
    "readZones": ["src/api/schema.json"],
    "criteria": ["Пользователь видит подтверждение отправки"]
  },
  {
    "id": "T02", "title": "Черновик формы", "requirements": ["A01"],
    "dependsOn": ["T01"], "zones": ["src/form", "tests/form"],
    "readZones": [], "criteria": ["Ввод переживает обновление страницы"]
  }
]
```

Движок вычисляет wave. Все действующие требования должны быть покрыты.
Пустой план, неизвестный ID, цикл и потерянное требование отклоняются.
Zones — область записи; readZones — дополнительные входы. Чтение включает
транзитивные зависимости и общие файлы проекта. Пересечение записи одной
задачи с чтением/записью другой требует явной цепочки dependsOn; одного
разнесения по волнам недостаточно. Не переименовывай проверенную задачу,
чтобы сбросить историю критиков.

## Специализации команды

`plan` создаёт карточки всех четырёх ролей. Необязательный `team --file …`:

```json
{
  "tasks": {
    "T01": {
      "worker": {"specialization": "Форма и обработка отказов", "checks": ["Повторная отправка не создаёт дубль"]},
      "critic1": {"specialization": "Логика и крайние случаи", "checks": ["Проверен повторный запрос"]},
      "critic2": {"specialization": "Независимая перепроверка", "checks": []},
      "acceptor": {"specialization": "Сценарий посетителя", "checks": []}
    }
  }
}
```

Дополнительные checks добавляются к критериям задачи и стандартным проверкам
роли, не удаляют их. Карточки включают полный набор источников, ограничения,
спецификацию, зоны, зависимости и ID попытки. После первого критика они
заморожены. Перенастройка до критики сбрасывает назначения участников.

## Покрытие спецификацией

Пакет: `context --kind coverage --write`. Отчёт:

```json
{
  "basis": "<точный basis пакета>", "reviewer": "<отдельный проверяющий>",
  "independent": true, "unmapped": [],
  "checks": [
    {"requirement": "R01", "status": "covered", "specQuote": "<точная цитата спецификации>"},
    {"requirement": "A01", "status": "partial"}
  ]
}
```

Каждое действующее требование встречается один раз. Missing, partial или
непустой unmapped означают отказ. Unmapped содержит просьбы брифа, потерянные
даже при составлении реестра.

## Общая часть отчёта задачи

Сначала нативный агент создаётся средой, затем assign записывает действительные
runtime/native-id/session. В reviewer указывается **receipt.actor из assign**.
Для каждого этапа получай `context --kind task --task T01 --role <role> --write`.
Все пары expectedChecks должны попасть в checks ровно один раз:

```json
{
  "basis": "<basis текущего пакета>", "reviewer": "<receipt.actor>",
  "independent": true, "unmapped": [],
  "checks": [
    {
      "requirement": "T01", "criterion": "<точный критерий из expectedChecks>",
      "status": "passed", "artifact": "evidence/<реальный файл>.log",
      "note": "<наблюдавшееся поведение и результат>"
    }
  ]
}
```

Пример показывает форму одной строки, не готовый полный отчёт. Статусы:
passed, failed, not_tested, blocked. Каждой строке нужна note. Passed требует
непустой файл evidence внутри текущего прогона; остальные статусы сохраняют
объяснение. Адресная проверка `verify --task T01 -- …` должна быть успешной и
актуальной. Её output доступен в verification пакета. Скриншоты и прочие
свидетельства сохраняй в evidence; не подменяй их обещанием или брифом.

Worker использует свои expectedChecks и сдаёт через submit; поле independent
ему не требуется. Critic1, critic2 и acceptor требуют independent: true и
отдельных свежих контекстов. Подпись одним actor разных ролей запрещена.

## Поля двух критиков и исправления

Критик каждого раунда добавляет findings, включая пустой список при отсутствии
замечаний. Каждое замечание имеет уникальные id, severity (`blocking` или
`note`), text и criterion из expectedChecks его роли. Blocking, непрошедшие
checks или unmapped не дают PASS.

```json
{
  "findings": [
    {"id": "F01", "severity": "blocking", "criterion": "<критерий роли>", "text": "<подтверждённая проблема>"}
  ]
}
```

После FAIL первого раунда исполнитель заново проверяет код и передаёт repair
с обычными worker checks и двумя полями:

```json
{
  "previousReport": "<SHA-256 отчёта critic1>",
  "addresses": ["F01"]
}
```

Addresses содержит ровно все blocking ID первого отчёта. Receipt исправления
сохраняет SHA отчёта, кандидата, проверки и историю предыдущих исправлений.

Второй критик обязателен после любого первого результата. Дополнительные поля:

```json
{
  "previousReport": "<SHA-256 отчёта critic1>",
  "repairReceipt": "<SHA-256 отчёта repair либо null после первого PASS>",
  "resolutions": [
    {"id": "F01", "status": "resolved", "note": "<что проверено>", "artifact": "evidence/<файл>.log"}
  ]
}
```

При первом PASS поле repairReceipt — JSON null, resolutions — пустой список,
кандидат не меняется. После исправления resolutions разбирает каждый blocking
ID: resolved/rejected требуют evidence, unresolved блокирует PASS. Findings
второго критика отдельно отражает вновь найденное. Неудача второго раунда
закрывает попытку; третьего раунда нет.

## Приёмщик задачи

После двух критиков отчёт отдельного acceptor передаётся в complete. Его
expectedChecks охватывают карточку, задачу, всех предков и общие ограничения.
Добавь previousReport с SHA отчёта critic2 и **точный inheritedProofs** из
пакета: ссылки `{task, attempt, report}` на принятые доказательства всех предков.
Даже при отсутствии зависимостей передаётся пустой массив.

Trace содержит ровно исходные требования из traceRequirements; для addition
пакет возвращает исходного родителя. Каждая строка:

```json
{
  "requirement": "R01", "brief": "B001", "quote": "<точная исходная цитата>",
  "result": "aligned", "note": "<сопоставление результата со словами владельца>",
  "artifact": "evidence/<файл>.log"
}
```

Result: aligned или drift. Приёмщик читает полный бриф до реестра и отмечает
потерянное в unmapped. Drift или непрошедшая проверка блокирует задачу.
Исторический предок может подтверждаться свежим принятым потомком только
через явные зависимости, inheritedProofs и перепроверку всех его критериев.

## Волна и финальная приёмка

Выполни общую verify без --task. Получи context вида wave или acceptance.
Общая форма отчёта аналогична; reviewer обозначает отдельного проверяющего,
independent обязателен. Checks перечисляет каждую пару ID требования и его
условия приёмки. Приёмка задач не заменяет эти сверки полного брифа.
Последняя волна должна иметь свежий basis перед следующей волной и финалом.

## Хранение и ограничения доказательств

Events.jsonl содержит цепочку снимков состояния; taskHistory — попытки,
карточки, участников, отчёты, исправления и приёмку. Источники и связанные
записи неизменны. Context и status.json производны; source-map.json связывает
их с run, состоянием, последним событием и контрольными суммами файлов.

Код 0 — успешная команда/проверка, код 2 — нарушение контракта или отказ.
Не скрывай отказ shell-конвейером. Полнота JSON, хеши, записи native ID и
independent не удостоверяют личность модели или истинность наблюдений.
Организатор обязан использовать реальные нативные инструменты и независимое
чтение; проверки поведения выполняются в доступной среде.

## Дополнения alpha.4

План принимает risk low/normal/high и riskReason. Для low объяснение обязательно.
Это рекомендация выбора доступной модели, не замена двух раундов критики.

Discovery и carryover описаны в [continuity.md](continuity.md). Новые прогоны
init требуют свежего исследования до spec/plan и успешной чистой проверки
перед финалом. Исторический PASS не наследуется как текущий.

Clean-prepare возвращает path/head/tree и immutable artifact. Clean-verify
возвращает output и artifact с командой, кодом выхода и признаками изменения
исходника/клона. Финальный отчёт указывает `cleanrun` — SHA его artifact.

Сначала приёмщик получает blind-пакет без реестра и спецификации. Команда
`blind --file …` принимает первичные наблюдения:

```json
{
  "basis": "<из context --kind blind>",
  "reviewer": "<native-ID нового итогового приёмщика>",
  "independent": true,
  "observations": [
    {
      "brief": "B001",
      "quote": "<точная цитата оригинала>",
      "status": "passed",
      "note": "Что проверено в чистом клоне",
      "artifact": "evidence/<фактический-файл>.log"
    }
  ]
}
```

Статусы: passed, failed, not_tested, blocked. Passed требует evidence.
Покрывается каждый текущий B-источник; у исторических H-источников проверяются
applicableQuotes нынешнего поручения, остальные старые слова служат контекстом.
Точный смысл и полноту наблюдений определяет приёмщик; проверка присутствия
цитат не заменяет его работу. Один и тот же набор первичных наблюдений нельзя
перезаписать после раскрытия реестра. Новый кандидат требует нового basis.

После записи blind доступен context --kind acceptance. К прежнему финальному
JSON с checks/unmapped добавляются:

```json
{
  "cleanrun": "<SHA cleanrun.artifact>",
  "blindReport": "<SHA blindReview.report>",
  "blindMapping": [
    {"observation": 0, "requirement": "R01"}
  ]
}
```

Это дополнение к полному отчёту, не самостоятельный отчёт. Reviewer остаётся
тем же приёмщиком. Нулевые индексы observations перечисляются ровно один раз.
Наблюдение должно быть связано с исходной цитатой требования; для унаследованной
работы — с её первоначальным источником. Потерянное требование сопоставляется
с null и явно заносится в unmapped, успешная сдача тогда невозможна.

Если более поздним решением владельца требование снято/перенесено, сопоставление
должно явно содержать scopeDecision с точным объектом decision этого требования.
Так учитывается как первоначальный запрос, так и его изменение. Прежняя
невыполненная просьба после разрешённой отмены не выдаётся за реализованную:
она остаётся исключением по решению владельца. Этот механизм не скрывает
неуспешное действующее требование.

Большой context --write разделён на конверт и sections. В каждой ссылке есть
file/sha256/absolutePath. Данные не удаляются: полный набор проверок/источников
нужно прочитать из секций. envelopeBytes — байты, tokenCount null означает,
что реальные токены не измерялись. Usage формат — в continuity.md.
