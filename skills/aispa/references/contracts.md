# Данные и отчёты · 0.1.0-alpha.9

## Каталог документов alpha.7

`state.documents` связывает относительный путь источника с неизменным артефактом
`{file, sha256}`. Описание содержит `sourceSha256`, `bodySha256`, `summary`,
`summaryOrigin` (`extractive` или `semantic`). Оно не участвует в доказательстве
выполнения требования и не заменяет его исходные источники.

`documents` по умолчанию возвращает `format: compact`: `path`, `status`
(`fresh`, `stale`, `missing`, `unavailable`) и только актуальное `summary`
до 160 символов. При необходимости добавляются `summaryTruncated` и
`headerNeedsRefresh`. Выдача ограничена 48 строками и 12 000 символами
сериализованных строк. `--detailed` сохраняет диагностические поля хешей,
происхождения и `header.bodyMatches`, `summaryMatches`, `needsRefresh`;
его пределы — 48 строк, 48 000 символов строк и 600 символов описания.
Поля `omitted` и `limits` объясняют неполноту; `--path` выбирает нужные источники.

`context` не включает каталог, если все зоны чтения и записи выбранных задач
задают точные допустимые существующие файлы. Повторяемый `--source` позволяет
передать уже известные файлы при широких зонах; для task допускаются только
его zones/readZones, включая зависимости, или общие входы. `documentRouting`
объясняет отсутствие каталога либо выбор компактной навигации. В варианте без
каталога `documentWarnings` проверяет все выбранные и зарегистрированные общие
источники без лимита 48; большой список сохраняется в sections целиком.
Каталоги и будущие пути оставляют компактный каталог. Выбор навигации не меняет
basis, обязательные брифы, readZones или expectedChecks. Coverage без явных
источников не нуждается в каталоге; blind не принимает `--source` и не содержит
каталога. Подробные причины и статусы — в [documents.md](documents.md).

`document --path … --sha256 … --summary …` регистрирует описание только для
прочитанных байтов. `--write-header` отдельно разрешает запись управляемого
заголовка в поддерживаемый Markdown. `documents --refresh [--path …]` обновляет
извлечённые ориентиры без изменения исходников. `discover` возвращает
`receipt.documentRegistration`, включая пропущенные регистрации. Полный порядок —
[documents.md](documents.md).

JSON — UTF-8; входы готовь в `.aispa/inbox/`. Пакет контекста получай после
последней проверки кода. `context … --write` сохраняет его и возвращает file,
sha256, absolutePath и basis; обычный context печатает полный пакет.
Записывающие команды возвращают компактную квитанцию, не весь журнал.

## Требования

```json
[
  {
    "id": "R01", "text": "Посетитель отправляет заявку",
    "kind": "requested", "brief": "B001",
    "quote": "посетитель отправляет заявку", "core": true,
    "acceptance": ["После отправки посетитель видит подтверждение"]
  },
  {
    "id": "A01", "text": "Сохранение черновика формы",
    "kind": "addition", "parent": "R01", "core": false,
    "acceptance": ["После обновления страницы введённый текст сохранён"]
  }
]
```

Requested и constraint требуют дословную цитату указанного брифа. Addition
ссылается на исходного родителя и не становится ядром. ID: R/G/A/X и минимум
две цифры; повторное использование запрещено. Core — boolean. Критерии
непустые и уникальные. Scope меняется только отдельной командой с новой
цитатой владельца; техническая трудность не считается разрешением.

## Разбор идеи alpha.8

`idea` возвращает текущий basis и компактное представление; `idea --file …`
сохраняет проверенный отчёт, `idea --full` явно запрашивает полное содержимое.
Новые прогоны требуют свежий ideaReview перед seal и spec. Основание связано
с run, всеми briefs и полным реестром requirements; вычисляемые sealed/core
его не меняют. Исходные слова и решения по объёму остаются отдельным каноном.

Обязательные поля: basis, depth (`compact`/`deep`), depthReason, summary,
anchors, coverage, areas, assumptions, additions, sourceObservations, challenge.
Anchors содержит `{brief, sha256, quote}` для каждого текущего брифа; coverage —
`{requirement, role, proposal}` для каждого действующего требования. Роли
requested → outcome, constraint → constraint, addition → addition.
Areas охватывает 13 фиксированных областей. Оба режима требуют assessed для
problem, user, outcome, alternatives и small_test; это рассмотрение, не
доказательство рыночного спроса. В остальных областях каждый
unknown/not_applicable имеет объяснение.

Предположение имеет text, validation, consequence; предложение дополнения —
parent, text, rationale. Добавления в отчёте не изменяют scope автоматически.
SourceObservations при наличии связываются с сохранённой collection discovery,
точными цитатами и текущими SHA файлов. Они не доказывают спрос или истинность
произвольного вывода. Структурная полнота отчёта не заменяет смысловую проверку.

Полный формат и примеры — [product-development.md](product-development.md).
Отчёт ограничен 48 000 символами, компактный view — 8000 с явным omitted.
Неизвестные поля отклоняются; изменения добавляют новый неизменный артефакт
в ideaHistory. Нельзя переписать требование или выдать исходное за добавление
через разбор идеи.

## План и зависимости

```json
[
  {
    "id": "T01", "title": "Отправка заявки", "requirements": ["R01"],
    "dependsOn": [], "zones": ["src/form", "tests/form"],
    "readZones": ["src/api/schema.json"],
    "criteria": ["Пользователь видит подтверждение отправки"]
  },
  {
    "id": "T02", "title": "Черновик формы", "requirements": ["A01"],
    "dependsOn": ["T01"], "zones": ["src/form", "tests/form"],
    "readZones": [], "criteria": ["Ввод переживает обновление страницы"]
  }
]
```

Движок вычисляет wave. Все действующие требования должны быть покрыты.
Пустой план, неизвестный ID, цикл и потерянное требование отклоняются.
Zones — область записи; readZones — дополнительные входы. Чтение включает
транзитивные зависимости и общие файлы проекта. Пересечение записи одной
задачи с чтением/записью другой требует явной цепочки dependsOn; одного
разнесения по волнам недостаточно. Не переименовывай проверенную задачу,
чтобы сбросить историю критиков.

Для новых прогонов перед записью плана нужен `plan-check --file <черновик>` и
`plan --file <итог> --review <отчёт>`. Отчёт содержит ровно basis, draft, groups,
separate. Basis и нормализованный draft берутся из plan-check. Каждая группа
`{task, from, reason}` связывает итоговую задачу с непустым списком исходных;
исходные задачи распределяются ровно по одному разу. Сохранённая мелкая граница
из suggestions объясняется строкой `{suggestion, reason}` в separate.

Движок проверяет связность группы, точные объединения requirements/zones/readZones,
сохранность каждого критерия, внешние зависимости и непонижение риска.
Совпавший текст критериев разных объединённых задач получает префикс
`<исходный ID>: <исходный текст>` для каждой задачи; остальные тексты остаются
дословными. RiskReason содержит все непустые исходные обоснования дословно.
Полнота проверок и
лимит двух критиков не сокращаются. `taskRoleStartsBefore/After` описывает
четыре роли на задачу; `measuredTokenSavings: null` не является оценкой экономии.
Формат и пример — [product-development.md](product-development.md).

## Специализации команды

`plan` создаёт карточки всех четырёх ролей. Необязательный `team --file …`:

```json
{
  "tasks": {
    "T01": {
      "worker": {"specialization": "Форма и обработка отказов", "checks": ["Повторная отправка не создаёт дубль"]},
      "critic1": {"specialization": "Логика и крайние случаи", "checks": ["Проверен повторный запрос"]},
      "critic2": {"specialization": "Независимая перепроверка", "checks": []},
      "acceptor": {"specialization": "Сценарий посетителя", "checks": []}
    }
  }
}
```

Дополнительные checks добавляются к критериям задачи и стандартным проверкам
роли, не удаляют их. Карточки включают полный набор источников, ограничения,
спецификацию, зоны, зависимости и ID попытки. После первого критика они
заморожены. Перенастройка до критики сбрасывает назначения участников.

## Покрытие спецификацией

Пакет: `context --kind coverage --write`. Отчёт:

```json
{
  "basis": "<точный basis пакета>", "reviewer": "<отдельный проверяющий>",
  "independent": true, "unmapped": [],
  "checks": [
    {"requirement": "R01", "status": "covered", "specQuote": "<точная цитата спецификации>"},
    {"requirement": "A01", "status": "partial"}
  ],
  "ideaChecks": [
    {"probe": "adoption", "status": "covered", "specQuote": "<цитата о спросе или гипотезе>", "note": "Решение отражено."},
    {"probe": "value_cost", "status": "covered", "specQuote": "<цитата о пользе и затратах>", "note": "Решение отражено."},
    {"probe": "operations", "status": "covered", "specQuote": "<цитата об операторе и данных>", "note": "Решение отражено."},
    {"probe": "lifecycle", "status": "covered", "specQuote": "<цитата о повторном применении>", "note": "Решение отражено."},
    {"probe": "actors", "status": "covered", "specQuote": "<цитата о правах участников>", "note": "Решение отражено."}
  ]
}
```

Каждое действующее требование встречается один раз. Missing, partial или
непустой unmapped означают отказ. Unmapped содержит просьбы брифа, потерянные
даже при составлении реестра.

## Общая часть отчёта задачи

Сначала нативный агент создаётся средой, затем assign записывает действительные
runtime/native-id/session. В reviewer указывается **receipt.actor из assign**.
Для каждого этапа получай `context --kind task --task T01 --role <role> --write`.
Все пары expectedChecks должны попасть в checks ровно один раз:

```json
{
  "basis": "<basis текущего пакета>", "reviewer": "<receipt.actor>",
  "independent": true, "unmapped": [],
  "checks": [
    {
      "requirement": "T01", "criterion": "<точный критерий из expectedChecks>",
      "status": "passed", "artifact": "evidence/<реальный файл>.log",
      "note": "<наблюдавшееся поведение и результат>"
    }
  ]
}
```

Пример показывает форму одной строки, не готовый полный отчёт. Статусы:
passed, failed, not_tested, blocked. Каждой строке нужна note. Passed требует
непустой файл evidence внутри текущего прогона; остальные статусы сохраняют
объяснение. Адресная проверка `verify --task T01 -- …` должна быть успешной и
актуальной. Её output доступен в verification пакета. Скриншоты и прочие
свидетельства сохраняй в evidence; не подменяй их обещанием или брифом.

Worker использует свои expectedChecks и сдаёт через submit; поле independent
ему не требуется. Critic1, critic2 и acceptor требуют independent: true и
отдельных свежих контекстов. Подпись одним actor разных ролей запрещена.

## Поля двух критиков и исправления

Критик каждого раунда добавляет findings, включая пустой список при отсутствии
замечаний. Каждое замечание имеет уникальные id, severity (`blocking` или
`note`), text и criterion из expectedChecks его роли. Blocking, непрошедшие
checks или unmapped не дают PASS.

```json
{
  "findings": [
    {"id": "F01", "severity": "blocking", "criterion": "<критерий роли>", "text": "<подтверждённая проблема>"}
  ]
}
```

После FAIL первого раунда исполнитель заново проверяет код и передаёт repair
с обычными worker checks и двумя полями:

```json
{
  "previousReport": "<SHA-256 отчёта critic1>",
  "addresses": ["F01"]
}
```

Addresses содержит ровно все blocking ID первого отчёта. Receipt исправления
сохраняет SHA отчёта, кандидата, проверки и историю предыдущих исправлений.

Второй критик обязателен после любого первого результата. Дополнительные поля:

```json
{
  "previousReport": "<SHA-256 отчёта critic1>",
  "repairReceipt": "<SHA-256 отчёта repair либо null после первого PASS>",
  "resolutions": [
    {"id": "F01", "status": "resolved", "note": "<что проверено>", "artifact": "evidence/<файл>.log"}
  ]
}
```

При первом PASS поле repairReceipt — JSON null, resolutions — пустой список,
кандидат не меняется. После исправления resolutions разбирает каждый blocking
ID: resolved/rejected требуют evidence, unresolved блокирует PASS. Findings
второго критика отдельно отражает вновь найденное. Неудача второго раунда
закрывает попытку; третьего раунда нет.

## Приёмщик задачи

После двух критиков отчёт отдельного acceptor передаётся в complete. Его
expectedChecks охватывают карточку, задачу, всех предков и общие ограничения.
Добавь previousReport с SHA отчёта critic2 и **точный inheritedProofs** из
пакета: ссылки `{task, attempt, report}` на принятые доказательства всех предков.
Даже при отсутствии зависимостей передаётся пустой массив.

Trace содержит ровно исходные требования из traceRequirements; для addition
пакет возвращает исходного родителя. Каждая строка:

```json
{
  "requirement": "R01", "brief": "B001", "quote": "<точная исходная цитата>",
  "result": "aligned", "note": "<сопоставление результата со словами владельца>",
  "artifact": "evidence/<файл>.log"
}
```

Result: aligned или drift. Приёмщик читает полный бриф до реестра и отмечает
потерянное в unmapped. Drift или непрошедшая проверка блокирует задачу.
Исторический предок может подтверждаться свежим принятым потомком только
через явные зависимости, inheritedProofs и перепроверку всех его критериев.

## Волна и финальная приёмка

Выполни общую verify без --task. Получи context вида wave или acceptance.
Общая форма отчёта аналогична; reviewer обозначает отдельного проверяющего,
independent обязателен. Checks перечисляет каждую пару ID требования и его
условия приёмки. Приёмка задач не заменяет эти сверки полного брифа.
Последняя волна должна иметь свежий basis перед следующей волной и финалом.

## Хранение и ограничения доказательств

Events.jsonl содержит цепочку снимков состояния; taskHistory — попытки,
карточки, участников, отчёты, исправления и приёмку. Источники и связанные
записи неизменны. Context и status.json производны; source-map.json связывает
их с run, состоянием, последним событием и контрольными суммами файлов.

Код 0 — успешная команда/проверка, код 2 — нарушение контракта или отказ.
Не скрывай отказ shell-конвейером. Полнота JSON, хеши, записи native ID и
independent не удостоверяют личность модели или истинность наблюдений.
Организатор обязан использовать реальные нативные инструменты и независимое
чтение; проверки поведения выполняются в доступной среде.

## Дополнения alpha.4

План принимает risk low/normal/high и riskReason. Для low объяснение обязательно.
Это рекомендация выбора доступной модели, не замена двух раундов критики.

Discovery и carryover описаны в [continuity.md](continuity.md). Новые прогоны
init требуют свежего исследования до spec/plan и успешной чистой проверки
перед финалом. Исторический PASS не наследуется как текущий.

Clean-prepare возвращает path/head/tree и immutable artifact. Clean-verify
возвращает output и artifact с командой, кодом выхода и признаками изменения
исходника/клона. Финальный отчёт указывает `cleanrun` — SHA его artifact.

Сначала приёмщик получает blind-пакет без реестра и спецификации. Команда
`blind --file …` принимает первичные наблюдения:

```json
{
  "basis": "<из context --kind blind>",
  "reviewer": "<native-ID нового итогового приёмщика>",
  "independent": true,
  "observations": [
    {
      "brief": "B001",
      "quote": "<точная цитата оригинала>",
      "status": "passed",
      "note": "Что проверено в чистом клоне",
      "artifact": "evidence/<фактический-файл>.log"
    }
  ]
}
```

Статусы: passed, failed, not_tested, blocked. Passed требует evidence.
Покрывается каждый текущий B-источник; у исторических H-источников проверяются
applicableQuotes нынешнего поручения, остальные старые слова служат контекстом.
Точный смысл и полноту наблюдений определяет приёмщик; проверка присутствия
цитат не заменяет его работу. Один и тот же набор первичных наблюдений нельзя
перезаписать после раскрытия реестра. Новый кандидат требует нового basis.

После записи blind доступен context --kind acceptance. К прежнему финальному
JSON с checks/unmapped добавляются:

```json
{
  "cleanrun": "<SHA cleanrun.artifact>",
  "blindReport": "<SHA blindReview.report>",
  "blindMapping": [
    {"observation": 0, "requirement": "R01"}
  ]
}
```

Это дополнение к полному отчёту, не самостоятельный отчёт. Reviewer остаётся
тем же приёмщиком. Нулевые индексы observations перечисляются ровно один раз.
Наблюдение должно быть связано с исходной цитатой требования; для унаследованной
работы — с её первоначальным источником. Потерянное требование сопоставляется
с null и явно заносится в unmapped, успешная сдача тогда невозможна.

Если более поздним решением владельца требование снято/перенесено, сопоставление
должно явно содержать scopeDecision с точным объектом decision этого требования.
Так учитывается как первоначальный запрос, так и его изменение. Прежняя
невыполненная просьба после разрешённой отмены не выдаётся за реализованную:
она остаётся исключением по решению владельца. Этот механизм не скрывает
неуспешное действующее требование.

Большой context --write разделён на конверт и sections. В каждой ссылке есть
file/sha256/absolutePath. Данные не удаляются: полный набор проверок/источников
нужно прочитать из секций. envelopeBytes — байты, tokenCount null означает,
что реальные токены не измерялись. Usage формат — в continuity.md.

## Знания по принятому коду alpha.8

После успешной актуальной acceptance назначается новый независимый участник:
`knowledge-assign --runtime … --native-id … --session …`. Пакет
`context --kind knowledge --write` содержит его ID, снимок кода и настоящие
квитанции проверок с digest и короткую выборку `commandHistory`; бриф,
спецификация и чужие ревью не нужны автору
для пересказа намерений. Он изучает фактическую реализацию.

`knowledge-record --file …` принимает basis снимка кода, writer назначенного
участника, entries и uncertainties. Запись имеет key, kind, text, sources;
source — `{path, sha256}`. Kind: command, trap, decision, glossary. Command
дополнительно содержит точный argv и `verification: {kind, sha256}`. Для
alpha.9 `kind: execution`, sha256 — SHA подлинной успешной записи из commands
этого прогона; legacy `project|cleanrun` и digest текущего receipt сохраняют
совместимость. Для каждой
категории без entries обязательно явное объяснение в uncertainties.

История сохраняет происхождение, последовательность и замены supersedes;
текущий код проверяется по SHA. Адресная выдача `knowledge --path … --kind …`
не переносит старый PASS; при изменившемся источнике знание скрывается как
stale. По умолчанию без выбора путей/типов знания не загружаются. Новый finish
требует актуальную запись знаний, отдельно от всех прежних проверок.
Ограничения, схема и пример — [product-development.md](product-development.md).

До 64 локальных отчётов сохраняются между контрольными снимками. Команда
`knowledge-compact` архивирует их без удаления исходников и позволяет продолжить
запись. При новом init снимок создаётся автоматически. В снимке до 128 записей
и 512 KiB их содержимого; предел одного артефакта — 1 MiB. Не вошедшие записи
остаются в неизменном архиве с происхождением.

Обычный query не обходит архив. `knowledge --path … --archive --archive-depth 4`
добавляет ограниченный поиск; глубина 1–64, по умолчанию 4. `archive.unread`
показывает точную ссылку на оставшуюся непрочитанную историю.
`archive.archivedRecordCount` — число отчётов автора, а не уникальных знаний.
При устаревании новой редакции старая не возвращается как действующая.

## Проверяемое развитие продукта alpha.9

Новый `idea --file` требует ровно пять строк `challenge` по probe:
`adoption`, `value_cost`, `operations`, `lifecycle`, `actors`. Строка имеет ровно
`probe`, `status`, `finding`, `decision`, `validation`, `requirements`.
`status` — `resolved|assumption|blocker|not_applicable`; три текстовых поля
непустые, до 1600 символов каждое. `requirements` — непустые уникальные ID
действующих требований. Это структурная проверка, не подтверждение спроса.
`compact` и `deep` различаются обоснованной глубиной, не числом обязательных
вопросов. Неизвестное помечают гипотезой, N/A объясняют предметно.

Независимый отчёт `coverage` для новых прогонов добавляет ровно пять
`ideaChecks`: `{probe, status, specQuote, note}`. `status` —
`covered|missing|partial`. Для `covered` нужна дословная непустая цитата из
текущей спецификации, в которой отражены **выбранное решение и способ его
проверки** из соответствующего challenge. `missing` и `partial` снижают
результат покрытия. Проверяющий сверяет смысл решения, гипотезы или блокера;
автоматический поиск слов не удостоверяет рыночный факт. Вопросы владельцу —
только до `seal` согласно
выбранному `auto|important|interview`; позже координатор принимает и
записывает самостоятельные решения.

Отчёт `plan --review` новых прогонов содержит прежние `basis`, `draft`,
`groups`, `separate` и обязательный `delivery`:

```json
{
  "profile": "feature",
  "reason": "Несколько зависимых частей дают один сценарий пользователя.",
  "slices": [{"id": "S01", "kind": "user", "outcome": "Пользователь завершает сценарий.", "tasks": ["T01"], "demonstration": {"task": "T01", "criterion": "<точный критерий T01>"}, "supports": []}],
  "migrations": [],
  "migrationReason": "У существующего интерфейса нет прежних потребителей или формата для переноса."
}
```

`profile` — `small|feature|system|migration`. Каждый срез содержит ровно
`id, kind, outcome, tasks, demonstration, supports`; задача входит в один
срез, демонстрация ссылается на её настоящий критерий. Нужен хотя бы один
`user`; `enabler` указывает ID пользовательских срезов, которым помогает.
При миграции строка содержит ровно `id, reason, expand, migrate, contract,
consumers, compatibility, rollback`. Три непустых непересекающихся списка
задач задают порядок через `dependsOn`. Каждый `consumer` — `{path, task}`
в зоне записи задачи migrate. Каждая строка compatibility/rollback —
`{task, criterion}` для каждого этапа. На одном этапе критерий rollback
отличается от критерия compatibility; одна проверка не доказывает и
совместимость, и восстановление. Для `profile: migration` список
миграций непуст; иначе пустой допустим с конкретной `migrationReason`.
Проверка схемы не находит неизвестных проектных потребителей сама.

## Диагностика после первого FAIL

Перед `repair` запроси `repair-plan T01` без `--file`: read-only ответ даёт
`basis`, `task`, `attempt`, `firstReport`, `blockingFindings`, `recorded` и
правило маршрутизации. Не вычисляй basis вручную. Затем сохрани
`repair-plan T01 --file <JSON>` с полученным basis. Он связан с ID попытки,
контрактом, первым отчётом критика и исходным worker. Отчёт имеет ровно поля:

```json
{
  "basis": "<текущий repair basis>",
  "cause": "implementation_gap",
  "diagnosis": "Ошибка локализована в обработке пустого входа.",
  "route": "same",
  "reason": "Исходный worker знает верный подход; нужен адресный фикс.",
  "changes": "Исправить ветку пустого входа и повторить критерий.",
  "addresses": ["<каждый blocking finding ID critic1>"],
  "context": []
}
```

`cause`: `implementation_gap|missing_context|wrong_approach|external_blocker`.
`route`: `same|fresh|blocked`. Локальный дефект допускает исходного worker;
недостающий контекст или неверный подход требует нового worker со свежим
контекстом и записанной сильной моделью; внешний блокер остаётся blocked.
`addresses` перечисляет **все** blocking ID первого отчёта. Для fresh
`context` непуст и адресно указывает, что перечитать/проверить. Диагноз
сохраняется неизменно до ремонта; новый worker не создаёт третий раунд.
Два критика и отдельный приёмщик остаются обязательными.

## Реальные команды и передача проекта

`verify [--task T01] [--purpose install|run|check|test] -- <argv>` и
`clean-verify [--purpose …] -- <argv>` по умолчанию используют `check`.
После фактического выполнения, в том числе неуспешного, движок сохраняет
историю `commands`. `commands --kind project|task|cleanrun --purpose …
--limit N` возвращает ограниченные сводки и точный `ref:{id,sha256}` без
сырых логов и локальных путей. `commands --receipt <sha256>` читает одну
точную запись: настоящий argv, назначение, область, attempt, code/candidate,
время, exit code и SHA вывода. Это личный receipt текущего прогона, не
публичный документ и не текущий PASS. Неуспешный receipt нельзя использовать
для проверенной команды знаний или handoff.

Обычные документы проекта создавай внутри задач, чтобы критики и приёмщик
проверили их. После задач и волны сохрани их вместе с кодом в Git, выполни
свежую `verify --purpose check` на текущем коде и только тогда вызови
`handoff --file <JSON>`. Он принимает
существующий документ, не создаёт и не редактирует его. Пример малой работы
для POSIX с реально доступным `python3`; на Windows используй проверенный
`python` или `py -3`, если они ведут к тому же интерпретатору:

```json
{
  "schema": 1,
  "profile": "small",
  "documents": [{"path": "README.md", "sha256": "<SHA файла>", "sources": [{"path": "src/app.py", "sha256": "<SHA исходника>"}], "covers": {"quickstart": "Запуск", "architecture": "Устройство", "decisions": "Решения", "glossary": "Термины"}}],
  "notApplicable": {},
  "decisionDetails": {"choice": "<дословная фраза в разделе Решения>", "alternatives": "<дословная фраза>", "consequences": "<дословная фраза>"},
  "commands": {
    "install": {"notApplicable": "<та же конкретная причина в разделе Запуск>"},
    "run": {"receipt": {"sha256": "<успешный SHA из commands>"}, "document": "README.md", "heading": "Запуск", "display": "python3 -m app", "runner": "python3"},
    "check": {"receipt": {"sha256": "<успешный текущий project check>"}, "document": "README.md", "heading": "Запуск", "display": "python3 -m unittest", "runner": "python3"},
    "singleTest": {"receipt": {"sha256": "<успешный purpose=test>"}, "document": "README.md", "heading": "Запуск", "display": "python3 -m unittest tests.test_one", "runner": "python3"}
  },
  "obligations": []
}
```

Заполнители выше не являются действительным отчётом: `display` должен точно
совпасть с переносимым отображением фактического argv, а текст должен буквально
находиться в объявленном Markdown-разделе. Для Python runner допустимы
`python3`, `python` и `py -3`, только когда выбранный alias доступен в текущей
среде и разрешается в тот же интерпретатор, что первый argv receipt. На
Windows display строится с PowerShell literal quoting; неподдерживаемый
аргумент команды вызывает отказ вместо непроверенной строки. Это не
доказательство, что alias доступен на другой ОС. `runner: null` использует платформенное
отображение argv без личного домашнего пути; абсолютный путь интерпретатора
без переносимого проверенного alias не проходит. Проверка receipt
связывает purpose: `singleTest` ↔ `test`, остальные по имени. `check`
обязателен и должен быть успешной **текущей** общей project-проверкой.
`install`, `run`, `singleTest` могут иметь `{notApplicable: "<причина>"}` с
причиной в quickstart. Категории `architecture`, `decisions`, `glossary` можно
обоснованно исключить только при `profile: small`, записав `notApplicable`
в том же документе. При наличии decisions три `decisionDetails` должны
буквально находиться в соответствующем разделе. Каждый документ имеет
1–12 настоящих tracked source-файлов либо evidence-ссылок, в том числе хотя
бы один проектный файл; один лишь сам документ не является источником.
Каждый blocked task должен быть в `obligations` и в названном разделе.

Валидация проверяет путь, tracked status, SHA, разделы, структуру, секретные
шаблоны и подлинные receipts; она **не удостоверяет смысл, полноту инженерного
объяснения или отсутствие всех приватных сведений**. Ответственность за
содержимое у автора и проверяющего. Handoff связан с текущим code SHA: после
изменения файлов обнови документы, receipt и manifest. Частная knowledge
curation проходит только после успешной итоговой приёмки и не подменяет
обычные документы передачи.
