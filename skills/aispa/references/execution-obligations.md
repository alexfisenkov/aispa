# Обязательства исполнения

Новый `init` включает `executionObligations`. Старый прогон продолжает свой
закреплённый runtime; его журнал и политику не обновляют вручную. Маршрут
поддерживает только `kind: deadline` и события `engine-finish` либо
`host-final-handoff`. Это учёт срока исполнения, а не освобождение от
продуктовых требований или универсальное исключение из приёмки.

## До первого seal

Сохрани полный бриф и прочитай `brief-source`. Срок должен занимать отдельную
исходную единицу; `quote` обязательства буквально равен её `text`. Нельзя
вырезать удобную часть смешанного фрагмента, переписать слова владельца или
переклассифицировать уже зарегистрированное продуктовое требование, включая
ядро. Движок отклоняет пересечение цитат с исходными требованиями того же
брифа. Неподдержанный случай остаётся ограничением, а не скрытым исключением.

Перед фиксацией срока нужен обычный файл свидетельства начала внутри
`evidence/` текущего run. Специальной команды записи start receipt нет.
Возьми проверенный `runDirectory` из `status` (относительно `<project>/.aispa/`).
Следующий POSIX-пример создаёт **новый** UTF-8 файл без перезаписи и выводит
его действительный SHA; замени путь и note фактическими значениями:

```sh
python3 - "<project>/.aispa/runs/<run>/evidence/execution-start.json" <<'PY'
from datetime import datetime, timezone
from pathlib import Path
import hashlib, json, sys

target = Path(sys.argv[1])
at = datetime.now(timezone.utc).isoformat()
value = {"event": "execution-start", "at": at,
         "note": "Фактическое начало исполнения; укажите наблюдаемое основание."}
raw = (json.dumps(value, ensure_ascii=False) + "\n").encode("utf-8")
target.parent.mkdir(parents=True, exist_ok=True)
with target.open("xb") as output:
    output.write(raw)
print(json.dumps({"startedAt": at, "startEvidence": {
    "file": "evidence/" + target.name,
    "sha256": hashlib.sha256(raw).hexdigest()}}, ensure_ascii=False))
PY
```

Проверь выбранный каталог до записи; не используй symlink и не редактируй
`events.jsonl`, active pointer или сохранённые receipts. Свидетельство должно
описывать наблюдавшееся начало: время создания файла само по себе не доказывает
более раннее начало работы. `startedAt` должен точно совпадать с `at` файла,
не быть в будущем и не быть позже `deadline`. Все времена — ISO 8601 с зоной.
На Windows тот же Python-код можно сохранить в обычный локальный скрипт и
запустить доступным `python`/`py -3`; shell heredoc не является PowerShell.

Сначала подготовь оба независимых исходных разбора срока с аннотациями,
описанными ниже; затем сформируй запись ledger по совпавшей интерпретации.
JSON для `execution-obligation --file .aispa/inbox/deadline.json` содержит
ровно эти восемь полей. Значения в угловых скобках — заполнители:

```json
{
  "id": "E01",
  "kind": "deadline",
  "event": "engine-finish",
  "brief": "B001",
  "quote": "<полный точный text отдельной единицы brief-source>",
  "startedAt": "<фактическое at из свидетельства начала>",
  "startEvidence": {
    "file": "evidence/execution-start.json",
    "sha256": "<SHA-256 точных байтов этого файла>"
  },
  "deadline": "<срок из поручения в ISO 8601 с часовым поясом>"
}
```

Команды здесь и далее передаются закреплённому
`tools/aispa.py --root <project>`. ID имеет вид `E` и минимум две цифры;
повторный ID не заменяет запись. Запись допускается только в running до
первого `seal`, до spec и задач. Движок добавляет `run`, `recordedAt` и
`record: {file, sha256}`. `execution-obligations` перечитывает обязательства
и показывает `sealed`, `results`, `externalReceiptSupported: false`.

В обоих исходных разборах (`brief-extract` и независимом `brief-review`)
срок остаётся `kind: intent`. Каждый читатель самостоятельно добавляет в
соответствующий `units[]` поле `execution`, прочитав только исходный бриф.
Ему нельзя передавать выбранные координатором event/deadline или ledger.
`brief-source` и исходный шаблон этих данных не раскрывают.

Для абсолютного срока форма такая:

```json
"execution": {
  "event": "host-final-handoff",
  "deadline": "2026-10-21T12:00:00+00:00"
}
```

Для относительного бюджета, например десяти минут, используется другая форма:

```json
"execution": {
  "event": "host-final-handoff",
  "budgetSeconds": 600
}
```

Допустимы ровно `event` и одно из `deadline`/`budgetSeconds`. Бюджет —
положительное целое число секунд. Оба независимых разбора должны совпасть:
абсолютные времена сравниваются после приведения к UTC. Ledger обязан сохранить
то же событие и абсолютный срок; для бюджета разность `deadline - startedAt`
должна точно равняться `budgetSeconds`. Отсутствие аннотации хотя бы у одного
читателя, разные события или разные сроки блокируют карту и seal.

Если в цитате буквально написан `engine-finish` или `host-final-handoff`,
движок дополнительно проверяет это событие. Если есть буквальные ISO-времена,
для абсолютного срока выбранный deadline должен совпасть с одним из них.
Для независимо подтверждённого `budgetSeconds` буквальное время может быть
началом: оно должно совпасть с `startedAt` или deadline, а разность времён —
с бюджетом. У ISO-времени без зоны проверяется локальная дата и
время; выбор зоны остаётся явной интерпретацией независимых читателей.
Эти проверки не доказывают смысл произвольной естественной речи: перевод
«отправь финальный ответ» в `host-final-handoff` выполняет независимый
исходный читатель, а не автор ledger в процессе приёмки своей классификации.

После сохранения обоих исходных отчётов и регистрации обязательства проверяющий
берёт свежий `brief-map-context`. В строке используются точные `brief/start/end`,
`disposition: execution`, `requirements: []`, `executionObligations: ["E01"]`
и содержательная `reason`. Quote обязательства по-прежнему равен всему text
отдельной единицы. `seal` сохраняет состав, независимую карту и обе ссылки
`sourceReports`; при finish эти исходные аннотации перечитываются.

## Blind-наблюдение и результат

Первичный blind-отчёт сохраняется до открытия реестра. Он может честно
содержать `not_tested`/`blocked` для события, которое ещё не произошло.
При последующем сопоставлении каждое наблюдение сохраняется. Дополнение к
полной итоговой форме:

```json
{
  "blindMapping": [{
    "observation": 0,
    "requirement": null,
    "executionObligation": "E01",
    "executionRecord": "<SHA исходной record обязательства E01>"
  }]
}
```

`brief` и `quote` наблюдения должны точно совпасть с заранее зафиксированным
обязательством. `scopeDecision` в такой строке запрещён. Движок сохраняет
находку отдельно как `executionFindings`; наблюдение не удаляется и его статус
не переписывается. Ошибка продукта и потерянная просьба этим маршрутом не
снимаются. Поля полного отчёта и авторство — [contracts](contracts.md).

При `finish` берётся одно фактическое время: `engine-finish` получает passed
при `at <= deadline`, иначе failed. `host-final-handoff` всегда pending,
с `at: null`; отдельно сохраняется, истёк ли срок. Поздняя квитанция host
пока не реализована: будущую отправку нельзя подтвердить заранее, а событие
движка нельзя переименовать в отправку. `status.remaining.execution` до finish
показывает pending, после — фактические неуспешные/ожидающие результаты.
При них итог — `delivered_with_remaining`, даже если продукт принят.

## Следующий прогон

Новый `init` переносит failed/pending исполнение отдельно как
`executionRemainders`; успешный исторический срок не становится новым PASS.
Сохраняются исходная цитата, запись обязательства, начало, seal, оба независимых
исходных разбора срока и результат finish, если он был. Если finish не произошло, результат остаётся pending.
`memory` возвращает ограниченную сводку с `executionOmitted` и ссылкой
`handoff` на полную историю; `status.remaining.inheritedExecution` показывает
отдельные исторические остатки с `historical: true`, `currentProof: false`.

Для исторического ID `CE-…` доступны отдельные решения через существующий
`carry`: `keep`, `defer`, `drop`. Они не включают исполнение в продуктовый scope.
`map` и `resolve` для CE запрещены: новое выполнение продукта не доказывает
старую отправку и не исправляет ранее пропущенный срок.

`keep` сохраняет открытый остаток без новой авторизации. Для `defer` и `drop`
сначала нужен новый бриф владельца в текущем прогоне и дословная цитата его
решения. Копия старого брифа, изменённая цитата и тот же бриф для следующего
изменения решения отклоняются. Пример с действительными ID и словами владельца:

```sh
python3 tools/aispa.py --root <project> carry CE-<id> --action drop \
  --brief B002 --quote "<дословное новое решение владельца снять этот исторический срок>"
```

`drop` означает отказ владельца от дальнейшего учёта этого исторического долга,
а не подтверждение события. Исходный `pending` или `failed`, deadline, запись E
и доказательства остаются неизменными. Движок добавляет receipt с точной связью
с исходными run/E-ID/record SHA и цитатой нового брифа. Это решение и исходный
результат сохраняются в последующих архивах. Поздние host receipts по-прежнему
не поддержаны, статус срока не становится passed.

После `drop` CE остаётся в архивной сводке с `disposition: dropped` и
`timingOutcomeUnchanged: true`, но исключается из активного
`remaining.inheritedExecution`. `defer` остаётся активным остатком; `keep`
не отменяет defer и не открывает уже снятый долг. Пока есть активное
унаследованное исполнение, следующий результат сохраняет
`delivered_with_remaining`. После явно разрешённого снятия всех таких долгов
текущий продукт может завершиться accepted при выполнении остальных проверок.
