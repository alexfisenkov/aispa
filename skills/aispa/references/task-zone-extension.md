# Дополнительные файлы той же попытки

`task-zone-extension` разрешает точные дополнительные файлы для уже записанных
требований heavy-задачи после первого WARN/BLOCK/FAIL. Это техническое уточнение
плана; смысл достаточности прежнего разрешения проверяет координатор. Новые
требования или полномочия этим инструментом не предоставляются.

Команда не меняет attempt ID, класс, риск, зависимости, критерии, политику,
режим, исполнителей, исходную сдачу, первый отчёт и число использованных кругов.
Исходные карточки и test-intent остаются в эпохе 0; ремонт получает новую эпоху.
`previousReport`, `repairReceipt` и все обязательные finding IDs сохраняются.
После второго non-PASS попытка блокируется штатным образом.

Поддерживается только задача со статусом `running` и фазой `repair`; `blocked`
отклоняется до записи расширения. Команда не возобновляет заблокированную задачу.
Нужны зарегистрированный planner/coordinator, исходный автоматический test-intent,
исходный полный снимок первого старта и ещё не использованные потомки. Нельзя
расширять завершённую попытку, первый PASS, вторую критику, сданный ремонт,
назначенный critic2, каталоги, `.`, шаблоны и удалять зоны. До нового ремонта
нужен настоящий новый RED после расширения и затем GREEN; прежний RED не
подтверждает новую эпоху. Старые тестовые источники остаются в истории.
Добавленный путь может отсутствовать или быть обычным файлом.
Имя не обязано иметь расширение: `Dockerfile`, `Makefile`, `LICENSE` допустимы.
Квадратные скобки в `routes/[slug].tsx` — буквальная часть точного имени;
пути не раскрываются как glob. Символы `*` и `?` в запросе запрещены.
При последующем
расчёте кандидата, до и после выполнения проверки и при текущей проверке
test-intent снова проверяется его точный файловый тип. Каталог, ссылка/junction
или специальный файл блокируют использование эпохи; подкаталог не получает
разрешение через префикс. Исторические квитанции при этом сохраняются как история,
а текущая проверка не становится PASS.

До подготовки любых материалов проверяется свободная revision test-intent:
новая эпоха обязательно расходует следующую запись того же операционного
бюджета (в официальной 0.4.0 — 16). История и лимит не сбрасываются.
Переход 15 → расширение → revision 16 допустим; при уже записанных 16
и prepare, и apply отказывают без изменения файлов или журнала.

Если `repair-plan` уже выбрал `fresh` и новый worker назначен, расширение
сохраняет это назначение. Прежняя диагностика остаётся неизменной историей,
но её basis не подходит новой эпохе. Нужно явно записать новый `repair-plan`
с актуальным basis и маршрутом `fresh`; после этого тот же назначенный
свежий worker продолжает ремонт. Повторное назначение или смена маршрута
на `same` не разрешаются. В пределах одной эпохи после назначения worker
диагностика по-прежнему заморожена. Если замена ещё не сделана, новый диагноз
`fresh` требует штатного назначения нового worker до ремонта.

Диагностика новой эпохи получает schema 2: contract/epoch, предыдущая
квитанция и позиция журнала проверяются по фактическому append. В provenance
сохраняется назначенный worker; автор текста не записывался CLI, поэтому
`author: null` честно оставляет его неизвестным. Назначенный worker не
выдаётся за автора. Старые schema 1 и их basis не переписываются, автор им
задним числом не приписывается. Цепочка квитанций сохраняется целиком.

Обычный маршрут из текущего закреплённого CLI:

```text
task-zone-extension T01
task-zone-extension T01 --file extension.json --actor <existing-coordinator>
task-zone-extension T01 --file extension.json --actor <existing-coordinator> --apply --expected-journal-sha256 <fresh-sha>
```

Без файла — осмотр. С файлом — проверка полного предлагаемого плана без записи.
`--apply` использует общий замок CLI и свежий CAS журнала. Файл содержит:

```json
{
  "attempt": "<existing-attempt>",
  "contract": "<current-contract>",
  "reason": "Why these files implement the existing approved requirement",
  "files": [
    {"path": "src/example.py", "requirement": "R01", "reason": "Existing implementation criterion"},
    {"path": "tests/test_example.py", "requirement": "R01", "reason": "Regression for that criterion"}
  ],
  "planReview": {"basis": "<plan-check basis>", "draft": [], "groups": [], "separate": []}
}
```

`planReview` — полный штатный разбор из `plan-check` для всего предложенного
плана, включая прежний неизменный `delivery`, если он включён политикой.
Только выбранная задача получает дополнительные `zones`; все прочие поля
плана сохраняются. Обычные DAG, зоны чтения/записи, интерфейсы и доставка
проверяются прежними валидаторами. Новый planner receipt добавляется к истории.
Карточки неиспользованных потомков переподготавливаются; использованные
контракты потомков блокируют операцию.

## Адресный ремонт официальной 0.4.0

Старый runtime не редактируют и не запускают для ремонта. Отдельный инструмент
`tools/repair_task_zones.py` поддерживает только точное дерево официальной
0.4.0: source commit `0977f893106312a87068fb6533e03f1ca9ad8633`, 93 файла,
digest `18da50b582274c2010d5e8607800053dab0134ca8f234674b653d83657ba33e9`.
Ремонт sourceQuote для 0.3.5 остаётся отдельной неизменной процедурой.

```text
python -B tools/repair_task_zones.py --root <isolated-project> inspect
python -B tools/repair_task_zones.py --root <isolated-project> prepare --candidate-package <reviewed-skills/aispa> --expected-journal-sha256 <sha>
python -B tools/repair_task_zones.py --root <isolated-project> apply --manifest-file <prepared-manifest> --expected-manifest-sha256 <reviewed-manifest-sha> --expected-journal-sha256 <sha> --approval-file <existing-owner-authorization> --confirm
```

`inspect` строго read-only. `prepare` сохраняет отдельную копию и manifest,
не выбирая их для прогона. Все файлы исходного Release сохраняются; diff
ограничен CLI, planning, contracts, team, repairs, test-intent, двумя maintenance-модулями,
их отдельной командой и этой инструкцией. В частности, незавершённые изменения
прикладных задач из другого worktree не могут попасть в копию.
Candidate должен побайтово совпадать с maintenance-пакетом самого вызванного
инструмента; произвольный внешний пакет с правками в разрешённых путях не принимается.

Независимое review должно проверить точный manifest и смысл разрешения владельца:
утилита проверяет байты, а не подлинность слов или смысл полномочий.
Используется уже данное реальное разрешение; новый бриф не создаётся.

`apply` под замком проверяет CAS, manifest, источники и все локальные артефакты
истории. Единственное новое событие выбирает runtime digest и квитанцию;
version, policy, задачи и доказательства сохраняются. Оригинальные runtime и
префикс журнала не изменяются. Далее используют CLI из пути `runtime`, который
вернул инструмент; прежний CLI не соответствует выбранному digest.
После прерывания неподключённая staging-копия может остаться как артефакт;
она не становится активной без успешного append и read-back.

Fixtures в `tests/test_task_zone_extension.py` и `tests/test_runtime_zone_repair.py`
проверяют реальные локальные RED/GREEN и синтетические роли, сохранение FAIL,
цепочку ремонта/critic2, CAS, подмены и исходный официальный runtime. Это не
доказательство качества модельных решений или разрешение на живой apply.
