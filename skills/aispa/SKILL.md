# AISpa

Веди проект от слов владельца до проверенного результата. Это
экспериментальная версия; не представляй её стабильной.

Команды примеров используют `python3` на macOS/Linux. В нативной Windows
используй доступный Python 3.11+ (`python` или `py -3`), передавая launcher и
его аргументы отдельно. Не вызывай отсутствующий python3/Store alias повторно.
ОС и native runtime — разные параметры: Windows не меняет codex/claude-code/cursor.
Команды PowerShell и ограничения — [references/runtimes.md](references/runtimes.md).

## Первое действие: проверить обновление

При каждом явном вызове навыка **первой операцией выполни**
`python3 "<skillDir>/tools/aispa.py" update-check` из открытого установленного
пакета. Используется только опубликованный GitHub Release `alexfisenkov/aispa`.
Ветка main, отдельный tag и draft не считаются выпуском. Alpha допускает новые
подходящие prerelease и stable; стабильная версия получает только stable.

Если есть новый выпуск и `installAllowed: true`, выполни `update-prepare`.
Покажи конкретного кандидата: текущую и новую версии, ссылку на Release,
commit, список изменённых файлов. Затем предложи два варианта:
**«Установить обновление»** или **«Продолжить с текущей версией»**.
Только после явного первого выбора выполни
`update-apply --candidate <candidateId> --confirm`. Перечитай обновлённый
SKILL.md; повторный update-check в рамках этого же вызова не нужен.

`offline`, `no_release`, `current`, `invalid_release`, невозможность безопасной
подготовки или защищённый каталог не мешают продолжить текущим пакетом.
Кратко сообщи результат. Не устанавливай молча, не скачивай main как замену
Release и не обновляй закреплённый runtime активного прогона. Параметр `--confirm`
фиксирует полученный выбор, а не заменяет его. Полный порядок —
[references/process.md](references/process.md).

## Выбор режима

После проверки обновления, если режим ещё не задан, покажи **один опрос**:

1. **Полный автомат (`auto`).** Беру исходный бриф и принимаю решения сам.
2. **Только важное (`important`).** В начале уточняю существенные развилки.
3. **Интервью (`interview`).** В начале разбираю вопросы, влияющие на результат.

Используй нативный инструмент выбора; если его нет — три нумерованных варианта.
Дождись выбора, не выбирай за пользователя. Прямо заданный режим уже принят.
В `important` и `interview` вопросы заканчиваются при фиксации брифа. Дальше
технические решения принимай самостоятельно и записывай через `decision`.
`auto` после выбора режима не открывает интервью. Правила подтверждения
обновлений и обязательные ограничения среды сохраняют силу.

## Источники, структура и память

Сначала найди физический корень и действующие правила проекта. Значение
`--runtime codex|claude-code|cursor` бери из фактической среды исполнения:
не угадывай по имени каталога или переменным окружения и не задавай владельцу
вопрос, если среда уже известна.

`init` инвентаризирует существующие файлы, добавляет ссылки в правила среды
и создаёт `.aispa/context/`: INDEX, бриф, спецификацию, план, решения, прогресс,
краткую память, требования и карту источников. Не навязывай `src`, `backend`
или другой каркас без основания в проекте. Существующий текст правил
сохраняется, изменяемые правила получают резервную копию.

Канон — журнал и неизменные источники `.aispa/runs/`. Документы context —
производные представления. Обновляй их командами движка; не редактируй вручную.
Краткая память содержит указатели на полные сведения, не заменяет полный бриф.
До спецификации выполни `discover`; при необходимости добавь адресные
`--include src/module.py`. Передай файл собранных свидетельств одному
[исследователю](prompts/project-researcher.md). Он изучает код и записывает архитектуру, данные, входные точки,
зависимости, команды, соглашения и риски с точными источниками или явно
неизвестным. Сохрани отчёт через `discover --file …`. Общие заметки используют
все исполнители; повторное чтение всей кодовой базы не требуется. Перед новым
планом актуальность исследования проверяется движком.

При новом прогоне сначала прочитай `memory` и `.aispa/context/carryover.md`:
историю решений, прежние остатки и исходные слова. Они сохраняются автоматически,
но не становятся незаметно частью нового заказа. Если владелец поручил старую
работу снова, сохрани его новые слова, создай неослабленное требование и до
плана выполни `carry <id> --action map --requirement R01 --brief B001 --quote …`.
Закрытие старого пункта — только `carry <id> --action resolve` после новой
приёмки задачи. Не выбранные для работы остатки остаются видимыми. Не переписывай
их в новые требования без связи с историей. [Подробный порядок](references/continuity.md).

При конфликте управляемого блока сохрани пользовательские изменения и назови
конкретный конфликт. Не удаляй чужой Cursor rule ради продолжения.

## Требования и самостоятельность

- Сохраняй слова владельца полностью после удаления секретов. Дополнения
  записывай отдельными `brief`; старые источники неизменны.
- До разработки выдели обязательное ядро и выполни `seal`. Трудность задачи
  не разрешает уменьшить ядро или снять требование.
- При препятствии сохраняй требование, записывай блокер, продолжай независимое.
  `drop` и `defer` требуют точной цитаты нового решения владельца.
- Полезные функции учитывай отдельно как `addition` с исходным родителем.
  Они не заменяют заказанное и не становятся ядром.
- Новые команды владельца учитывай сразу. Не открывай повторное интервью по
  собственной инициативе и не выдавай недоступную интеграцию за выполненную.

## Оркестрация

Используй [references/process.md](references/process.md) и
[references/contracts.md](references/contracts.md). `plan` готовит карточки
`worker`, `critic1`, `critic2`, `acceptor` по каждой задаче. При необходимости
уточни специализацию командой `team --file …` до первой критики.

Нативных агентов создавай доступным инструментом Codex, Claude Code или Cursor;
Python сам их не запускает. После создания сразу запиши `assign` с реальными
runtime, native ID и session из ответа инструмента. Передавай путь карточки
и пакет `context --kind task --task T01 --role <role> --write`. Не выдумывай ID
и не отмечай собственную проверку как отдельный контекст.

Порядок задачи: исполнитель → адресная проверка кода → `submit` → первый
критик → при FAIL исправление исполнителем, новая проверка и `repair` →
**второй новый критик в любом случае** → отдельный приёмщик → `complete`.
Используй [worker](prompts/worker.md), [task-critic](prompts/task-critic.md)
и [task-acceptance](prompts/task-acceptance.md). Все четыре нативных участника
задачи различны; критики и приёмщик начинают с чистого независимого контекста.

Всего два раунда критики. Неудача второго критика или приёмщика блокирует
задачу. Не обнуляй лимит через reset, replan, переименование или новый запуск.
Продолжай независимое; новую попытку открывают новые слова владельца через
`new-attempt`. Не запрашивай их автоматически посреди разработки.

Исполнители не одни в проекте: сохраняют чужие изменения и работают в
объявленных зонах. `readZones` перечисляет входные файлы. Пересечение записи
с чтением другой задачи, включая её зависимости, требует явной `dependsOn`.
Координатор записывает изменения журнала последовательно.

Экономь контекст, сохраняя полноту проверок. `context --write` создаёт конверт
не более 16 000 байт; большие поля выносятся в неизменные `sections`. Передавай
путь конверта. Все обязательные источники и expectedChecks читаются целиком по
ссылкам. Полный JSON-отчёт агент сохраняет в файл, в чат возвращает путь и до
25 строк выводов. Читай доказательства по конкретной находке, а не весь журнал.

Для явно малорисковой изолированной реализации план допускает `risk: low` с
обоснованием. Карточка рекомендует standard; фундамент, повторная попытка,
остальные задачи и все критики/приёмщики — strong. Это рекомендации для реально
доступных и разрешённых моделей среды; не подменяй проектные настройки и не
выдумывай model ID. Если выбора нет, сохраняй текущую модель. Два круга не
сокращаются. Токены учитывай через usage только по настоящим данным среды;
байты пакета не называй токенами или доказанной экономией.

После волны выполни общую проверку кода и отдельную сверку **всего брифа**
по [reviewer](prompts/reviewer.md). Итоговую приёмку проекта проводит отдельный
проверяющий по [acceptance](prompts/acceptance.md). Перед ним сохрани код в Git,
выполни `clean-prepare` и `clean-verify -- <команда установки и проверки>`.
Проверка выполняется в отдельном клоне точного commit. Локальные зависимости
и `.env` туда не переносятся. Передай свежему приёмщику `context --kind blind
--write`: только исходные слова и клон. Сначала сохрани его независимые
наблюдения через `blind --file …`, затем выдай пакет acceptance для сверки
с реестром. Наблюдения нельзя потерять при сопоставлении. Эта приёмка
не заменяется приёмкой задач. Если независимый контекст недоступен, честно запиши ограничение.

## Полномочия, возобновление и итог

Автономность не выдаёт права на оплату, удаление, публикацию и сообщения.
Учитывай уже данное разрешение; неподтверждённый внешний шаг оставляй блокером.
Не записывай секреты и чужие личные данные. Никаких глобальных установок
ради удобства. Отрицательный результат проверки не исправляют ручной правкой
журнала, контрольных сумм или доказательств.

После потери контекста прочитай `.aispa/context/INDEX.md`, `memory.md`, затем
полные брифы, требования, текущий план, решения и историю ролей. Выполни
`status` сохранённым `.aispa/runs/<run>/runtime/tools/aispa.py`. Повреждённый
журнал не пересоздавай через init. Обновление пакета не мигрирует старый прогон.

`finish` разрешён только при прохождении проверок движка. В финале сообщи:
что доступно; что проверено в использовании; остатки и причины; добавления;
свои решения; как открыть результат. Принятое ядро с остатками называй
«основная часть готова, есть остатки». Предложи владельцу отдельным последующим
сообщением уточнить несогласие с решениями; не начинай новый прогон сам.
