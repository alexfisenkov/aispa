# AISpa

Веди проект от слов владельца до проверенного результата. Версия 0.1.0.
Этот файл — постоянный маршрут;
подробности открывай только для текущего этапа и роли. Полный каталог команд,
документов и архивов заранее в контекст не загружай.

Для служебных изменений и `status` используй глобальный `--compact` **перед**
командой: полный ответ сохранится по адресу и SHA; ошибки и код выхода
сохранятся. Команды чтения без `--write` остаются полными. Для подготовки
используй `brief-source --write`, затем `brief-map-context --write` только после
двух независимых разборов, и `template <kind> --write` для пустых форм.
После реального назначения роли получай
`context --kind task --task T01 --role <роль> --write --with-template`:
передавай `context`, `card`, `template` по их `absolutePath` без перепечатки тел.
Worker сначала получает обычный `context … --write`; bundle с формой — только
после успешной адресной проверки. Отдельный `template <роль> --task … --write`
сохраняется для совместимости и получения только формы; он не создаёт пакет.
Движок заполняет только известные поля формы, а не выводы проверяющего.
Карточка, пакет и выданная форма — обычный вход роли. Не загружай целиком
`references/contracts.md` ради одного отчёта: найди заголовки и прочитай
нужный раздел при неясности поля или диагностике валидатора. Это сокращает
справочный материал, но не исходный бриф, код и обязательные проверки роли.
Если активный прогон закрепил прежний runtime без этих флагов и шаблонов,
продолжай его прежними командами; не пересоздавай прогон ради оптимизации.

## Первое действие при явном вызове

Сразу выполни `python3 "<skillDir>/tools/aispa.py" update-check` из открытого
установленного пакета. На Windows выбери реально доступный Python 3.11+
(`python` или `py -3`); launcher и его аргументы передавай отдельно.
Не повторяй отсутствующий `python3` либо Store alias. ОС и native runtime
различны: Windows не превращает codex в cursor или claude-code.

Источник обновления — опубликованный GitHub Release `alexfisenkov/aispa`:
ветка main, tag и draft не считаются выпуском. Если есть новый выпуск с
`installAllowed: true`, выполни `update-prepare`, покажи текущую и новую версии,
ссылку на Release, commit и изменённые файлы. Предложи выбор
«Установить обновление» / «Продолжить с текущей версией». Только после явного
выбора установки: `update-apply --candidate <candidateId> --confirm`, затем
перечитай установленный SKILL.md. `--confirm` фиксирует уже полученный выбор.
При `offline`, `no_release`, `current`, `invalid_release`, ошибке подготовки или
защищённом каталоге продолжай текущим пакетом и кратко назови результат.
Активный прогон остаётся на закреплённом runtime; не устанавливай main вместо
Release. Детали: [процесс](references/process.md), [среды](references/runtimes.md).

## Режим и полномочия

Если режим не задан явно, после update-check покажи один выбор и дождись ответа:
`auto` — самостоятельная работа по исходному брифу; `important` — только важные
развилки до фиксации брифа; `interview` — подробный разговор до фиксации брифа.
Используй нативный инструмент выбора либо три нумерованных варианта.
В `auto` не открывай интервью. Вопросы `important` и `interview` заканчиваются
на `seal`; после него решения принимай автономно и фиксируй через `decision`.
Новые слова владельца учитывай сразу. Не проси повторить уже данное разрешение.
Обновление, защищённые поля, оплата, удаление, публикация и сообщения сохраняют
свои отдельные границы полномочий. Недоступный внешний шаг называй блокером.

## Инварианты каждого этапа

- Сохраняй полный исходный бриф без секретов; дополнения — отдельными `brief`.
  Перед `seal` два разных участника отдельно учитывают каждую исходную часть;
  сверяющий видит оригинал, а не выводы первого. `scenarios` проверяет восемь
  случаев для каждой действующей функции, `interfaces` связывает стыки с задачами.
  Исходные источники неизменны. Требования и обязательное ядро не сокращай из-за
  сложности. `drop` и `defer` требуют точной цитаты нового решения владельца.
  Невыполнимое ядро остаётся явно заблокированным, независимую работу продолжай.
- Канон — проверяемый журнал и неизменные источники в `.aispa/runs/`.
  `.aispa/context/` — производные представления. Не правь журнал, SHA, receipt
  или документы context вручную. `init` не лечит повреждённый журнал. При
  оборванной последней записи сначала `journal-inspect`, затем адресное
  `journal-recover --sha256 … --confirm`: оригинал сохраняется побайтно.
  Приостановленный прогон требует свежей команды `journal-verify` и отчёта
  независимого `recovery-reviewer` через `journal-reconcile`; неизвестные
  внешние эффекты запрещают возобновление.
- Нативных агентов вызывает среда, не Python. Сохраняй реальные runtime,
  native ID и session через `participant` или `assign`; ID нельзя выдумывать.
  Отдельный реестр ролей не удостоверяет модель сам: сверяй фактические ответы
  среды и сохраняй реальные usage для всех участников. Для heavy исполнитель, первый
  независимый критик и отдельный приёмщик различны. В новых прогонах PASS
  первого критика ведёт прямо к приёмщику; WARN/BLOCK/FAIL требуют ремонта
  и второго свежего критика. Не запускай и не назначай critic2 заранее.
  Любой non-PASS второго или приёмщика блокирует задачу. Старые закреплённые
  прогоны сохраняют свой прежний контракт двух кругов. Reset, replan, новое
  имя и новый прогон не обнуляют лимит; новую попытку открывают только новые
  слова владельца через `new-attempt`. Не выпрашивай их посреди работы.
- В новых прогонах классифицируй задачи до исполнения: по умолчанию heavy.
  Light допускает только явно ограниченное обратимое изменение низкого риска.
  Он проходит worker → адресная проверка → `submit` → verified completion,
  без отдельных критиков и приёмщика задачи. Это не итоговая приёмка проекта.
  Сомнение или изменение риска требует `promote-task`, сохраняя историю.
  Подробности открывай по необходимости: [классы задач](references/task-tiers.md).
- После `init` зарегистрируй настоящего координатора один раз. Он может
  авторствовать разбор идеи, первичный разбор брифа, discovery и план; движок
  сохраняет авторство фазы отдельно от identity и не удваивает usage.
  Независимые сверки, критика и приёмка не получают coordinator alias.
  Проверяй `usage`/phase receipts: отсутствие автора не означает нулевые токены.
- Исполнители работают в объявленных зонах и сохраняют чужие изменения.
  Пересечение записи с чтением другой задачи, включая зависимости, требует
  `dependsOn`. Координатор пишет Journal последовательно.
- Проверка команды, критика, приёмка задачи, сверка брифа, clean-clone, blind и
  итоговая приёмка — разные доказательства. Старый успешный запуск из `commands`
  не является текущим PASS: повтори команду на актуальном коде. Сохраняй и
  неуспешные реальные запуски в истории, но не рекомендуй их как проверенные.
- Чистый клон точного Git commit — проверка, не sandbox. Локальный preview,
  зелёные библиотечные тесты и PASS критиков не подтверждают использование
  полного навыка или выпуск. Усечённый вывод команды не даёт PASS. Приёмка
  сначала фиксирует намерение теста, сквозные интеграции и реальные пробелы;
  недоступную проверку нельзя заменить обещанием. Не объявляй готовым то, что
  не проверено.
- До seal отдели только точно выраженные сроки исполнения через
  [узкий реестр обязательств](references/execution-obligations.md). Продуктовые
  условия не становятся исключениями. Будущая передача хостом остаётся явным
  остатком; продукт можно принять, но нельзя объявить будущий срок выполненным.
- В `test-intent` зафиксируй [отказные границы](references/failure-checks.md).
  Связь с тестовым файлом не доказывает выполнение сценария: критик проверяет
  действительные отрицательные проверки и сохранность данных.
- Секреты и чужие персональные данные не попадают в бриф, команды, логи,
  отчёты и репозиторий. Глобальная установка не нужна для удобства.

Открой также только профильный контракт из [references/contracts.md](references/contracts.md)
и нужный prompt роли. Вызов `context --kind … --write` создаёт адресный пакет;
каждый обязательный источник в нём прочитай целиком. Обрезанный вывод не равен
прочитанному файлу.

Подготовительные формы получай через `template <kind> --write`, исходные пакеты —
через `brief-source --write` и, после двух независимых разборов, `brief-map-context --write`.
Передавай пути файлов; каждый автор сам заполняет смысловые поля. Для назначенной
роли задачи `context --kind task --task T01 --role <role> --write --with-template`
возвращает контекст, карточку и форму; worker получает форму только после успешной
адресной проверки. Эти команды не назначают агента и не сдают отчёт автоматически.

Неизменные разделы context имеют стабильные адреса и SHA. В том же сохранённом
контексте повторно используй только текст, который **ты сам** уже получил
полностью, проверив неизменность SHA. Новый critic1, critic2 и приёмщик читают
обязательные источники независимо. После потери контекста восстанови их;
запись «прочитано» и наличие файла не заменяют содержание.

## После потери контекста

Прочитай `.aispa/context/INDEX.md`, `memory.md`, затем полные брифы,
требования, текущий план, решения и историю ролей. Запусти `status` сохранённым
`.aispa/runs/<run>/runtime/tools/aispa.py`. Продолжай с файла текущего этапа.
Новый пакет не мигрирует старый активный прогон. Нельзя пересоздать состояние
через `init`, если журнал повреждён.
