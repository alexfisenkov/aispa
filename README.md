**0.2.0 — экономный контроль** ([план](docs/plan-lean-control.md)).
В новых прогонах PASS критика сам закрывает тяжёлую задачу без отдельного
приёмщика, обычный код может идти классом standard без критика задачи под
общим обзором версии, критик сначала читает изменения своей зоны, сценарии
масштабируются глубиной, а служебные шаги можно отправлять одним `batch`.
Класс standard экономит, только если план явно им размечает задачи (по
умолчанию heavy). Выпуск 0.2.0 опубликован; экономия не измерена модельным прогоном.

Там же — **режимы проверки** ([бриф](docs/brief-check-modes.md),
[спецификация](docs/spec-check-modes.md)). Человек сам выбирает при старте, сколько
проверять: «Быстро» — в разы дешевле (это подпись выбора, экономия не измерена), без проверок по ходу, проблемы в итоговом
отчёте (прогон завершается «с остатками», пропущенные проверки названы); «Сбалансированно» — система сама решает по каждой задаче; «Максимум» —
долго и дорого, каждая задача доводится до PASS (одна дополнительная волна, затем
остаток следующего прогона). Автоподбора нет, смену режима система не предлагает
(принимает любые слова человека, смена видна в отчёте); по ходу работы вопросов
нет. Сильная модель советуется только задачам с безопасностью, ключами, доступом,
платежами и личными данными.

AISpa ведёт разработку от исходного брифа до проверяемого результата.
Слова владельца, требования, задачи, решения и доказательства связаны
сохранённой историей. Для завершения задачи нужны актуальная проверка и
доказательства; у тяжёлой задачи дополнительно обязательна отдельная приёмка.

Новый маршрут включается только новым `init`; старые прогоны продолжаются
своими закреплёнными runtime. Полные модельные испытания 0.1.0 по решению
владельца не проводятся. Экономия токенов и превосходство нового маршрута не
измерены. Предыдущие [парные испытания](docs/validation-alpha.10-paired-test.md),
[батарея после оптимизации](docs/validation-context-optimization-paired-test.md),
[адаптивный кандидат](docs/validation-adaptive-review-paired-test.md) и
[один повтор AISpa](docs/validation-lean-service-single-repeat.md) сохранены
с исходными результатами и ограничениями; они не доказывают качество light/heavy.

## Как работает

- По явному вызову сначала проверяется опубликованный GitHub Release.
  Обновление подготавливается для просмотра и устанавливается только после
  выбора пользователя. Без сети работа продолжается с текущей версией.
- Пользователь выбирает полный автомат, только важные вопросы или интервью.
  Вопросы заканчиваются при подготовке брифа; обязательное ядро фиксируется
  до разработки. Существенные решения агента сохраняются.
- Каждая исходная часть брифа получает отдельный учёт и независимую сверку до
  `seal`. Для действующих функций проверяются сценарии выбранной глубины: в новых
  прогонах balanced — основной путь, пустые данные, ошибки и сохранность; deep —
  все восемь, включая повторный вызов, доступ и внешние эффекты. Стыки между частями системы связываются с
  задачами и проверками. Неучтённый источник не исчезает из проекта молча.
- До фиксации брифа агент разбирает саму идею: проблему, пользователя, результат,
  альтернативы, небольшой проверочный эксперимент и сценарии отказа. Гипотезы
  отличаются от наблюдений; полезное дополнение не заменяет исходное требование.
  Отдельно разбираются спрос, польза и расходы, эксплуатация, повторное
  использование и другие участники. Решения проходят сверку со спецификацией.
- Перед спецификацией агент изучает существующий проект: архитектуру, данные,
  точки входа, зависимости, команды, правила и риски. Наблюдения связаны с
  файлами и их контрольными суммами; неопределённость указывается явно.
- В проекте поддерживаются бриф, спецификация, план, решения, прогресс и краткая
  память. Новый прогон сохраняет историю и остатки предыдущих, а текущий объём
  определяется новым брифом и отдельными решениями по остаткам.
- До исполнения задача получает класс и обоснование. По умолчанию — heavy.
  Light разрешён для ограниченных обратимых правок обычной документации или
  оформления с низким риском; короткий diff сам по себе не даёт это право.
  После адресной проверки и отчёта исполнителя light получает «Выполнение
  проверено», без отдельных критиков и приёмщика задачи. Это ещё не приёмка проекта.
  Standard — обычный код без критика задачи: низкий или обычный риск, от него
  зависит только финальная задача, зоны не касаются правил агента, секретов, доступа,
  платежей, миграций, схем и контрактов. Его покрывает общий обзор версии.
- Heavy в новых прогонах: первый независимый критик проверяет и приёмку задачи
  (критерии, ограничения, сверку с цитатами владельца), его PASS закрывает
  задачу. WARN/BLOCK/FAIL ведут к ремонту и второму свежему критику. Максимум
  два круга. Закреплённые прогоны сохраняют отдельного приёмщика. Новый риск
  требует явного повышения light или standard до heavy с сохранением истории.
  Reset, replan и переименование не позволяют обойти использованные проверки.
- Нативные участники разных фаз записываются по реальным ID среды. История
  использования моделей учитывает всех зарегистрированных участников; сумма
  не объявляется полной, если часть usage отсутствует.
- Перед запуском план проверяется на лишнее дробление. Связанные части можно
  объединить, сохранив каждое условие, причины риска и внешние зависимости.
  Каждое исходное условие сохраняется; heavy нельзя превратить в light укрупнением.
  План связывает задачи в проверяемые пользовательские результаты. Миграции
  разделяют добавление нового, перенос потребителей и удаление старого;
  каждому шагу нужны проверки совместимости и восстановления.
- После первого FAIL записывается причина и план ремонта. Локальный дефект
  может исправлять исходный исполнитель; недостаток контекста или неверный
  подход требуют свежего исполнителя. Третий круг автоматически не возникает.
- После волны независимый проверяющий сверяет весь бриф. Финальная приёмка
  проекта остаётся отдельным этапом. Изменение источников или кода может
  сделать прежнее доказательство устаревшим.
- Перед сдачей проверяются сквозные интеграции и намерение тестов: что именно
  проверяла команда, где кончается её покрытие и какие сценарии ещё не испытаны.
  Успешный код возврата при усечённом выводе не считается PASS.
- Независимый обзор всей версии обязателен. Для финальной heavy он входит
  в её критику; для финальной light или standard выполняется отдельно через
  `integration-review` до handoff и чистого клона. Исполнитель не подписывает
  независимую проверку собственной работы.
- Финальная приёмка новых прогонов требует проверки сохранённого
  commit в отдельном чистом клоне. Проверяющий сначала получает исходный бриф
  и продукт, затем сверяет свои наблюдения с реестром требований.
- До чистого клона в обычных файлах Git готовятся инструкция запуска,
  архитектура, решения и словарь подходящего проекту размера. Для маленького
  проекта достаточно одного README с обоснованными исключениями. Команды
  связаны с сохранёнными фактическими выполнениями; приватный бриф не экспортируется.
- Если ядро принято, второстепенные недоделки допускают результат
  «основная часть готова, есть остатки». Они остаются в учёте.
- Оборванный конец журнала можно восстановить только после осмотра точного SHA
  и побайтной резервной копии. Прогон остаётся на паузе до свежей проверки и
  отчёта независимого участника; неизвестные внешние эффекты блокируют возврат.
- После приёмки отдельный автор читает готовый код и сохраняет проверенные
  команды, ловушки, причины решений и словарь. Следующие задачи получают
  только относящиеся к ним свежие записи; старая проверка не становится новым PASS.
  Входная инструкция короткая: подробные шаги открываются по текущей фазе.

Python-движок записывает роли, переходы и доказательства. Нативных агентов
создаёт нативная среда доступными инструментами сессии. В кандидате 0.3.0
это Codex, Claude Code, Cursor, OpenClaw, Gemini CLI или Antigravity.
Без независимого контекста проверяющего приёмка остаётся заблокированной.
Вызовов модельных провайдеров внутри движка нет; записанные ID не являются
криптографическим подтверждением независимости модели.

Локальный дашборд можно запустить повторно без второго сервера. Он показывает
ожидание владельца и последние события; интерфейс имеет русский и английский
языки, системную, светлую и тёмную темы. Отдельный экспорт — исторический
снимок: он не опрашивает живой сервер и не выдаёт старую приёмку за текущую.

## Установка

AISpa ставится как навык (skill) для агента: папка `aispa` кладётся в каталог
навыков вашей среды. Поддерживаются Codex, Claude Code и Cursor на macOS, Linux
и нативной Windows. Установщик `install.py` скачивает **опубликованный выпуск
GitHub** (по умолчанию последний стабильный), сверяет commit, хеши и состав
файлов, показывает, что именно будет записано, и ставит только после вашего
подтверждения. Существующую папку он никогда не перезаписывает.

### 1. Что нужно заранее

- **Python 3.11 или новее.** Сторонние библиотеки не нужны.
- **Git** (установщик берёт из него точный commit выпуска).
- Доступ в интернет к `github.com` и `api.github.com` (только при установке и обновлении).

Проверка версий:

```bash
# macOS / Linux (bash, zsh)
python3 --version
git --version
```

```powershell
# Windows (PowerShell)
py -3 --version
git --version
```

Если `py` нет, попробуйте `python --version`. Нужна версия 3.11 и выше.

Где взять: Python — [python.org/downloads](https://www.python.org/downloads/)
(на Windows отметьте «Add python.exe to PATH» и установите «py launcher»);
на macOS также `brew install python git`, на Debian/Ubuntu —
`sudo apt install python3 git`. Git на Windows — [Git for Windows](https://git-scm.com/download/win).
После установки откройте новое окно терминала.

### 2. Скачайте установщик

Установщик публикуется как файл `install.py` в каждом Release. Ссылка на
последний стабильный выпуск:
`https://github.com/alexfisenkov/aispa/releases/latest/download/install.py`.
Скачайте его в любую рабочую папку (не в проект, куда будете ставить).

```bash
# macOS / Linux
mkdir -p ~/aispa-install && cd ~/aispa-install
curl -fsSL -o install.py https://github.com/alexfisenkov/aispa/releases/latest/download/install.py
```

```powershell
# Windows (PowerShell)
New-Item -ItemType Directory -Force "$HOME\aispa-install" | Out-Null
Set-Location "$HOME\aispa-install"
Invoke-WebRequest -Uri https://github.com/alexfisenkov/aispa/releases/latest/download/install.py -OutFile install.py
```

Проверьте, что установщик запускается: `python3 install.py --help`
(Windows: `py -3 -X utf8 install.py --help`).

### 3. Выберите, куда ставить

Таблица ниже относится к опубликованному 0.2.0. Новые среды кандидата 0.3.0,
их каталоги и команды после публикации — [инструкция установки](docs/install.md).

Нужны два выбора: **среда** (`--runtime`) и **область** (`--scope`).

| Среда | `--runtime` | В проект (`--scope project`) | Глобально (`--scope global`) | Вызов |
|---|---|---|---|---|
| Claude Code | `claude-code` | `<проект>/.claude/skills/aispa/` | `~/.claude/skills/aispa/` | `/aispa` |
| Codex | `codex` | `<проект>/.agents/skills/aispa/` | `~/.codex/skills/aispa/` | `$aispa` |
| Cursor | `cursor` | `<проект>/.cursor/skills/aispa/` | `~/.cursor/skills/aispa/` | `/aispa` |

- **В проект** — навык виден только в этом проекте. Нужен `--project-root` с
  абсолютным путём к корню проекта (папка должна существовать).
- **Глобально** — навык доступен во всех проектах. `--project-root` не указывают.
- Вместо пары `--runtime` + `--scope` можно задать любую свободную папку:
  `--destination <абсолютный-путь>` (с ними не сочетается).
- Навык вызывается только явно (`/aispa`, `$aispa`), сам он не включается.

Папка назначения **не должна существовать**: нужна свежая установка, не поверх старой.
Начните с небольшого проекта без реальных платежей и персональных данных.

### 4. Предпросмотр (ничего не устанавливает)

Пример: Claude Code, в проект. Для других сред поменяйте `--runtime`
(`codex`, `cursor`); для глобальной установки замените `--scope project
--project-root …` на `--scope global`.

```bash
# macOS / Linux
python3 install.py preview --runtime claude-code --scope project --project-root "$HOME/мой-проект"
```

```powershell
# Windows (PowerShell)
py -3 -X utf8 install.py preview --runtime claude-code --scope project --project-root "$HOME\мой-проект"
```

Команда читает выпуск, проверяет commit, `aispa-update.json` и `aispa.zip`,
собирает кандидата во временной папке `~/.aispa-installs/` и печатает JSON.
Папку навыка она не создаёт. Проверьте в ответе: `version` и `tag` (нужный ли
выпуск), `prerelease` (для стабильного — `false`), `destination` (куда
встанет), `commit`, `releaseUrl`, `fileCount`. Скопируйте `candidateId`.

### 5. Установка

```bash
# macOS / Linux
python3 install.py apply --candidate <candidateId> --confirm
```

```powershell
# Windows (PowerShell)
py -3 -X utf8 install.py apply --candidate <candidateId> --confirm
```

`--confirm` означает, что вы просмотрели кандидата и согласны. Установщик ещё раз
проверяет файлы, создаёт новую папку, копирует в неё пакет и перечитывает
результат (`"status": "installed"`). Если папка появилась после предпросмотра,
установка остановится; уже созданная частичная папка при ошибке не удаляется,
её можно осмотреть и убрать вручную.

### 6. Другая версия: `--tag`

По умолчанию берётся самый новый **стабильный** выпуск; предварительные
(alpha, beta) не выбираются. Чтобы поставить конкретный опубликованный выпуск,
добавьте его тег в `preview`:

```bash
python3 install.py preview --runtime claude-code --scope project --project-root "$HOME/мой-проект" --tag v0.1.0
```

Тег должен быть у опубликованного Release с ресурсами `aispa.zip` и
`aispa-update.json`. Черновики и теги без Release не подходят. Список — на
странице [Releases](https://github.com/alexfisenkov/aispa/releases).
Установщик `install.py` из нужного Release лучше брать оттуда же:
`https://github.com/alexfisenkov/aispa/releases/download/<тег>/install.py`.

### 7. Проверка установки

1. Папка есть и в ней лежит `SKILL.md`:

   ```bash
   ls "$HOME/мой-проект/.claude/skills/aispa"
   ```

   ```powershell
   Get-ChildItem "$HOME\мой-проект\.claude\skills\aispa"
   ```

2. Версия навыка (путь — из `destination` в предпросмотре):

   ```bash
   python3 "$HOME/мой-проект/.claude/skills/aispa/tools/aispa.py" --version
   ```

   ```powershell
   py -3 -X utf8 "$HOME\мой-проект\.claude\skills\aispa\tools\aispa.py" --version
   ```

3. Проверка обновлений (только чтение, ничего не меняет):

   ```bash
   python3 "$HOME/мой-проект/.claude/skills/aispa/tools/aispa.py" update-check
   ```

4. В агенте введите вызов своей среды (`/aispa` в Claude Code и Cursor,
   `$aispa` в Codex) и опишите идею проекта. Первое действие навыка при явном
   вызове — та же проверка обновлений; без сети он продолжает работу с
   установленной версией.

### 8. Обновление и откат

Обновляется уже установленная папка. Команды запускайте из установленного
пакета (`<папка-навыка>` — путь из шага 7), из корня проекта, не из самой папки навыка:

```bash
python3 <папка-навыка>/tools/aispa.py update-check
python3 <папка-навыка>/tools/aispa.py update-prepare
python3 <папка-навыка>/tools/aispa.py update-apply --candidate <candidateId> --confirm
python3 <папка-навыка>/tools/aispa.py update-rollback --backup <backupId> --confirm
```

В PowerShell то же самое с `py -3 -X utf8` вместо `python3`.

- `update-check` показывает, есть ли новый опубликованный выпуск (статусы
  `available`, `current`, `offline` и др.).
- `update-prepare` скачивает и проверяет кандидата рядом с установленной папкой
  (`.aispa-update-<id>/`) и печатает `candidateId` и список отличий.
  Установленный пакет не меняется.
- `update-apply` заменяет пакет после вашего решения. Прежняя версия остаётся
  рядом в `.aispa-backup-<id>/`; её имя печатается как `backupId`. Если вы
  правили файлы навыка руками, обновление откажется их затирать.
- `update-rollback` возвращает сохранённую версию, пока установленная не менялась
  после обновления.
- **Начатый прогон не затрагивается:** при `init` пакет копируется в проект и
  прогон до конца работает на этой закреплённой копии. Обновление или откат
  установленного навыка влияют только на новые прогоны.

Подробности и аварийное восстановление — [docs/updates.md](docs/updates.md).

### 9. Удаление

Отдельной команды удаления нет. Навык — обычная папка: закройте агент и удалите
каталог из шага 3 (например `rm -r "$HOME/мой-проект/.claude/skills/aispa"`,
в PowerShell `Remove-Item -Recurse -Force "$HOME\мой-проект\.claude\skills\aispa"`).
Рядом можно удалить `.aispa-backup-*`, `.aispa-update-*` и `~/.aispa-installs/`.
Папки `.aispa/` ваших проектов с историей прогонов и ссылки в `AGENTS.md`/`CLAUDE.md`
не трогайте, если хотите сохранить историю.

### 10. Частые проблемы

- **Windows: `python` открывает Microsoft Store или «не найден».** Это заглушка
  Store. Установите Python с python.org и пользуйтесь `py -3`, либо отключите
  «App execution aliases» для python.exe в параметрах Windows.
- **`python3: command not found` (Windows).** Там команда называется `py -3`
  или `python`, не `python3`.
- **Старый Python.** Ошибки синтаксиса или «3.11 required» — обновите Python.
- **Каталог установки уже существует.** Установщик не перезаписывает: выберите
  другой `--destination` или сначала сохраните и уберите старую папку.
- **Нет прав на каталог.** Ставьте в папку, где вы владелец (проект или
  `~/...`); не используйте `sudo` и «Запуск от администратора» без необходимости.
  Корень проекта должен существовать, путь — абсолютный, без `..` и без ссылок
  (symlink/junction).
- **Нет сети или выпуск недоступен.** Предпросмотр и обновление требуют доступа к
  GitHub. Офлайн установить нельзя; уже установленный навык работает без сети.
  Ошибка «Опубликованный стабильный Release … не найден» значит, что на
  GitHub ещё нет подходящего выпуска: укажите `--tag`.
- **Сертификаты (SSL).** На macOS с Python с python.org запустите
  «Install Certificates.command» из папки Python в «Программах».
- **Git не найден или не завершился.** Установите Git и откройте новый терминал.

Доверие основано на фиксированном GitHub-репозитории, HTTPS, опубликованном
теге, точном commit и хешах файлов; это не независимая цифровая подпись.
Подробности — [docs/install.md](docs/install.md), Windows — [docs/windows.md](docs/windows.md).

### Работа прямо из исходников (для разработки)

Копирование папки `skills/aispa` из ветки `main` не является установкой выпуска.
Если нужно, скопируйте **всю** папку в свободный каталог из таблицы шага 3,
не объединяя с существующей версией.

В кандидате 0.3.0 `init` требует явный `--runtime codex|claude-code|cursor|openclaw|gemini|antigravity`: агент берёт
значение из фактической среды, не угадывая по переменным окружения. Операция
создаёт ссылки в правилах проекта, локальную историю и закреплённую копию пакета;
все команды прогона идут через эту копию.

`.aispa/context/` содержит производные документы; канон — журнал и неизменные
источники `.aispa/runs/`. Частные брифы исключаются из Git вместе с `.aispa/`.
Добавленные ссылки в корневых правилах проекта нужно учитывать при коммите.

Автоматические проверки используют синтетические входы и отчёты: они проверяют
контракты движка. Нативный двухволновой пилот alpha.10 в Codex на macOS завершён
на закреплённом runtime, указанном в его протоколе;
Claude Code, Cursor и пользовательская приёмка требуют отдельного подтверждения.
В alpha.7 повторён замер контекста на том же снимке: известные файлы и память
дали −9,246% входа после чтения и −5,083% суммарного input, 12/12 фактов в каждом
запуске. Это результат одного малого проекта. Предварительные Releases выходят
после финальной проверки; факт публикации и проверки ресурсов фиксируется отдельно.
Для кандидата 0.1.0 публикация и свежая матрица CI ещё должны быть подтверждены
в его собственном отчёте; исторические результаты этого не заменяют.

## Разработка

Python 3.11+ и Git; на Windows нужен Git for Windows. Сторонних
Python-библиотек нет. Node 18+ нужен для тестов интерфейса. Из корня:

```bash
python3 -B -m unittest discover -s tests -v
node --test tests/dashboard.test.cjs
```

В PowerShell: `python -X utf8 -B -m unittest discover -s tests -v`
или `py -3 -X utf8 -B -m unittest discover -s tests -v`. Для CLI и проверки
продукта выбирайте один и тот же Python; [пример для Windows](docs/windows.md)
фиксирует его полный путь. Полный набор включает clean-run, CLI, blind и
реальную offline-установку зависимости в отдельную venv. Результат на Windows
подтверждается только нативной строкой матрицы CI для конкретного commit.

Проверки GitHub Actions запускаются вручную для проверенного набора изменений.
Отдельный workflow упаковывает ресурсы только после публикации Release.
Фактический результат проверок привязывается к commit SHA, а не к тексту
README. Структура и ограничения — [AGENTS.md](AGENTS.md).
