[Первый парный тест alpha.10](docs/validation-alpha.10-paired-test.md):

Обе версии прошли 61 скрытую проверку; дополнительное слепое ревью выявило

по скорости, стоимости и качеству один опыт не доказывает.

AISpa ведёт разработку от исходного брифа до проверяемого результата.
Слова владельца, требования, задачи, решения и доказательства связаны
сохранённой историей. Отчёт исполнителя сам по себе не завершает задачу.

В рабочей версии после alpha.10 добавлены заготовки отчётов без автоматических
оценок, `--compact` для служебных ответов и стабильные адреса контекста по SHA.
Шапка панели ведёт на публичный канал мастерской. Это изменения Git,

событием и пробелы учёта подготовительных фаз. Его замороженные результаты
не меняются; исправления находятся в следующем Git-кандидате ниже.

## Как работает

- По явному вызову сначала проверяется опубликованный GitHub Release.
  Обновление подготавливается для просмотра и устанавливается только после
  выбора пользователя. Без сети работа продолжается с текущей версией.
- Пользователь выбирает полный автомат, только важные вопросы или интервью.
  Вопросы заканчиваются при подготовке брифа; обязательное ядро фиксируется
  до разработки. Существенные решения агента сохраняются.
- Каждая исходная часть брифа получает отдельный учёт и независимую сверку до
  `seal`. Для действующих функций проверяются восемь сценариев, включая ошибки,
  пустые данные и повторный вызов. Стыки между частями системы связываются с
  задачами и проверками. Неучтённый источник не исчезает из проекта молча.
- До фиксации брифа агент разбирает саму идею: проблему, пользователя, результат,
  альтернативы, небольшой проверочный эксперимент и сценарии отказа. Гипотезы
  отличаются от наблюдений; полезное дополнение не заменяет исходное требование.
  Отдельно разбираются спрос, польза и расходы, эксплуатация, повторное
  использование и другие участники. Решения проходят сверку со спецификацией.
- Перед спецификацией агент изучает существующий проект: архитектуру, данные,
  точки входа, зависимости, команды, правила и риски. Наблюдения связаны с
  файлами и их контрольными суммами; неопределённость указывается явно.
- В проекте поддерживаются бриф, спецификация, план, решения, прогресс и краткая
  память. Новый прогон сохраняет историю и остатки предыдущих, а текущий объём
  определяется новым брифом и отдельными решениями по остаткам.
- Каждую задачу выполняет отдельный исполнитель. Первый независимый критик
  с PASS передаёт её отдельному приёмщику, сверяющему результат с исходными
  словами владельца. WARN/BLOCK/FAIL требуют ремонта и второго свежего
  критика. У старых закреплённых прогонов остаётся их прежний контракт.
- Нативные участники разных фаз записываются по реальным ID среды. История
  использования моделей учитывает всех зарегистрированных участников; сумма
  не объявляется полной, если часть usage отсутствует.
- Перед запуском план проверяется на лишнее дробление. Связанные части можно
  объединить, сохранив каждое условие, причины риска и внешние зависимости.
  Число задач уменьшается; независимая критика и отдельная приёмка сохраняются.
  План связывает задачи в проверяемые пользовательские результаты. Миграции
  разделяют добавление нового, перенос потребителей и удаление старого;
  каждому шагу нужны проверки совместимости и восстановления.
- После первого FAIL записывается причина и план ремонта. Локальный дефект
  может исправлять исходный исполнитель; недостаток контекста или неверный
  подход требуют свежего исполнителя. Третий круг автоматически не возникает.
- После волны независимый проверяющий сверяет весь бриф. Финальная приёмка
  проекта остаётся отдельным этапом. Изменение источников или кода может
  сделать прежнее доказательство устаревшим.
- Перед сдачей проверяются сквозные интеграции и намерение тестов: что именно
  проверяла команда, где кончается её покрытие и какие сценарии ещё не испытаны.
  Успешный код возврата при усечённом выводе не считается PASS.
- Финальная приёмка новых прогонов требует проверки сохранённого
  commit в отдельном чистом клоне. Проверяющий сначала получает исходный бриф
  и продукт, затем сверяет свои наблюдения с реестром требований.
- До чистого клона в обычных файлах Git готовятся инструкция запуска,
  архитектура, решения и словарь подходящего проекту размера. Для маленького
  проекта достаточно одного README с обоснованными исключениями. Команды
  связаны с сохранёнными фактическими выполнениями; приватный бриф не экспортируется.
- Если ядро принято, второстепенные недоделки допускают результат
  «основная часть готова, есть остатки». Они остаются в учёте.
- Оборванный конец журнала можно восстановить только после осмотра точного SHA
  и побайтной резервной копии. Прогон остаётся на паузе до свежей проверки и
  отчёта независимого участника; неизвестные внешние эффекты блокируют возврат.
- После приёмки отдельный автор читает готовый код и сохраняет проверенные
  команды, ловушки, причины решений и словарь. Следующие задачи получают
  только относящиеся к ним свежие записи; старая проверка не становится новым PASS.
  Входная инструкция короткая: подробные шаги открываются по текущей фазе.

Python-движок записывает роли, переходы и доказательства. Нативных агентов
создаёт Codex, Claude Code или Cursor доступными инструментами сессии.
Вызовов модельных провайдеров внутри движка нет; записанные ID не являются
криптографическим подтверждением независимости модели.

Локальный дашборд можно запустить повторно без второго сервера. Он показывает
ожидание владельца и последние события; интерфейс имеет русский и английский
языки, системную, светлую и тёмную темы. Отдельный экспорт — исторический
снимок: он не опрашивает живой сервер и не выдаёт старую приёмку за текущую.

## Попробовать альфу

Вход — [skills/aispa/SKILL.md](skills/aispa/SKILL.md). Для опубликованного
пакета используйте [первый установщик из Release](docs/install.md): он
показывает точную версию, commit и destination до записи. При работе прямо с
исходным checkout для разработки копируйте **всю папку** `skills/aispa` в
свободный проектный каталог и не называйте это установкой опубликованного
выпуска:

| Среда | Каталог | Явный вызов |
|---|---|---|
| Codex | `.agents/skills/aispa/` | `$aispa` |
| Claude Code | `.claude/skills/aispa/` | `/aispa` |
| Cursor | `.cursor/skills/aispa/` | `/aispa` |

Если одноимённый пакет уже существует, сначала сохраните его. Не объединяйте
версии поверх друг друга. Начните с небольшого проекта без реальных платежей
и пользовательских данных. Установка в пользовательские каталоги skills
не выполняется автоматически.

`init` требует явный `--runtime codex|claude-code|cursor`: агент берёт значение
из фактической среды, не угадывает его по переменным окружения. Операция создаёт
проектные ссылки в правилах, локальную историю и закреплённую копию пакета.
Все дальнейшие команды прогона идут через эту копию. Обновление установленного
навыка не переписывает активный runtime.

`.aispa/context/` содержит производные документы; канон — журнал и неизменные
источники `.aispa/runs/`. Частные брифы исключаются из Git вместе с `.aispa/`.
Добавленные ссылки в корневых правилах проекта нужно учитывать при коммите.

## Разработка

Python 3.11+ и Git; на Windows нужен Git for Windows. Сторонних
Python-библиотек нет. Node 18+ нужен для тестов интерфейса. Из корня:

```bash
python3 -B -m unittest discover -s tests -v
node --test tests/dashboard.test.cjs
```

В PowerShell: `python -X utf8 -B -m unittest discover -s tests -v`
или `py -3 -X utf8 -B -m unittest discover -s tests -v`. Для CLI и проверки
продукта выбирайте один и тот же Python; [пример для Windows](docs/windows.md)
фиксирует его полный путь. Полный набор включает clean-run, CLI, blind и
реальную offline-установку зависимости в отдельную venv. Результат на Windows
подтверждается только нативной строкой матрицы CI для конкретного commit.

Проверки GitHub Actions запускаются вручную для проверенного набора изменений.
Отдельный workflow упаковывает ресурсы только после публикации Release.
Фактический результат проверок привязывается к commit SHA, а не к тексту
README. Структура и ограничения — [AGENTS.md](AGENTS.md).
